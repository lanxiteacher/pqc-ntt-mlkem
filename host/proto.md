### 「协议」是什么，用大白话讲

两个人用对讲机联络，事先得约好一套暗号——「先说什么、对方回什么、每个字什么意思」。不约好就会出现这种局面：甲按自己的理解喊了一句，乙按自己的理解听成了另一件事，**两个人都不觉得自己错，但说的根本不是一回事**。

串口协议就是这份暗号本。它管的是：**谁先开口、开口说什么词、后面跟多少个数字、对方怎么回、多久没回算作废**。

而板子和电脑之间连着一根线，线上只能一个字节一个字节地流过去——**没有任何一个字节自带「我从哪来、我到哪去、我属于第几个数」的标签**。标签只能事先约好。这就是「协议不冻结，两边一定对不上」的原因。

## 二、这个文件的作用

**它是一份「暗号本」，不是代码。**

| | 是什么 | 几份 | 谁写 |
|---|---|---|---|
| **`host/proto.md`（本文件）** | 暗号本本身（规矩） | **一份，共享** | B 起草，两边一起改 |
| A 的板子端代码 | 照着暗号本，实现板子那一端 | 一份 | A |
| B 的上位机代码（`host/src/`） | 照着暗号本，实现电脑那一端 | 一份 | B |

```
        host/proto.md   ← 一份，两边共用
             │
     ┌───────┴───────┐
     ▼               ▼
A 写板子端       B 写电脑端      ← 这才是"各写一端"
```

**它解锁什么、不写会卡住什么：**

- **不写，A 的板子端没法开工。** `host/README.md:20` 原文：「**协议两侧各实现一端。** 板子侧是 A 写的。协议不冻结，两边一定对不上（见 H3）。」
- **不写，B 的上位机也没法开工。** 上位机要往串口写什么字节，完全由本文件决定。
- **不写，B 的「假串口」没法做。** `host/README.md:18` 原文：「**先对仿真跑通协议，再上板。** UART 收发灌进 testbench（`refsim/`），在真板子之前把协议跑通。上板时变量只剩"硬件对不对"一个。」

**两条纪律（本文件要求两边一起守）：**

1. **上位机里不允许出现任何「等板子」的特殊分支。** 上位机面对的永远是一个「字节流接口」——仿真里的假串口和真板子必须在它眼里完全同构。否则「仿真通过了」这句话就不构成对上板的任何保证。
2. **板子端的解析层就是板子端代码本身，不要另写一个「仿真版」。** 仿真时把字节流灌进解析层即可；上板时换掉的只有外面的引脚。

## 三、术语速查

本节覆盖正文里反复出现的术语。只出现一两次的专名（如 `AXI-Lite`、XDC）在用到的地方就地解释，不在这里堆。

| 术语 | 一句话解释 | 生活化比喻 |
|---|---|---|
| **串口** | 电脑和板子之间那根 USB 线，数据一个字节接一个字节地流 | 一根单车道的小路，车只能一辆接一辆过 |
| **波特率** | 这条路每秒能过多长的车队。本项目 **115200-8N1** | 车道限速。8N1 = 每个字节要 10 个「车位」（1 起始 + 8 数据 + 1 停止），所以 **115200 ÷ 10 = 11520 字节/秒** |
| **上位机** | 跑在电脑上的那个程序：发数据、收结果、自动比对 | 发号施令的一方。本项目里就是 `host/src/` 里的程序 |
| **帧 / 行** | 一次完整的消息单位。本协议里「一帧 = 一行」 | 一句话。约定「话说完了就换行」，换行符就是句号 |
| **命令字** | 开头的几个大写字母，告诉对方「我要你做哪件事」 | 对讲机里的呼叫代号 |
| **载荷** | 命令字后面真正要传的数据本体 | 信封里的信纸 |
| **校验** | 附在消息尾巴上的一小段数，用来判断这行有没有被传坏 | 信封上的封蜡：蜡完好 = 没被拆过；蜡碎了 = 这封信不可信 |
| **异或（XOR）** | 两个二进制位**不同记 1、相同记 0**；把一行的每个字节依次这么比下来，得到一个 8 位数当校验 | 两个人对暗号，逐字比：不一样就记一笔。比完整句话，看一共记了几笔 |
| **十六进制** | 用 `0`~`9` 和 `a`~`f` 共十六个符号写数。`0x0A` = 10，`d00` = 3328 | 十进制「逢十进一」，它「逢十六进一」。**4 个二进制位 = 1 位十六进制**，所以 12 位正好 3 位 |
| **ASCII** | 每个字符对应的一个数字编号（`'#'`=0x23、`'P'`=0x50）。校验算的就是这些编号 | 每个字在字典里的页码 |
| **RTL / Verilog** | 用来描述硬件电路的语言。A 写的就是它 | 把电路图画成文字 |
| **PL / PS** | ZYNQ 一颗芯片里的两块东西：PL = 可编程逻辑（FPGA 部分），PS = 片上的 ARM 处理器 | 一颗芯片里住着两个人：PL 是「能现场改接线的电路」，PS 是「一台小电脑」 |
| **testbench** | 专门给电路喂输入、比输出的仿真代码，不参与真实电路 | 试车台：先架起来空跑，不上真路 |
| **BRAM** | FPGA 片上自带的存储块，用来存那 256 个系数 | 芯片内部的草稿纸，比外部内存近得多 |
| **超时** | 「等太久了就当下没发生」，绝不无限等下去 | 电话响 30 秒没人接就挂，不是举着听筒等到天荒地老 |
| **行尾 LF** | 每行末尾那个「换行」字符，十六进制 **0x0A**。全项目统一只用它 | 句号。**只用一种句号**；混用会让「256 行字全一样」的两份文件被判成「256 行全不同」 |
| **假串口** | 在电脑仿真里冒充板子的那段程序，让上位机以为自己在跟真板子说话 | 排练用的替身演员。先跟替身把台词对熟，正式演出才不会砸 |
| **黄金向量** | B 已经做好的一套「标准答案」数据文件（`refsim/batch/*.txt`），板子的输出必须和它一模一样 | 考卷后面的标准答案 |
| **系数** | 数据的最小单位，一个 0…3328 的整数 | 队伍里的一个士兵 |
| **多项式** | 256 个系数排成的一串 | 256 人的方阵 |
| **模数 q = 3329** | 所有加减乘运算最后都对 3329 取余，所以结果永远落在 0…3328 | 钟表只有 12 格，指针转到 13 点就变成 1 点 |
| **NTT（正变换）** | 把 256 个系数换一组「更好算乘法的表示」 | 把一堆乘法题先翻译成加法题 |
| **INTT（逆变换）** | NTT 的反操作，把表示换回来 | 翻译回中文 |
| **点乘（PMUL）** | 两组系数一组对一组相乘，是 ML-KEM 里最耗时的步骤 | 两个方阵的士兵一对一拼刺刀 |
| **H1 / H3 / H6 / H7** | 计划里给「交接点」编的号。H1 = A 给 B 的端口说明；H3 = 串口协议；H6 = A 给 B 的 `.bit` 文件；H7 = C 要的演示页数据格式 | 两个部门之间的交接单编号 |

### 4.2 数据条数：每组 256 个系数

- 一个多项式 = **256 个系数**。依据：`refsim/gen_batch_vectors.py:38-40` 写死 `N = 256`、`NV = 16`；RTL 侧 testbench 按 `[0:NV*256-1]` 声明数组（`refsim/pe1/fntt_batch_tb.v:43`）。
- `refsim/batch/` 下的**批量向量文件**（`ntt_batch_*` / `intt_batch_*` / `pwm2_batch_*` / `fullmul_*` / `halfmul_*`）每个 **4096 行 = 16 组 × 256**（实测：全目录 53 个 `.txt`，其中 **15 个** 是 4096 行）。
  ⚠️ **数行数数出来的 4096 是 16 个多项式，不是 1 个。协议一次事务传的是 256 行。** 这是写协议时最容易踩的坑。
- 另有已经切好的**单组**文件：`refsim/batch/vin_00.txt` … `vin_15.txt`，各 **256 行**，每行 3 位小写（**实测全部合规**）——这才是可以直接当「一组」用的样板。
  - ⚠️ `vref_00.txt` … `vref_15.txt` 行数同样是 256，但**格式不合规**：实测 16 个文件**全是变长**（`vref_00.txt` 头三行就是 `74` / `61d` / `853`）。照 §5.3.1「必须恰好 3 位」去解析会被判 `#ERR 04`。它们是**期望值**（对拍用），不用于上行，也不要当格式样板。
  - ⚠️ 这 32 个 `vin_*` / `vref_*` 文件在仓库里**没有任何脚本或 testbench 引用**（`refsim/README.md` 也没提），目前只是备着。
  - 实测：`refsim/batch/` 里另外 38 个 `.txt`（`vin_*` 16 个、`vref_*` 16 个、`_full_ref` / `_half_ref` / `_gen_scratch_*` 6 个）都是 **256 行**。

### 4.3 一个系数的位宽：12 位

- 模数 **q = 3329**（`competition_guide_notes.md:96`、`research/pqc-ntt_ml-kem_compendium.md:42`、`README.md:15`）。
- 系数取值范围是 **0 … 3328**，共 3329 个值，恒为非负，**线上不需要传符号位**。
- 2^11 = 2048 < 3329；2^12 = 4096 ≥ 3329 → **至少 12 位**。
- 仓库里每一处也都按 12 位处理：RTL 顶层端口 `input [12*PE_NUMBER-1:0] din`（`rtl/pe1/KyberHPM1PE.v:40-41`；`KyberHPM1PE_top.v` 里在 `:20`）；各 C 工具统一用 `& 0x0FFF` 掩码（`refsim/ntt_once_tool.c:70`）。
- **实测核对**：`refsim/batch/` 主要向量文件里最大值确为 **3328（`d00`）**，在 `pwm2_batch_exp.txt` 与 `fullmul_exp.txt` 里都出现过；超过 3328 的行数 = 0。

> ⚠️ **顺带一处要修的文档小错**：`refsim/README.md:119` 写「覆盖 0..3327 全域，无越界」，**实测存在 3328**。**3328 是合法值**，本协议按 `0..3328` 写。
>
> ⚠️ **但本协议不检查系数范围。** 数据行只做「恰好 3 位十六进制」的**格式**检查（§5.3.1、§5.5），取值范围没有任何一条规定。所以 `d01`（= 3329）会被照收照算，**不会**报错。要让越界系数变成 `#ERR`，那是一条**新增规定**，得两边一起定（与 §六 第 6 条「行级检查做到多严」是同一类问题）。**当前草案的口径是：不查。**

## 五、草案详细内容

### 5.1 帧格式总览（协议里只有三种「行」）

**总原则：一次事务 = 一问一答。电脑发一条命令，板子把结果发回来，回完了再发下一条。不流水线、不排队。**

行与行只靠 **LF（`\n`，0x0A）** 分隔。**行的身份由第一个字符决定，不需要任何「帧头」。**

```
  行的种类          长相                          方向        谁能发
  ──────────────────────────────────────────────────────────────────
  命令行 / 应答行   # ...... *xx                 双向        两边都发
  数据行            [0-9a-f][0-9a-f][0-9a-f]      双向        两边都发
  空行              （只有一个 LF）               任意        一律忽略
```

**判断规则（几行就能背下来）：**

- 首字符是 **`#`** → 命令行 / 应答行
- 首字符是 **`0`~`9` / `a`~`f`（板子端也接受 `A`~`F`）** → 数据行
- 只有一个 LF 的空行 → **忽略**（这样传送末尾多一个换行不会致命）
- 其他 → 格式错误

> ⚠️ **大写的归属必须写死。** 本协议**要求电脑端只发小写**（§5.3.1、§5.4），但**板子端宽容接收**大写。两句话不矛盾，可是**分派规则必须以「含大写」的版本为准**——否则一行 `A2f` 按小写规则既不是命令行、也不是数据行，两端各判一个样。
> 板子端收到含大写的数据行时，**按数值等价处理**（`A2f` = `a2f` = 2607），不回错、也不要求电脑端改。

**为什么不需要「帧头 `AA 55`」**：同步靠三条自带冗余，不用额外加同步字——

1. **命令行的参数被回显。** 电脑发 `#PMUL TIME 1`，板子必须回 `#OK PMUL TIME 1`。对不上就说明有一端错位了。
2. **数据行的条数由命令决定，不由数据自己决定。** `#NTT 1` 后面必须跟正好 256 行；多一行、少一行、中间夹一行 `#` 开头的，全部判错。
3. **`#BEGIN <原命令> <count>` 里的 count 必须和后面实际行数相等。**

**一条完整事务的时序（以「点乘」为例）。⚠️ 这是两段式，不是流水线：**

```
①  电脑 → 板子：  #PMUL TIME 1*03 ⏎            ← 命令：算点乘，A 在时域，1 组
    ┈┈ 电脑在此停下，等板子回话（T_OK = 1 秒）┈┈

②  板子 → 电脑：  #OK PMUL TIME 1*27 ⏎          ← "命令收到、参数合法"（回显参数供核对）
    ┈┈ 电脑核对无误，这时才开始灌数据 ┈┈

③  电脑 → 板子：  044 ⏎                        ← 数据行 1（A 的第 0 个系数）
                  437 ⏎                        ← 数据行 2
                  ...                          ← A 共 256 行
                  61d ⏎                        ← A 的第 255 个系数
                  074 ⏎                        ← 接着是 B（已在 NTT 域），共 256 行
                  ...
                  853 ⏎                        ← B 的第 255 个系数   （下行共 512 行）
    ┈┈ 灌完，等板子出结果（T_BEGIN = 5 秒）┈┈

④  板子 → 电脑：  #BEGIN PMUL TIME 1 256*75 ⏎  ← "算完了，下面 256 行是结果"
                  000 ⏎                        ← 结果第 0 个系数
                  ...
                  d00 ⏎                        ← 结果第 255 个系数
                  #DONE PMUL TIME 1 256*32 ⏎   ← "本条事务结束"
```

> ⚠️ **上面的箭头是「先后顺序」，不是「同一时刻」。** 两列各自是一条独立的泳道，竖排对齐只表示次序。
> **电脑在收到 `#OK` 之前，一个数据字节都不许发**——第 ① 步和第 ③ 步之间夹着板子的回话，不是省略号。这条以前一版画反了，照图实现会两边互等。
> 反过来说：**板子收到完整命令行后必须立刻回 `#OK`，不能等数据。** 否则电脑等 `#OK`、板子等数据，**双方死锁**——这正是本文件要消灭的故障模式。

`#OK` 和 `#BEGIN` 分成两行是刻意的：**`#OK` 的到达时间 = 板子「有没有在听」；`#BEGIN` 的到达时间 = 板子「算了多久」**。板子没通、板子卡死、算得太慢，这三种故障靠这一对时间戳就能分开。

### 5.2 命令字表

**电脑 → 板子**

| 命令 | 参数 | 后面要跟的数据行数 | 功能 | 对应 A 的现有端口 |
|---|---|---|---|---|
| `#PING` | 无 | 0 | 探活。确认 COM10 后面真有东西在听 | — |
| `#NTT <n>` | n = 组数（**冻结为 1**，见 §六 第 2 条） | `n×256` | 正向 NTT（时域进、NTT 域出） | `load_a_f` → `start_fntt` → `read_a` |
| `#INTT <n>` | 同上 | `n×256` | 逆向 INTT（NTT 域进、时域出） | `load_a_i` → `start_intt` → `read_a` |
| `#PMUL NTT <n>` | 域词 + 组数 | `2n×256`（**前 A 后 B**） | 点乘，**A、B 都已在 NTT 域**。不做 NTT、不做 INTT | `load_a_i` + `load_b_i` → `start_pwm2` → `read_a` |
| `#PMUL TIME <n>` | 域词 + 组数 | `2n×256` | 点乘，**A 在时域、B 已在 NTT 域**。板子对 A 做一次 FNTT，点乘，再 INTT → **结果是时域** | `load_a_f` + `load_b_i` → `start_fntt` → `start_pwm2` → `start_intt` → `read_a` |
| `#PMUL FULL <n>` | 域词 + 组数 | `2n×256` | 点乘，**A、B 都在时域**。板子对 A、B 各做一次 FNTT，点乘，再 INTT → **结果是时域** | `load_a_f` + `load_b_f` → `start_fntt`（A，`start_ab=0`）→ `start_fntt`（B，`start_ab=1`）→ `start_pwm2` → `start_intt` → `read_a` |
| `#ABORT` | 无 | 0 | 放弃当前事务，立刻回到「等命令」状态 | — |
| `#LAYERS <n>` | ⚠ 预留，未定 | 未定 | 逐层蝶形中间结果导出。**受 C 的 H7 影响，见 §六 第 10 条** | — |

> ⚠️ **`n > 1` 时下行 `2n×256` 行怎么交错，本草案没有定义**（是 `A₁B₁A₂B₂…` 按组交替，还是 `A₁…Aₙ B₁…Bₙ` 按对象分块）。因为 §六 第 2 条建议**先冻结为 `n = 1`**。将来要放开 n，这块必须先单独定死。

**三种点乘分别对拍哪个文件**（电脑端判「这条过了没有」时用）：

| 命令 | 结果在哪个域 | 对拍 `refsim/batch/` 里的 |
|---|---|---|
| `#PMUL NTT` | NTT 域 | `pwm2_batch_exp.txt` |
| `#PMUL TIME` | 时域 | `halfmul_exp.txt` |
| `#PMUL FULL` | 时域 | `fullmul_exp.txt` |

（依据：三个 testbench 各自 `$readmemh` 的向量来源——`refsim/pe1/pwm2_batch_tb.v:47-49`、`halfmul_batch_tb.v:47-49`、`fullmul_batch_tb.v:50-52`。）

**为什么域词省不掉，以及为什么是「A 在时域」而不是「B 在时域」：**

`refsim/README.md:218-238` 记着数据有两种摆放——`load_*_f` 灌 BRAM **低半区**（给 FNTT 用，时域），`load_*_i` 灌**高半区**（给 INTT／点乘用，已展开的 NTT 域）。原文：「用错了不会报错，数据也一个不少地进去了，只是**位置不对**，结果是 256 个系数全错 —— 而"全错"又很容易被误判成 RTL 有 bug。」

⚠️ **更要紧的一层：现有核只有三个启动信号**（`rtl/pe1/KyberHPM1PE.v:39` 的 `start_fntt` / `start_pwm2` / `start_intt`），**没有「只对 B 做 FNTT」这种模式**——FNTT 永远作用在 A 那一路上（B 那一路由 `start_ab` 选中，见 `fullmul_batch_tb.v:124`）。所以「**A 在时域、B 已在 NTT 域**」是唯一能省掉一次变换的组合（实测调用顺序见 `refsim/pe1/halfmul_batch_tb.v:86-149`）。
**这一条早期草稿写反过**（写成「B 是时域」），照它实现会得到 256 个全错的系数、而且不报任何错。

这种「静默错误」只能靠协议显式声明域来堵。用英文单词而不是单个字母（`F`/`I`），是为了抓下来的日志自己会说话——**扫一眼就知道对不对，不需要靠记忆去映射缩写**。

**板子 → 电脑**

| 应答 | 参数 | 功能 |
|---|---|---|
| `#OK <原命令> <原参数>` | 回显 | 命令收到、参数合法。**必须回显**，这是同步的第一道保险 |
| `#BEGIN <原命令> <count>` | count = 即将发出的数据行数 | 计算完成，结果开始 |
| `#DONE <原命令> <count>` | 同上 | 本条事务结束 |
| `#ERR <code> <位置> <详情>` | 见下表 | 出错，放弃本条事务 |
| `#RDY <ver> <build> <errs>` | ⚠ 上电后板子主动发一次 | 让电脑自动识别板子。**需 A 确认要不要加**（§六 第 8 条） |

**错误码**

| code | 名字 | 含义 | 「位置」填什么 |
|---|---|---|---|
| `01` | 未知命令 | `#` 开头但不是上表里任何一个 | `0` |
| `02` | 参数非法 | n 不在允许范围；域词不是 `TIME`/`NTT` | 出错字段的序号 |
| `03` | 校验错 | 命令行 `*xx` 对不上 | 回 `got=<实际> exp=<应有>` 两个值 |
| `04` | 数据行格式错 | 一行不是恰好 3 位十六进制；或数据段里出现了 `#` 开头的行（`#ABORT` 除外） | 第一个非法字符的位置 |
| `05` | 数据行数不足 / 行超时 | 等一行等超时了（数值见 §5.5） | 已收到的行数 |
| `06` | 板内错误 | 算法核没在预期时间内回 `done` | `0` |
| `07` | 忙 | 上一件事还没算完又收到命令 | `0` |

`03` 的回帧长这样：`#ERR 03 got=3f exp=a2*52` —— **两个值都回**，人一眼能看到差在哪，比只说「校验失败」有用得多。

> `07`（忙）在正常流程里**不可能出现**（一问一答，电脑在收到回复前不会发下一条）。它的意义是：**万一出现了，说明有一端的状态机没守住规矩**——所以它是一条断言，不是一条正常路径。

**端到端的顺序义务**（写清楚，避免「两边都以为自己对」）：

- 电脑发命令后，**必须**等到 `#OK` 才发数据行；数据行发完**必须**等到 `#DONE` 才能发下一条命令。
- 板子发出 `#OK` 之后只认数据行；发出 `#DONE` 之前不接受新命令。
- 一次事务中，电脑**不许**中途插入 `#` 开头的行（`#ABORT` 除外）。

### 5.3 数据编码

#### 5.3.1 一个系数怎么写

**核心算式：12 位 ÷ 4 位（每个十六进制字符）= 正好 3 个十六进制字符。** 一个不多、一个不少——这就是「每系数 3 字符」的来历，不是凑出来的土办法。

- 写法**照抄仓库里已经冻结的那一套**（`team/FPGA竞赛_B_Claude环境对齐指南.md:236`）：**小写、补零到 3 位、不带 `0x` 前缀**。例：`044`、`437`、`4d0`、`d00`。
  - ⚠️ 「已冻结」指的是**H2 黄金向量的文件口径已经定了**；「本协议在线上用不用这个口径」仍然是 §六 第 5 条的待决项。两句不矛盾——**默认照它写，要改就一起改**。
- `004` 合法；`4` 和 `04` **不**合法（长度必须正好 3）。
- **板子端宽容接收**：收到大写 `A`~`F` 也照收。这是为了容错，不改变格式。
- **电脑端必须发小写**：因为要和 `refsim/batch/` 的文件字节一致，否则 `diff` 又会被判「256 行全不同」。
- 一行 = 3 个字符 + 1 个 LF = **4 字节**。

**这个选择的理由**：电脑端读 `refsim/batch/*.txt` 时**一个字符都不用转换**，把文件按 256 行切片后逐行写串口即可（不需要任何位拼接代码）；仿真侧的假串口 testbench 也可以把同一个文件的字节直接喂进 UART 接收端；板子回传的结果格式也和 testbench 现在 dump 出来的 `%03x` 文件同形。

> ⚠️ **别拿这几个文件当格式样板**：实测 `refsim/batch/fullmul_exp.txt`（22 行 1 位 + 269 行 2 位 + 3805 行 3 位）、`halfmul_exp.txt`、`halfmul_b.txt` 是**变长**的（生成端用 `%03x`、工具端用 `%x`，见 `refsim/gen_batch_vectors.py:117,139` 与 `refsim/polmul_full_tool.c:85`）。**同样变长的还有全部 16 个 `vref_*.txt`**（详见 §4.2）。合规样板以 `ntt_batch_*.txt` / `intt_batch_*.txt` / `pwm2_batch_*.txt` 为准（实测这三套 4096 行长度全为 3）。

#### 5.3.2 算一遍（传输时间）

```
链路速度 = 115200 波特 ÷ 10 位每字节 = 11520 字节/秒
          （8N1 = 1 起始位 + 8 数据位 + 1 停止位 = 10 位/字节）
```

| 场景 | 系数个数 | 字节数 = 系数 × 4 | 传输时间 = 字节 ÷ 11520 |
|---|---|---|---|
| 一个多项式（单向） | 256 | 1024 B | **88.9 ms** |
| 一次 NTT 或 INTT 事务（进 256 + 出 256） | 512 | 2048 B | **177.8 ms** |
| 一次 PMUL 事务（下行 A 256 + B 256，上行结果 256） | 768 | 3072 B | **266.7 ms** |
| 整批 16 组 NTT | 8192 | 32768 B | **2.844 s** |
| 整批 16 组 PMUL | 12288 | 49152 B | **4.267 s** |

控制行开销：每条事务 4 条控制行（`#命令` / `#OK` / `#BEGIN` / `#DONE`）。按本文件的格式实测（含 `*xx` 校验与 LF）：`#PMUL TIME 1*03` = 16 B、`#OK PMUL TIME 1*27` = 19 B、`#BEGIN PMUL TIME 1 256*75` = 26 B、`#DONE PMUL TIME 1 256*32` = 25 B，合计 **86 字节 ≈ 7.5 ms**，占 3072 字节的 **2.8%**，可以忽略。（`#BEGIN` / `#DONE` 还带 count 字段，比一般控制行长一点，所以不能按「15~18 字节」估。）

**单行时间：4 字节 × 10 位 ÷ 115200 = 347 µs。** 这个数是 §5.5 超时取值的基准。

#### 5.3.3 对照：二进制编码值多少

| 编码 | 每系数字节 | 整批 16 组 PMUL | 相对本方案 |
|---|---|---|---|
| **本方案：文本 3 位 hex + LF** | **4 B** | 49152 B → **4.267 s** | 基准 |
| 2 字节/系数（12 位塞进 16 位格子） | 2 B | 24576 B → 2.133 s | 快 2.1 秒 |
| 打包：两个 12 位塞进 3 字节 | 1.5 B | 18432 B → 1.600 s | 快 2.7 秒 |

（1.5 B/系数的来历：12 + 12 = 24 位 = 正好 3 字节；256 个系数是偶数，刚好整除、无补位。）

**这 2.1~2.7 秒就是本方案买「零转换代码 + 可直接比对 + 可用串口助手手工调试」付的钱。** 参考量级：板子算一次 FNTT 是 **18.1 µs**（`rtl/H1_port_spec.md` §七：pe1 共 905 拍 @50 MHz），链路上本来就慢 3~4 个数量级——**慢的是链路，不是这一倍**。

> ✅ **仓库内部那两处"打架"的估算已查清（2026-09-29）**：它们**不是矛盾，是同一个公式的不同档位** —— 都是「字节数 × 10 ÷ 115200」，数字都没错。2 字节/系数 = 512 B → 44.4 ms；1.5 字节/系数 = 384 B → 33.3 ms；本草案 3 位 hex = 4 字节/系数 = 1024 B → **88.9 ms**（256 × 4）。三档实测基准见 `rtl/H1_port_spec.md` §七。口径统一见 §六 第 5 条。

#### 5.3.4 结果回传顺序（必须定义，否则「全对但位置全错」）

RTL 读出的物理顺序**不是**系数自然序（`refsim/README.md:206-216`；**INTT 一行的最终依据是 `rtl/H1_port_spec.md` §三 的 iverilog 实测**）：

| 运算 | 输入顺序 | 输出顺序 |
|---|---|---|
| FNTT（正变换） | `0,2,1,3,4,6,5,7,...` | `0,2,1,3,4,6,5,7,...` |
| INTT（逆变换） | `0,2,1,3,4,6,5,7,...` | **`0,128,1,129,2,130,...`** ⚠️ 与 FNTT **不同** |
| PWM2（点乘） | A、B 各一份，都是交织序 | `0,2,1,3,4,6,5,7,...` |

`refsim/README.md:209` 原话：「**但 INTT 不一样**，照抄 FNTT 的循环去做 INTT 会得到"256 个系数全错"的假失败。」**两张表的算式各是什么**（`m` = 从第一个有效拍算起的拍序号）：FNTT / PWM2 是「把 `m` 的最低两位对调」—— `下标 = (m & ~3) | ((m & 1) << 1) | ((m >> 1) & 1)`，即组内 `0,2,1,3`；INTT 是「前半本与后半本交叉」—— `m` 偶 → 下标 `m/2`，`m` 奇 → 下标 `128 + (m-1)/2`，即 `0,128,1,129,...`。**两张表不一样，别照抄一张。**

**本草案的规定：板子按自己读出的物理顺序原样回传，电脑端按运算类型决定怎么解包。** 理由：板子少做一个地址映射（A 省事，少一个 bug 源），而电脑端本来就有按运算分立的脚本；一旦电脑端解错，整组对拍会**响亮地失败**（256 个系数全错），不会静默出错。⚠️ **板子端不额外发「序型标志」** —— 电脑端**知道自己刚发的是哪条命令**（`#NTT` → FNTT 序、`#INTT` → INTT 序、`#PMUL NTT <n>` → PWM2 序），从命令就能推出该用哪张表。所以 §5.2 的 `#BEGIN <原命令> <count>` 帧格式**保持原样，不加字段**。

> ✅ **已定（2026-09-29）：甲 —— 原样回传，且不加序型标志。** 见 §六 第 4 条。

#### 5.3.5 落盘时的行尾铁律

电脑端把收到的数据写文件时：

- **必须用二进制模式写**（C 用 `fopen(path, "wb")`，Python 用 `open(path, "wb")`），**LF 行尾**。Windows 会把 `\n` 翻成 `\r\n`，导致 256 个数值全对、`diff` 却报「256 行全不同」。（`CLAUDE.md:96-97`）
- 仓库已在 `.gitattributes` 里用 `* -text`（不做任何行尾转换，存什么取什么）兜底。**不要**改成 `text=auto` 或 `eol=lf`——那两种都会在 checkout 时改写字节。（`.gitattributes:16-18`、`CLAUDE.md:98-100`）
- **不许用 `diff --strip-trailing-cr` 遮掩**行尾差异——那是把症状藏起来，不是修好。（`CLAUDE.md:97`）
- 不要用「网页下载 → 编辑 → 上传」改仓库文件——那条路绕开了 `.gitattributes` 这道防线。（`CLAUDE.md:101-102`）

> ⚠️ **一处必须写清的限制**：上面「结果可以直接 `diff` `refsim/batch/*_exp.txt`」这句话，**只对 `ntt_batch_*` / `intt_batch_*` / `pwm2_batch_*` 成立**（实测这三套每行都是 3 位）。仓库里**变长格式**（1~3 位混排）的是另一批：`fullmul_exp.txt` / `halfmul_exp.txt` / `halfmul_b.txt`，**外加全部 16 个 `vref_*.txt`**，再加 `_full_ref.txt` / `_half_ref.txt` / `_gen_scratch_ntt.txt` / `_gen_scratch_out.txt`（实测 53 个 `.txt` 里共 **23 个**是变长）。若电脑端按 3 位回写，对这些文件会出现「**数值全对、文本不匹配**」——**症状和行尾 CRLF 那个坑一模一样，成因却完全不同**，排查时别认错。
>
> **处理办法（二选一，见 §六 第 5 条）**：
> (a) 对拍**按数值比，不按文本逐字节比**（推荐，一行代码的事）；
> (b) 或在冻结前把 `fullmul_exp` / `halfmul_exp` / `halfmul_b` / 16 个 `vref_*`（共 **19 个**有实际用途的）用 `%03x` 重新生成一遍，让全仓库只剩一种写法。

### 5.4 校验

**分两类，规则不同——这是刻意的。**

| 行类型 | 校验 | 长相 |
|---|---|---|
| **命令行 / 应答行** | **有**。整行（`*` 之前的所有 ASCII 字节，含空格）逐字节异或，取低 8 位，写成 2 位十六进制，前面加 `*` | `#PING*33` |
| **数据行** | **无**。就是 3 位十六进制 + LF，不加任何后缀 | `044` |

**算法（手工可算，这是选它的主因）：**

> 把行里 `*` 之前的每一个字节（就是每个字符的 ASCII 码）依次做异或，取低 8 位，写成 2 位**小写**十六进制，接在 `*` 后面。

**四条必须写死的细则**（不定死就是两端各写一版、所有行都报校验错）：

1. **覆盖范围**：从**行首第一个字符**（含 `#` 和空格）起，到 **`*` 之前**（不含 `*`）。不定这条，两边会各写一版。
2. **`*` 本身、LF（`\n`）、被忽略的 CR（`\r`）都不参与计算。**
3. **`*` 后面必须正好 2 位**，0-9 与 a-f，**全协议只用小写**（数据区也是小写，全协议只有一套 hex 大小写规则，减少一处两端不一致点）。
4. **空载荷帧也要算**：`#PING` 的校验是 `#`^`P`^`I`^`N`^`G` 五个字节的异或，**不是 0**。

**算例 1**：`#PING`

```
'#'=0x23  'P'=0x50  'I'=0x49  'N'=0x4e  'G'=0x47
0x23 ^ 0x50 = 0x73
0x73 ^ 0x49 = 0x3a
0x3a ^ 0x4e = 0x74
0x74 ^ 0x47 = 0x33        →  线上就是  #PING*33 ⏎
```

**算例 2**：`#PMUL TIME 1`（注意空格 0x20 也要参与）

```
0x23^0x50=0x73 ^0x4d=0x3e ^0x55=0x6b ^0x4c=0x27 ^0x20=0x07
^0x54=0x53 ^0x49=0x1a ^0x4d=0x57 ^0x45=0x12 ^0x20=0x32
^0x31=0x03                                   →  #PMUL TIME 1*03 ⏎
```

**本协议用到的全部校验值（可当对照表逐条复算）：**

| 行（`*` 之前的内容） | 校验 |
|---|---|
| `#PING` | `*33` |
| `#NTT 1` | `*7c` |
| `#INTT 1` | `*35` |
| `#PMUL TIME 1` | `*03` |
| `#PMUL TIME 2` | `*00` |
| `#PMUL NTT 1` | `*58` |
| `#ABORT` | `*69` |
| `#OK PMUL TIME 1` | `*27` |
| `#BEGIN PMUL TIME 1 256` | `*75` |
| `#DONE PMUL TIME 1 256` | `*32` |
| `#OK NTT 1` | `*58` |
| `#BEGIN NTT 1 256` | `*0a` |
| `#DONE NTT 1 256` | `*4d` |
| `#ERR 03 got=3f exp=a2` | `*52` |

两条值得注意的（都不是错误）：

- `#PMUL TIME 2` 的校验是 **`*00`**。**校验值为 0 是完全正常的**，不是「没有校验」——它只是恰好异或成了 0（纯巧合，和这一行的含义无关）。⚠️ **写这类「某条恰好是 0」的说明时，必须先真的把那条算一遍**：本表上一版就是拿一条**算出来不是 0** 的行当例子，整段论证的论据不存在。
- `#PMUL NTT 1` 和 `#OK NTT 1` 算出来**都是 `*58`**。异或本来就不保证「不同内容给不同值」——这正是它强度低于 CRC 的地方，也是为什么**回显才是第二道防线**。

> ⚠️ **这张表出过错，是被脚本抓出来的。** 上一版有 3 个值算错（`#BEGIN PMUL TIME 1 256` 写成 `*00`、实为 `*75`；`#DONE PMUL TIME 1 256` 写成 `*20`、实为 `*32`；`#ERR 03 got=3f exp=a2` 写成 `*66`、实为 `*52`），而且错值被原样抄进了 §5.1 的示例事务和 §5.2 的错误码示例。后果不小：**一端照表硬编码、一端照算法实现，校验闸门必然对不上，还会互相指责对方有 bug。**
> 所以：**冻结前请用一段十行脚本从「`*` 之前的字符串」直接生成这张表**（顺手放进 `skill/scripts/`），并在表头写明「本表由脚本生成」。§5.5 末尾的三种注入错误自测正好能反过来复核它。
> 本版这 14 条已由 B **逐条脚本复算**，与表一致。

**`#OK` 的应答也要带校验**：电脑收到先验校验、再比对回显的参数，两道都过才算 `#OK` 有效。

**为什么数据行不加校验（三条理由）：**

1. **加了会毁掉本方案最大的好处。** 数据行一加 `*xx` 就变成 7 字节/系数，`refsim/batch/*.txt` 的字节流就不再是合法载荷——必须多写一个转换程序。而「能直接把 batch 文件喂进去」正是这个方案存在的理由。
2. **数据行的错误有天然的下游兜底，命令行的没有。** 一个系数传错了，端到端数值对拍会**必然**发现（256 个系数一个不差才算过）。而一条命令被噪声改写，板子可能跑去执行一个完全没预期的运算——**命令错了没有任何下游能兜住**。
3. **错误定位反而是文本方案的强项。** 二进制打包错一位会「整体全错、无法定位」；文本行错一行就只错那一行，`diff` 直接告诉你「第 137 行不同」。

**为什么用异或而不是 CRC16：**

- 命令行只有十几个字节，异或**能用纸笔算**——在没写好任何代码之前，就能在串口助手里手打一条命令、手算校验。CRC16 做不到这一点，而写 CRC16 代码本身就是一个出错点（两端必须位序/初值/多项式严格一致，一旦对不上，现象和「真的传坏了」一模一样，反而更难查）。
- 异或能查出**所有奇数位错误**（单比特翻转是最常见的噪声形态）。查不出的是「同一行里偶数位同时翻转」——但命令行的参数还有第二道防线：板子在 `#OK` 里回显参数，电脑核对。

> ⚠️ 要不要给数据行也加校验、要不要换成 CRC，见 §六 第 6 条。

**坏校验怎么处理**：板子回 `#ERR 03 got=.. exp=..`，**不重传、不猜**。电脑收到后打印原始那一行（十六进制 + ASCII 两种形式），然后处理本事务失败。

### 5.5 超时与错误处理

**总原则：任何等待都必须有上限。** 对应 `CLAUDE.md:104-105` 约定 2「testbench 里不要写无界 `while (done == 0)`」——单次跑没事，套进循环后任何一轮异常都会**永久挂死而不是报错**。这条要求从测试台推广到板子端的接收状态机：**宁可报错退出，不可静默空等。**

**超时数值**（全部可配置）：

| 名字 | 在哪一侧 | 从何时起算 | 建议值 | 到时的动作 |
|---|---|---|---|---|
| `T_LINE` | 板子端 | 收到本行第一个字节起（数据段） | **1 秒** | 丢弃本行，回 `#ERR 05`，回到「找行首」状态 |
| `T_CMD` | 板子端 | 收到**命令行**第一个字节起，**每收到一个字符就重置**（字符间超时，不是整行超时） | **10 秒** | 丢弃这半行，**静默**回到「等命令行」状态——**不回任何行** |
| （等命令行时） | 板子端 | 还没收到第一个字节 | **不设超时** | 一直等。这条要明确写出来，否则两端会各自猜 |
| `T_CORE` | 板子端 | 给了 `start_*` 之后 | **100 毫秒** | 回 `#ERR 06`（运算没在预期时间内完成），不静默 |
| `T_OK` | 电脑端 | 发出命令帧之后 | **1 秒** | 判为「帧没到」：记录日志、走重试流程 |
| `T_BEGIN` | 电脑端 | 数据行发完之后 | **5 秒** | 判为「收到了但没算完 / 没回来」：记录日志、走重试流程 |
| `T_RX` | 电脑端 | 收到 `#BEGIN` 之后，每等一行 | **1 秒** | 同上 |
| `T_DONE` | 电脑端 | 数据行收齐之后 | **1 秒** | 同上 |

**为什么 `T_LINE` 取 1 秒，而不是「一行只需 347 µs 所以取 4 ms」**：
一行确实只要 347 µs，但线上的字节是由 CH340 走 USB 分包送进来的，中间会经过 Windows 的调度抖动。**留 4 ms 太紧，会把正常的抖动误判成超时。** 取 **1 秒**：相对 347 µs 是约 2900 倍余量，既容忍抖动，又远小于「人感觉到卡死」的时间。**关键不是数值的大小，是「必须有一个有限的上限」。**

（**`T_CMD` 为什么不取 1 秒**：本协议把「校验能手算 → 可以在串口助手里手打一条命令」当成选异或而不是 CRC 的主要理由（§5.4）。可人逐字符敲一条 `#PMUL TIME 1*03` 要十几秒，而且**字符之间**必然停顿——按「整行 1 秒」计时，等于把「手打调试」这条路自己堵死。所以 `T_CMD` 改成**字符间超时**、默认 **10 秒**。）

**为什么命令行超时后板子必须「静默丢弃、不回行」**：电脑此刻正在**发**命令，它没有在等任何应答。板子这时主动回一行 `#ERR`，在电脑看来就是一行**归属不明**的行——按关键规则四，处置是「停止整轮测试」。于是一次手抖会把整批测试打断，而超时本来只是一件小事。
同理写死：**电脑在发数据行期间收到非预期 `#ERR`（不是自己正在等的那条），也按归属不明处理 → 停。** 所以板子在收到完整命令行之前，一个字节都不许主动发。

**为什么 `T_OK` / `T_BEGIN` 分开计**：请求帧最长约 179 毫秒；板子算一次是微秒级（pe1 一次 FNTT **18.1 µs** = 905 拍 @50 MHz，`rtl/H1_port_spec.md` §二/§七），回传帧约 90 毫秒。取 1 秒（约 5 倍余量）与 5 秒（含装数据 + 计算 + 回填）。**分开计时才能在日志里区分「帧没送到」和「算不完」两类故障**——这正是 `#OK` / `#BEGIN` 分两行存在的意义。

> ✅ **已定（2026-09-29）：板子端不走 PS 裸机 C**（见 §六 第 1 条），所以 `T_BEGIN` **不需要**为 `AXI-Lite` 往返留余量。实测依据：pe1 一次 FNTT 905 拍 = 18.1 µs；一次完整乘法（FNTT+PWM2+INTT）2458 拍 = 49.2 µs（`rtl/H1_port_spec.md` §二/§七）。**`T_CORE` = 100 ms 与 `T_BEGIN` = 5 s 都绰绰有余 —— 本节所有超时值一律不变。**

#### 关键规则一：超时后板子必须回到「等命令行」状态

这是整个错误处理里最重要的一条。板子如果在数据段中途超时（收了 137 行、还差 119 行），**必须立刻丢弃本事务、清空行缓冲、回到「等命令行」状态**。

理由：如果板子赖在「收数据」状态不走，电脑后续发的命令行的 `#` 会被当成数据行判 `04`，然后电脑再发的数据行又会被当成上一条命令的尾巴——**从此全线错位，而且两边都以为自己是对的**。这是唯一一种会让整条链路**静默失效**的故障，必须在协议里堵死。

#### 关键规则二：电脑侧的重试策略

1. 任一时序超时 → **先发一次 `#ABORT*69`**（双保险：板子可能比电脑晚超时、还赖在数据段里），然后丢弃本事务已收的数据。
   - ⚠️ **`#ABORT` 的应答必须写死，否则规则二会自己撞规则四。** 板子收到 `#ABORT` 后按 §5.2 的通用规则**回显** `#OK ABORT*..`；**电脑必须先把这一行读掉并校验，再发重传**。若不定这条，板子回的 `#OK ABORT` 会撞上电脑正等着的那条命令的 `#OK`——回显对不上 → 触发关键规则四「停止整轮测试」，而规则二的本意恰恰是「一条失败不要中止整批」。
   - 另一种可选设计是「`#ABORT` 静默无应答」。两种**只能选一种**；本草案默认**「回 `#OK ABORT`」**。
2. 整条事务**从头重发**，最多 **3 次**（计数式护栏，不是 `while(true)`）。
3. 3 次仍失败 → 放弃该条，记录「第几组、第几条命令、失败在哪一步」，**继续下一条**（不要因为一条失败中止整批）。

**幂等前提（这条必须写进协议，将来改命令时要一起改）**：上表所有命令都是**覆盖式**的——`#NTT` 就是「把缓冲区填满 256 个系数然后算」，没有累加状态、没有「续传」。所以**重复执行 1 次和 3 次结果完全相同，重发是安全的**。将来谁想加「部分加载」之类的增量命令，就得同时重新设计重发规则。

#### 关键规则三：收到 `#ERR` 不重发

板子能回错误码，说明**它活着、链路通、它理解了你的命令**——重发同一条命令只会得到同一个错误。此时**打印错误码和它带的参数（第几个字符越界、收到几行），然后处理本事务失败**。错误码带参数就是为这个。

#### 关键规则四：回显对不上就立刻停

电脑收到一行后，先看第一个词是不是 `#OK` / `#BEGIN` / `#DONE` / `#ERR`；是前三种时，还必须核对**回显的命令和参数是不是自己刚发的那条**。对不上 → 判定「错位」，打印这一行原文然后**停止整轮测试**。不做任何猜测性跳过——错位意味着「后面收到的所有字节都归属不明」。

> **唯一的例外：`#OK ABORT`。** 它是对「电脑刚发出去的 `#ABORT`」的应答，本来就**不对应任何正在进行的运算**。所以电脑的重试流程里必须专门有一条「读掉 `#OK ABORT`」，不能拿它去比对「当前事务的回显」。除此之外没有任何例外——不定这一条，关键规则二（超时后发 `#ABORT` 再重发）与本节会**在执行层面互斥**。

#### 关键规则五：不做静默恢复

任何一次重试都必须在日志里留一行（「第 N 条命令超时，重发」）。B 的红线是「通过必须能被别人复算」（`team/FPGA竞赛_B_引导与计划.md:226`），一次静默重试会把「链路不稳」这个事实藏掉。

#### 边界情况怎么判

| 情况 | 处理 |
|---|---|
| 空行（只有 LF） | 忽略，不计入行数。这样传送末尾多一个 LF 不会致命 |
| 收到 `\r`（回车） | 忽略这个字节。容错用，但**协议要求电脑端不发**（LF 行尾铁律） |
| 数据行出现 `#` 开头 | 判 `#ERR 04`（数据段内不允许有命令，`#ABORT` 除外） |
| 处在「等命令行」状态，一行超过 64 字节还没等到 LF | 判 `#ERR 04`，丢弃该行 |
| 处在「数据段」状态，一行超过 4 字节还没等到 LF | 判 `#ERR 04`，丢弃该行（数据行必须恰好 3 字符 + LF） |
| 行内出现非十六进制字符 | 判 `#ERR 04` |

> ⚠️ **长度怎么数，必须写死**：`\r` 在**计数之前就被丢掉**——即 `044\r\n` 算 **3 字节**（合规），不是 4 字节（越界）。不定这条，电脑端或串口助手不小心发了 CRLF，就会被误判成 `#ERR 04`，「忽略 CR」的容错意图正好落空。命令行那条「64 字节」同理。

#### 明确不做的事（写出来，免得两边各自猜）

- **不做自动重传**（板子不主动重发、电脑不逐行 ACK）——事务级重试已经够用。
- **不做滑动窗口 / 序列号**——本协议一次最多几百行，没有回绕风险。
- **不做流控**（板子不喊「慢点」）——见 §六 第 2 条（n 的上限与板内驻留容量）。
- **不做奇偶校验位**——8N1 的 N 就是「无校验」，与 `19_uart_loopback` 一致，不改。逐行校验由行格式 + 命令行异或承担。

#### 降级路径（计划已定，文档照写）

上位机做不完时，可以用仿真波形截图代替串口实测；**但验证数据本身不能省**——它是「功能正确性 20 分」的载体（`team/FPGA竞赛_B_引导与计划.md:219-220`）。所以本协议的**可交付下限**是「协议冻结 + 假串口在仿真里跑通」，真板联调是加分项而非前提。

#### 冻结前的验收方式（三条注入错误的自测）

在 `refsim/` 里造一个假串口对端，故意做三件事：

1. **发半行就停** → 板子侧应在 `T_LINE` 后回 `#ERR 05`，而不是卡死；
2. **发错一个字符** → 应回 `#ERR 04`（或 `#ERR 03`）并报出位置；
3. **收到命令后故意不回** → 电脑侧应在 `T_OK` 超时、发 `#ABORT`、重发一次、再超时后**干净退出而不是卡死**。

这三条跑通，才算协议冻结有了依据。

### 第 1 条（最关键，其余都受它影响）板子那一端由谁实现、用什么写？

- **议题**：串口协议的对端解析器，是纯 PL 里的 Verilog 状态机，还是 PS 上的裸机 C 程序？
- **选项甲**：纯 PL 的 Verilog 状态机（照官方 `19_uart_loopback` 的路子）。
- **选项乙**：PS 裸机 C 接收，再经 `AXI-Lite` 访问 PL 里的 NTT 核。
- **各自代价**：
  - 甲：要在 Verilog 里手写行缓冲、十六进制解析、异或累加器——本协议是**行协议**，纯 PL 实现的工作量明显大于二进制定长帧；好处是链路最短、无 AXI 往返延迟。
  - 乙：字符串切分 + 十六进制转换在 C 里是几行代码，本协议几乎免费；但要多一层 `AXI-Lite` 寄存器组，且 `T_BEGIN` 的延迟量级会变大。

- ✅ **已定（2026-09-29）：甲 —— 纯 PL 的 Verilog 状态机。** A 拍的板，依据 `选题指南.pdf` §3.3.1.1：初级组的考察侧重就是**逻辑设计 / 状态机 / 时序约束 / 接口协议**，而「软硬协同」是**高级组**的加码项，不在本队考察面上。

### 第 2 条 一次事务传几组（命令里 `<n>` 的上限）

- **议题**：`#NTT <n>` 的 n 能取 1…16，还是只能取 1？
- **选项甲**：n 只能取 1。电脑端把 `ntt_batch_in.txt`（4096 行）按每 256 行切一片，发 16 条命令。
- **选项乙**：n 最大 16。一次把 4096 行全灌进去。
- **各自代价**：
  - 甲：板子端一次只需驻留 256 个系数（`PMUL` 是 512 个），缓冲压力最小；代价是事务数 ×16，总时间多出 16 组控制行开销（约 16 × 7.5 ms = 120 ms，可忽略）。
  - 乙：省事、日志少；但板子端要能同时驻留 16 组数据，且一旦中途出错整批重来。
- **建议**：**先按 n = 1 冻结**。理由：现有核的 BRAM 是 A、B 各占一份（`load_*_f` 灌低半区、`load_*_i` 灌高半区，见 `refsim/README.md:218-238`），16 组同时驻留的容量上限只有 A 知道。n > 1 作为后续可选扩展，不影响 n = 1 时的任何帧格式。
- ✅ **已定（2026-09-29）：甲 —— n 只能取 1。** 电脑端把 4096 行按每 256 行切一片，发 16 条命令。`n > 1` 记为**可选扩展**：加它不影响 `n = 1` 时的任何帧格式，故**不挡本次冻结**（见 §九(c)）。

### 第 3 条 板子侧的缓冲是「整帧缓冲」还是「边收边灌」

- **议题**：板子收到数据行后，是先存够一整组再灌进核，还是逐行直接灌进核的装载口？
- **选项甲**：**边收边灌**——每收到一行就转成 12 位数、写进核的装载端口。
- **选项乙**：**先缓冲一整组**（256 或 512 个 12 位数，约 384 / 768 字节），收齐后再一次性装载。
- **各自代价**：
  - 甲：几乎不占额外缓冲（只需 3 字符行缓冲 + 一个计数器）；代价是格式校验必须在「灌进去之前」完成，且中途出错无法回退。
  - 乙：校验完再灌，出错干净；代价是要一块多项式缓冲 RAM（256 × 12 位 ≈ 384 B；`PMUL` 要 A、B 两块 ≈ 768 B）。
- ✅ **已定（2026-09-29）：乙（先缓冲一整组）。甲不是"不划算"，是"根本做不到"。** 依据 `rtl/H1_port_spec.md` §四 的实测：核的 `load_*` 口**没有「数据有效」选通信号** —— 只要 FSM 进了 `OP_LOAD_DATA` 就每拍硬写一次 BRAM，靠内部计数器数满才退出。**不能逐拍断续给、不能灌到一半停**（灌一半会永远卡在装载态，后续 `start_*` 不响应）。
- **量级对比（H1 §四）**：核灌满一个多项式 **256 拍 = 5.12 µs**；串口送一个多项式 **4,444,444 拍 = 88.9 ms**。相差 **17,361 倍**（若比"算一次 FNTT"则差 4,911 倍）。所以数据流只能是 `UART → [行缓冲 + 十六进制解析] → [多项式缓冲 BRAM] → 核的 din`：**先收满整组，再花 256 拍 burst 进核**。

### 第 4 条 结果回传顺序：原样回传带标志，还是板子侧重排

- **议题**：FNTT / PWM2 的物理读出是交织序（`0,2,1,3,...`），INTT 是**另一种**序（`0,128,1,129,...`，见 §5.3.4）。回给电脑时按哪个序？
- **选项甲**：**原样回传**，用 `#BEGIN` 里附带一个序型标志（`i` = 交织 / `n` = 自然），电脑端按运算类型解包。
- **选项乙**：**板子先重排成自然序**再回传，电脑端三种运算共用一个解包器。
- **各自代价**：
  - 甲：A 少一级地址映射逻辑（少一个 bug 源）；代价是电脑端要按运算类型分三种解包顺序，容易写错。
  - 乙：电脑端简单统一；代价是 A 要多写一级重排，且重排本身要按运算类型分支。
- **建议**：**甲**。理由：电脑端的解包顺序写错会**响亮地失败**（256 个系数全错），是可见的失败；而板子侧多一段 RTL 分支是可见的复杂度。这条按「哪边更容易发现错误」来选。
- ✅ **前提已核对（2026-09-29）**：A 已在 `rtl/H1_port_spec.md` §三 给出「第 m 拍对应哪个系数下标」的 iverilog 实测表，即 §5.3.4 那张。核对结果：**FNTT / PWM2 与本草案一致；INTT 不一致** —— 本草案原写「自然序 `0,1,2,3,...`」，实测是 `0,128,1,129,...`，已改正。⚠️ **纠错记录**：错源是 `refsim/README.md:206-216` 那张表（本草案原样搬用），而 `refsim/pe1/intt_batch_tb.v:112-115` 的**代码才是对的**（`fout[m]=dout; fout[m+128]=dout;`，跑过 4096/4096）——是表和注释写错了，不是 RTL 错。三处（本草案、`refsim/README.md`、`intt_batch_tb.v` 的注释）已同步修正。A 同时确认核**没有** `AXI-Lite` 包装层（第 1 条已定：纯 PL）。
- ✅ **已定（2026-09-29）：甲 —— 原样回传，且不加序型标志。** 电脑端按**自己发出的命令**判断该用哪张表（`#NTT` → FNTT 序 / `#INTT` → INTT 序 / `#PMUL NTT <n>` → PWM2 序），因此 §5.2 的 `#BEGIN <原命令> <count>` **格式不动、不加字段**。选甲的理由见 §5.3.4。

### 第 5 条 数据编码档位 + 统一仓库里那两处打架的估算

- **议题**：每个系数在线上占几个字节？仓库里现有两处估算口径不一致，也必须一起定一个。
- **选项甲**：**文本，3 位小写十六进制 + LF = 4 字节/系数**（本草案默认）。整批 16 组 PMUL = 49152 B ≈ **4.267 s**。
- **选项乙**：二进制。2 字节/系数 → 24576 B ≈ **2.133 s**；或两个 12 位打包进 3 字节（1.5 字节/系数）→ 18432 B ≈ **1.600 s**。
- **各自代价**：
  - 甲：慢 2.1~2.7 秒；换来的是**电脑端和仿真端都不需要写任何编解码**（把 `refsim/batch/*.txt` 按 256 行切片直接写串口 / 直接喂 UART 接收端）、串口助手里逐字可读、坏字节大概率变成非法字符被格式检查当场抓住、校验能手算。
  - 乙：快；但两端都要写位拼接 / 解包（打包 1.5 字节时，电脑端反向拆、板子端按字节节拍攒够 24 位再拆两个 12 位），这是零基础队伍最容易写出「**错位一位、整体全错**」的地方，且线上字节不再是人能肉眼检查的。
- ✅ **已定（2026-09-29）：甲（文本，3 位小写十六进制 + LF）** —— A 对采哪种编码**没有意见**，理由是「文本的『一行错只错一行、`diff` 能定位』在调试期值这个钱」（`rtl/H1_port_spec.md` §七）。参考量级：板子算一次 FNTT 是 **18.1 µs**，链路本来就慢 3~4 个数量级——**再省这 2 秒没有意义**。二进制留作 W4 之后的加速档。
- ✅ **那两处"口径矛盾"已查清（2026-09-29）**：它们**不是矛盾，是同一个公式（字节数 × 10 ÷ 115200）的不同档位**，数字都对 —— 512 B（2 B/系数）→ 44.4 ms；384 B（1.5 B/系数）→ 33.3 ms；本草案 1024 B（4 B/系数）→ **88.9 ms**。三档实测基准见 `rtl/H1_port_spec.md` §七。**报告里统一写「本草案 = 3 位十六进制 = 4 字节/系数 = 88.9 ms/多项式」**；引用另两档时必须写明是哪个档位，否则两个数看上去像打架。
- **附带的第二问**（变长文件怎么办）：实测仓库里共有 **23 个**变长文件——`fullmul_exp.txt` / `halfmul_exp.txt` / `halfmul_b.txt`、**全部 16 个 `vref_*.txt`**，以及 `_full_ref.txt` / `_half_ref.txt` / `_gen_scratch_ntt.txt` / `_gen_scratch_out.txt`。处理办法：(a) 对拍**按数值比**，不按文本逐字节比；(b) 或在冻结前把其中**有实际用途的 19 个**（`fullmul_exp` / `halfmul_exp` / `halfmul_b` + 16 个 `vref_*`）用 `%03x` 重新生成一遍，让全仓库只剩一种写法。详见 §4.2 与 §5.3.5。

### 第 6 条 校验：数据行要不要也加？要不要换成 CRC？

- **议题**：本草案规定命令行加异或校验、数据行不加。两个可选项。
- **选项甲**：（本草案默认）命令行异或，数据行不加。
- **选项乙**：(a) 数据行也加校验；(b) 或整体改用 CRC-16。
- **各自代价**：
  - 甲：保住「直接把 `refsim/batch/*.txt` 喂进去」这条最大的复用性（见 §5.4）。数据行的错误由端到端数值对拍兜底。
  - 乙(a)：数据行变 7 字节/系数，**必须多写一个转换程序**，复用性归零；换来逐行可检出。
  - 乙(b)：更能扛错；但要先写好代码才能调试，且两端位序 / 初值 / 多项式必须严格一致——**一旦对不上，现象和「真的传坏了」一模一样**，反而更难查。
- **建议**：**甲**。理由是「命令错了没有任何下游能兜住，数据错了有端到端对拍兜底」这条不对称。
- ✅ **已定（2026-09-29）：甲 —— 命令行异或校验，数据行不加。** 数据行的错误由端到端数值对拍兜底。「数据行加校验」与「改用 CRC-16」记为**可选扩展**：两者都会改掉数据行长度，属**破坏性变更**，冻结后要按 §九(b) 双方同意才能上。

### 第 7 条 超时数值，特别是 `T_BEGIN`

- **议题**：§5.5 那张表里的数值（板侧 `T_LINE` 1 秒、板内看门狗 `T_CORE` 100 毫秒、电脑侧 `T_OK` 1 秒 / `T_BEGIN` 5 秒）。
- **选项甲**：照本草案默认值。
- **选项乙**：由 A 按实际实现路径（纯 PL 还是 PS 裸机 C）给量级。
- **各自代价**：`T_LINE` 和 `T_CORE` 要在板子端照着实现；`T_BEGIN` 在 PS 路径下明显需要更大。
- **建议**：`T_LINE` 与 `T_CORE` 按上表；**`T_BEGIN` 请 A 按实际路径给一个量级**，或干脆做成电脑侧可配置参数（推荐后者）。
- ✅ **已定（2026-09-29）：照本草案默认值冻**（板侧 `T_LINE` 1 s / 板内看门狗 `T_CORE` 100 ms / 电脑侧 `T_OK` 1 s / `T_BEGIN` 5 s）。理由：第 1 条已定为**纯 PL 状态机**，原担忧的「PS 路径下 `T_BEGIN` 需更大」随之消失（§5.5 该节的 ✅ 注已写明所有超时值不变）。另把 `T_BEGIN` 做成**电脑端可配置参数**（默认 5 s），成本几乎为零。

### 第 8 条 要不要加「上电主动发一行 `#RDY`」

- **议题**：板子上电后主动发一行 `#RDY <ver> <build> <errs>`，让电脑自动识别 COM10 后面是不是我们的板子。
- **选项甲**：加。
- **选项乙**：不加，靠电脑发 `#PING` 试探。
- **各自代价**：
  - 甲：电脑端不用盲探，且能一眼看出两端跑的是不是同一版固件、板子累计丢过多少帧。
  - 乙：板子端少处理一段「上电时序」。注意 `sys_rst_n`（N16）是**低有效**，与上游 RTL 的 `reset` 异步**高**有效相反，上电瞬间的自发行为要确认不会干扰电脑正在做的其它事。
- **建议**：**加**，但**放在冻结之后补也可以**——它是纯增量，不影响任何已有帧。`<build>` 用一个 A 在 RTL 里放的 32 位常量（例如综合日期或手写编号）。
- ✅ **已定（2026-09-29）：甲（加 `#RDY`），但标为「冻结后补」。** 纯增量、不碰任何已有帧，**不挡本次冻结**（列在 §九(c) 的故意推迟清单里）。

### 第 9 条 `#PMUL` 要不要拆成「装 A / 装 B / 开始」三步？

- **议题**：现在是一条 `#PMUL TIME <n>` 后面跟 2n×256 行数据，一次装完。
- **选项甲**：一步装完（本草案默认）。
- **选项乙**：拆成 `#LDA`（装 A）+ `#LDB`（装 B）+ `#GO`（开始）三条命令。
- **各自代价**：
  - 甲：少两次往返、电脑端代码更短。
  - 乙：能和 A 现有端口一一对应（`load_a_*` / `load_b_*` / `start_pwm2`），且出错时能区分「装载错」还是「计算错」。
- **建议**：**甲**（三个时间戳 `#OK` / `#BEGIN` / `#DONE` 已经能区分「帧没送到」与「算不完」）。若 A 认为拆开更好实现，改成乙也不影响其余部分。
- ✅ **已定（2026-09-29）：甲 —— 一步装完，不拆。** 若 A 实现时认为拆开更顺手，改乙**不影响其余部分** —— 但那会增删命令字，属**破坏性变更**，冻结后按 §九(b) 双方同意再改。

### 第 11 条 复用 `19_uart_loopback` 的哪些部分、H1 端口说明

- **议题**：官方例程里现成的 UART 收发模块（含 50 MHz 时钟下的分频参数）是直接复用还是自己重写？例程顶层端口名与本协议假设的 `clk` / `rst` / `uart_rx` / `uart_tx` 是否一致？

- ✅ **H1 端口说明已于 2026-09-29 交付**（`rtl/H1_port_spec.md` §六）。结论三条：`rtl/uart_rx.v` / `rtl/uart_tx.v` **原样复用**（`CLK_FREQ=50000000` / `UART_BPS=115200` 正是本板的值）；顶层 `rtl/uart_loopback.v` **不复用**（它只是把 `uart_rx_done` 直连 `uart_tx_en`，那一层要换成协议状态机）；引脚照抄例程 XDC（`sys_clk`=U18 / `sys_rst_n`=N16 / `uart_rxd`=T19 / `uart_txd`=J15，均 LVCMOS33）。
