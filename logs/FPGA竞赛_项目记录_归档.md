## 三、选题调查：核心认知（2026-09 中旬）

### "有深度的作品 ≠ 做了 CPU"

深度的 4 个真实来源（均不需要 CPU）：
1. **算法/架构加速**：算法软件跑 → 硬件流水线跑，给出加速比
2. **接口/协议工程**：UART/以太网/PCIe/JESD204B 等
3. **系统完整度/软硬协同**：多个子系统拼成解决真实问题的闭环
4. **信号处理链路**：FFT/锁相放大/滤波，把精度做到极致

CPU 的真实作用：作为**学习脚手架**（练状态机/数据通路/总线）和作为 **RISC-V SoC**（CPU+外设+能跑真实程序，2026 趋势点名的主流方向）。**裸单周期 CPU ≈ 课程设计，不深。**

### 候选方向对比（零基础 + AI + 2 个月视角）

| 方向 | 所需基础 | 硬件风险 | AI杠杆 | 天花板 | 2个月可完成 | 7020适配 |
|---|---|---|---|---|---|---|
| 软核CPU/SoC | ●● | ○ | ●●● | 中高(做成系统才高) | 中 | 优 |
| 算法加速器(FFT/卷积/FIR) | ●● | ○ | ●●● | 高(近年最热) | 中 | 优 |
| 图像/视频处理 | ●●● | ●● | ●● | 高(获奖大户) | 低 | 中(需摄像头/HDMI) |
| 信号/仪表(DDS/频率计) | ●● | ●● | ●● | 中 | 中 | 中(需DA/AD) |
| 高速接口/通信 | ●●●● | ●●● | ●● | 高(卷) | 低 | 需子卡 |

> 关键：对"零基础+2个月+AI"而言，**真正卡死人的维度是"硬件风险"和"AI杠杆"，不是天花板**。

### 近年（2025–2026）整体趋势

- 三大主线：**端侧 AI / 国产化 / 边缘化**；多模态感知融合成获奖主流特征
- AI 硬件加速、RISC-V SoC 软硬协同、工业缺陷检测为热方向
- 评委审美：**工程完整度 + 资源利用率 + 实测对比数据** > 技术名词堆砌
- 通用经验（拿奖本质）：选对题 → 做完整（能上板、能复现、有数据对比）→ 讲清楚

### AI-agent 的边界（决定选题方向）

- **AI 能帮**：生成/改 Verilog、写 testbench/仿真、修逻辑 bug、解释代码、写报告、整理对比数据
- **AI 帮不了**：上板那一步（引脚约束/时序违例/板子不亮）、实物演示、现场答辩的理解复述
- → 选题口诀：**"代码密集度高、硬件耦合度低"** —— 把难度放在 AI 擅长的代码里，避开 AI 帮不了的模拟电路/高速接口/摄像头时序

## 四、选题专项调研：算法硬件加速方向（2026-09-09 全过程）

### 调研背景与用户两次筛选指令

1. 用户问"什么算法适合放 FPGA 优化、研究少/较新" → 第一轮给出学术前沿清单 + 3 个小而新候选（储层计算ESN / 超维计算HDC / KAN）。
2. 用户加要求："**加速效果要明显、要有对比对象**（市面 CPU 跑、FPGA 加速后效果好），再找一轮多推荐" → 第二轮给出基因比对SW / MonteCarlo / SIFT-ORB / 压缩感知 / 点云DBSCAN / 端侧小LLM / 3DGS 等"对比震撼"候选。
3. 用户纠正：**没考虑实际板卡** → 确认平台后重筛；用户拍板：**新算法优先、接受难实现**（"先别考虑队员能力欠缺"）。

### 平台确认后的重筛结论（硬约束枪毙了大量"新"题）

- **XC7Z020（7020）**：BRAM ≈ **4.9Mb ≈ 0.6MB**（最卡约束）、220 DSP、53,200 LUT。
- 因 7020 + 摄像头/HDMI 可用 → **实时视觉方向重新成立**（原判"无摄像头"被推翻）。
- **被枪毙**：大图GNN / 端侧LLM / 3DGS渲染（需 U200/HBM 级）；小 ViT/MobileViT（7020 实测端到端仅 **~1.4×**，演示不震撼）。
- **关键认知**：7020 上"最新算法"与"夸张加速比"常冲突——加速比上 43× 的多为经典并行算法；真·新范式在 7020 往往只有 1.4× 或装不下。落点 = **经典内核 + 新应用/新系统 + 实测数据**，或"搬新范式上 7020 当第一个、自己测数字"。
- CPU 基准定在 **PC 上位机**（跑同算法 C/Python 计时对比）→ 保住 PL-only。

> ⚠️ **2026-09-09 二次修正（重要）**：上述三选一**全部依赖摄像头/HDMI、方向全为图像视觉**，被队长打回——"算法硬件加速不一定非用摄像头"。已重筛 **无摄像头、纯 PC↔FPGA（串口/USB）数据载体** 的非视觉候选 A/B/C/D（PQC-NTT / ESN储层 / SNN生物信号 / HDC非视觉）→ 详见《FPGA竞赛_选题细化_算法加速_非视觉方向.md》。三选一稿保留作被打回记录。

### 最终三选一候选（已被打回，仅存档）

| | 候选 | 加速证据 | 新算法度 | 备注 |
|---|---|---|---|---|
| ① | **实时视频去雾/增强**(DCP/CLAHE) | PYNQ-Z2(≈7020)实测 **43× / 12FPS@0.79W**；1080p CLAHE 30FPS | 内核老、落地热 | 最稳保底 |
| ② | **超维计算HDC 视觉分类** | 7020 无数据要自测；ZCU104 上 40× | **高(2024-25新范式)** | 要新算法+敢自测选它 |
| ③ | **ORB 特征提取/稳像/拼接** | PYNQ-Z2 48FPS vs CPU 15FPS | 中 | 居中、工作量偏大 |

## 五、2026-09-18 · 板卡可行性与选型（完整过程）

板卡锁定**领航者 ZYNQ-7020** → 调研四候选在该板上的可行性，落盘《**FPGA竞赛_可行性分析_非视觉候选_领航者7020.md**》。

本轮**推翻了三处旧判断**：
1. "四候选 7020 适配均极好" → 真瓶颈是 DSP/BRAM，不是 LUT
2. SNN"逻辑简单" → 见过打满 220 DSP 的实测
3. "上板 UART 是 AI 帮不了的点" → 官方已有纯 PL 串口例程

**新发现最重要的一条**：**串口带宽比计算核慢 3–4 个数量级**，是四个候选共同的天花板，
必须用"片上激励源 + 正确性另走一路"的架构绕开。选型推荐 **B(ESN)**。

### 🎯 选题锁定（同日，推翻了上一条的推荐）

读完官网《选题指南.pdf》（2026 AMD）全文 25 页，**推翻两处旧判断**：

1. **赛道结构变了** —— 旧记录里的"基础能力/综合能力赛道"是 2025 年的。2026 AMD 赛道为 **3.1 RTL/HLS 本地智能体设计 / 3.2 具身智能 / 3.3 自主选题（初/高级组）**。**"算法硬件加速"不再是独立赛道**，A/B/C/D 四候选的落点是 **3.3 自主选题**，小组按学历归组（全队大一~大三 → **初级组**，器件范围含 Zynq-7000，7020 可用）。
2. **AI-agent 打法是官方计分项** —— 3.3 评测权重：创新性 30 / 性能与资源 20 / 功能正确性 20 / **大模型协作与技能包 15** / 文档与可复现 15。**技能包（skill/ 目录）+ 设计报告里的"大模型协作记录"是白送的分，但必须从第一天开始留痕。** 另：代码**必须开源**（GitHub/Gitee，推荐 MIT/Apache-2.0），目录名必须纯英文。

**最终锁定**：3.3 自主选题（初级组）· 面向后量子密码 ML-KEM 的 FPGA 硬件加速器（NTT/INTT + 模乘核）· PL 算核 + PS 轻量协同。即选 **A(PQC-NTT)**，但按"砍到能交货"重划 scope（只做 NTT/INTT 核 + 模乘 + KAT 对拍 + 折叠度扫描；不做完整 KEM）。

**改选 A 而非原推荐 B(ESN) 的理由**：可行性分析写推荐时缺了"评分权重"这一维。补上后 ——
创新性占 30 分，而**串口带宽比计算核慢 3~4 个数量级意味着"快多少倍"的叙事天生站不住**，
必须换成不靠倍率的故事；**A 恰好有"常量时间实现天然抗侧信道"这张牌**，比倍率硬得多。
且 A 是四者中唯一有**官方 KAT 权威判据**的（20 分"功能正确性"给的是硬证据）。

**EIS（视觉防抖）复核为否决**，理由澄清：不是"因为它是视觉"，而是 ① 无权威正确性判据
② 板级工作量（摄像头 I2C/DVP-MIPI、DDR/VDMA、HDMI 时序）正是 AI 帮不了的部分
③ 厂商例程缺失。**它输在"功能正确性"和"AI 杠杆"，不输在"视觉"。**

⚠️ **本轮最重要的产出是一条负面结论**：调研中试图凭记忆重建 NTT 的 twiddle 层序**反复失败**
（正向 NTT 的同态性都对不上）→ **只有逐行抄 `ref/ntt.c` 才对**。这条已写进踩坑清单。
✅ **当日晚些时候已攻破**（见第七节）：所谓"`zetas_inv` 层序"是个**伪问题**。
教训：**先确认要找的东西存在，再花力气复现它。**

## 七、2026-09-18 第三轮详情：硬件验证 + 层序难题攻破

### 🎯 攻破了挂了很久的"W1 最高优先级"难题

**根因是问题问错了。** 之前反复"凭记忆重建 `invntt` 的 twiddle 层序"都失败，
是因为一直在找一张**根本不存在的表**。

`zetas_inv` 这个词在整个 `kyber_ref/` 里**只出现在 `ntt.c` 开头的一句注释**中；
可执行代码里 `zetas[]` 只被引用两次：

```c
ntt()    : k = 1;   zeta = zetas[k++];   // 正向，一路加
invntt() : k = 127; zeta = zetas[k--];   // 逆向，一路减
```

**同一张表、方向相反，仅此而已。**

- 落盘 **`refsim/ntt_layers.c`** + `run_ntt_layers.sh`：从 `ref/ntt.c` 原样导出 7+7 层层序表，
  按表重新实现 `ntt`/`invntt`，与参考实现裸函数对拍 **200 组随机输入 → 逐比特完全一致**。
- 层序表有个可利用的对称性：**正向第 i 层的下标区间 == 逆向第 (7−i) 层的区间，方向相反。**
- 顺带查清一个对拍陷阱：**`poly_ntt()` = 裸 `ntt()` + `poly_reduce()`**，两者输出不相等。
  RTL 作者的期望输出对应带约减那一支。

### 🎯 已有开源 RTL 的 NTT —— 已确认符合 FIPS 203

不是"作者 testbench 打印 Correct 所以大概没大错"。完整链条在 `refsim/`，一条命令可复跑
(`sh run_fntt_check.sh`)：

```
FIPS 203 KAT 1000 条 → 锚定 C 参考实现为地面真值
参考实现复算作者的输入 → 与作者期望输出逐比特一致（512/512 系数）
我方 16 组独立向量灌 RTL → 全过（4096/4096 系数）
```

**为什么中间那环不能省**：作者 testbench 是「作者的期望值 vs 作者的 RTL」，只能证自洽 ——
万一作者 twiddle 表排错，它照样打印 `Correct!`。先用 KAT 把参考实现锚成**外部**真值，
链条才对外部标准闭合。

**"通过"必须配"非退化"才作数**：4096 个输入系数里 2355 个不同值、覆盖 0..3327 全域。
这种熵下全中不可能是巧合。**这条以后验任何硬件都要先做。**

**意义**：`acmert/kyber-polmul-hw` 的 `pe1/` **可以直接当基线对照**，不必从零写 NTT
再自己验自己。我们有了一套可复用的软硬件一致性测试台。

### ⚠️ 本轮修正的两处旧信息

1. **"本机没有 Verilog 仿真器"是过时的** —— 已装 **iverilog 12.0**（`/c/iverilog/bin`，
   `winget install --id Icarus.Verilog`）。注意 Bash 里 PATH 不带它，每次要 export。
2. **KAT 条数**：曾写的 70 条是中途状态，最终是 **1000 条全部通过**。

### 还没验的（明确边界）

- **只验了正变换 FNTT**。INTT 和 PWM2（点乘）向量已备好但没灌进 RTL；INTT 方向更难
  （GS + 末级缩放），值得补。
- 只验了 `PE_NUMBER=1`；多 PE 并行配置没验。
- 这是**功能验证**，不涉及面积/时序/功耗（等 Vivado 综合）。

`research/mlkem_kat/kat_MLKEM_768.rsp`，**1000 条**、12,012,890 字节，四项独立复算 **1000/1000 逐比特通过**。

## 十、分工演变的完整过程（v1→v4）

**评分表里 30 分是"过程分"**（大模型协作 15 + 文档与可复现 15），加上我们已有硬证据的
"功能正确性 20 分"，**共 50 分不需要天才想法，只需要从第一天老实记录**。所以三条铁律：

1. **不能三个人全扑在"把东西做出来"上** —— 必须固定有人守过程分
2. **上板必须最早开始** —— 那是 AI 最帮不上、最可能卡住的一步
3. **降级先砍功能深度，后砍文档** —— 功能砍了丢单项分，文档烂了丢 30 分

| 版本 | 变化 | 触发原因 |
|---|---|---|
| v1 | A RTL ｜ B 验证+上位机 ｜ **C 系统集成+上板** | 初稿 |
| v2 | 上板从 C 划给 B | 上板是高方差技术活，C 技术最弱 |
| v3 | 上板从 B 划给 A；「工位」概念确立 | **板子实际在 A 手里** —— 工位只能有一个主责人 |
| v4 | Vivado 从 C 划给 A；C 换做演示/文档/相关工作表 | **Vivado 是完整开发工具链（综合/实现/bitstream/下载），不是板子驱动** —— 装在 C 的机器上对 A 毫无用处 |

⚠️ **v4 的关键结论**：bitstream 由 Vivado 生成、也由 Vivado 下载，而板子只有一块、
只能插在一台机器上 → **「装了 Vivado 的机器 + 板子」是一个物理工位，只能有一个主责人**。
上板失败的原因（时序不收敛 / 资源超了 / 数据不对）都要退回去改 RTL，
工位与 RTL 归同一个人，返工不用跨人描述。

⚠️ **已识别的单点风险**：工位与 RTL 都在 A 身上。唯一缓解手段写成了纪律 ——
**仿真能抓到的问题不要留到板上去抓**（板级一轮十几分钟起，且"串口没数据"
可能是引脚 / 时序 / 协议 / 上位机四个原因之一，混在一起极难定位）。

✅ **A、B、C 现在都能开工**：iverilog 已装、验证台已跑通，A 的 RTL 与 B 的
验证台+上位机都不用等 Vivado；C 的三项主战场（演示页 / 相关工作表 / 日志）
完全不依赖 A、B。
