============================================================
二、★ 咬出的缺陷：跑完之后工作区变脏（CRLF）
============================================================

■ 现象

`check_reproducible.sh` 跑完，最后一段打印：

    ⚠️ 跑完之后工作区有未跟踪文件（脚本没清理干净）：
         M refsim/batch/ntt_batch_exp.txt
         M refsim/batch/ntt_batch_in.txt

（严格说它们是**已跟踪文件被改**，不是「未跟踪」——顺手提一句脚本那句措辞。）
注意：**这只是个 warning，不影响退出码**。所以"全绿"照样成立，
但**评委跑一遍会看到这两行"脏"**，观感不好；而且这意味着**四条脚本不是一个
"只读"的验证链** —— 它回写了入库文件。

■ 根因（我定到了行）

    refsim/run_intt_pwm2_check.sh:71-72
        cp "$KAT/ntt_in.hex"  batch/ntt_batch_in.txt
        cp "$KAT/ntt_out.hex" batch/ntt_batch_exp.txt

`$KAT = ../research/mlkem_kat`。而**这两个 KAT 原件本身是 CRLF**：

    research/mlkem_kat/ntt_in.hex   →  4096 行 / 4096 个 CR
    research/mlkem_kat/ntt_out.hex  →  4096 行 / 4096 个 CR

`cp` 原样拷字节 → 入库的 `batch/ntt_batch_*.txt`（**LF**）被覆盖成 **CRLF** → 脏。

■ 为什么值得报（不只是"两行黄字"）

**同一个文件，两个脚本写法不一致**：

  · `run_fntt_check.sh:68-70` 用 **python `"wb"` + `"\n"`** 写 `ntt_batch_in/exp.txt` → **LF**（对）
  · `run_intt_pwm2_check.sh:71-72` 用 **`cp`** 写同两个文件 → **CRLF**（带进了源的 CR）

所以**最终行尾取决于你最后跑的是哪一条**。`check_reproducible.sh` 里四条按顺序跑，
`run_intt_pwm2_check.sh` 在后 → 收尾就是 CRLF。这正是 `CLAUDE.md` 约定 1 描述的那个坑
（"数值全对、diff 报全不同"）——只不过这次不是 checkout 转换，是**脚本自己 `cp` 进去的**。

■ 建议修法（一行，你定）

把 `cp` 换成剥 CR 的等价拷贝，保持 LF：

    tr -d '\r' < "$KAT/ntt_in.hex"  > batch/ntt_batch_in.txt
    tr -d '\r' < "$KAT/ntt_out.hex" > batch/ntt_batch_exp.txt

或干脆复用 `run_fntt_check.sh` 那段 python `"wb"` 写法，两个脚本各写一个函数收敛掉。

■ 我怎么确认的（可复跑）

    # ① 源是 CRLF：
    tr -dc '\r' < research/mlkem_kat/ntt_in.hex | wc -c      # → 4096
    # ② 单跑 run_fntt_check.sh（python 写）→ CR=0、工作区干净
    # ③ 再跑 run_intt_pwm2_check.sh（cp）→ CR=4096、git status 出现 M 两项
    # ④ 还原：git checkout -- refsim/batch/ntt_batch_in.txt refsim/batch/ntt_batch_exp.txt

我本地已用 ④ 还原，仓库工作区是干净的，**没有把 CRLF 提交进去**。
