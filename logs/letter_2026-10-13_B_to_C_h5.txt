一、H5 五项：数字 + 出处
============================================================

---- 1 ---- 考了多少条 KAT、对了多少条：**1000 / 1000**

  四项独立复算：KeyGen / Encaps / Decaps / 隐式拒绝，各 1000 条。
  出处：`refsim/README.md:17-19`；原始校验环境 `research/mlkem_kat/README.md`。

  ⚠️ **措辞要小心（答辩大概率被追问这一点）**：这 1000 条**不是 NIST 官方发布的
  文件**，而是社区仓库 `post-quantum-cryptography/KAT` 维护的 FIPS 203 兼容向量集。
  报告里应写：「**社区维护的 FIPS 203 兼容向量集，已由参考实现独立复算验证**」，
  不要写成「NIST 官方 KAT」—— NIST 官方走 ACVP（JSON 格式，面向算法验证系统）。
  之所以仍然可信：一份错误的向量集不可能让独立实现四项全中。
  详见 `research/mlkem_kat/README.md` 文首警告。

---- 2 ---- 对拍了多少个系数：**六条通路，各 4096 / 4096**

  | 通路 | 内容 | 结果 |
  |---|---|---|
  | FNTT | 16 组独立向量 | 4096 / 4096 |
  | INTT | 16 组 | 4096 / 4096 |
  | PWM2 | 点乘，16 组 | 4096 / 4096 |
  | 往返自检 | RTL 的 FNTT **实际输出**灌回 RTL 的 INTT | 4096 / 4096 |
  | 完整乘法 FULL | FNTT(A)→FNTT(B)→PWM2→INTT | 4096 / 4096 |
  | 半程乘法 HALF | FNTT(A)→PWM2→INTT | 4096 / 4096 |

  另有链上中间那一环：**作者的期望输出 == 参考实现，512 / 512**
  （DIN0 256 + DIN1 256）。
  出处：`refsim/README.md:29-43`；各入口的**判定行原文**在 `refsim/README.md:103-126`。

  一句话解释「完整乘法」为什么最有说服力：它**时域进、时域出、链上没有任何缩放
  因子**，期望值就是参考实现的输出，逐比特直接比。点乘的 R 与 INTT 的 R⁻¹ 在链上
  正好抵消 —— 所以这一组全过，反过来给单运算那一层的标定做了背书：
  **若 R 或 R⁻¹ 有一个标错了，端到端这两组不可能严丝合缝地全过。**

---- 3 ---- 数据够不够五花八门：见下表

  | 向量集 | 行数 | 不同值 | 最常见值占比 |
  |---|---:|---:|---:|
  | `intt_batch_in`   | 4096 | 2374 | 0.15% |
  | `intt_batch_exp`  | 4096 | 2355 | 0.17% |
  | `pwm2_batch_a`    | 4096 | 2374 | 0.15% |
  | `pwm2_batch_exp`  | 4096 | 2371 | 0.22% |
  | `fullmul_a` / `_b`| 4096 | 2355 | 0.17% |
  | `fullmul_exp`     | 4096 | 2357 | 0.20% |
  | `halfmul_b`       | 4096 | 2374 | 0.15% |
  | `halfmul_exp`     | 4096 | 2357 | 0.20% |

  覆盖 0..3327 全域、无越界。
  判据（出处：`skill/scripts/check_nondegenerate.sh` 文件头）：
    · 不同值 / 总行数 ≥ 30%   —— 实测约 58%（2355~2374 / 4096）
    · 最常见值占比 ≤ 2%       —— 实测 < 0.25%
  出处：`refsim/README.md:153-166`。

  这组数的用途：证明「4096 个系数全中」**不可能是蒙对的**。
  一个永远通过的测试没有价值 —— 所以每一项「通过」都配一份「非退化」统计。

二、波形图（本次新出）
============================================================

  两个文件，内容**完全同一个窗口**，你挑一张用：

    · `report/figures/refsim_wave_fntt_compare.svg`   矢量 —— **优先用这张**
      （`figures/README.md` §三：矢量优先，Word / LaTeX 都能插，放大不糊）
    · `report/figures/refsim_wave_fntt_compare.png`   GTKWave 真窗口截图（备选）

  **这张图在断言什么**（一句话，可直接抄进 §4）：

      FNTT 读出窗口内 256 拍，RTL 输出 dout 与期望值 exp_now **逐拍相同**；
      cmp_ok 每拍采样一次两者的比较结果，图中全程为高 —— 无一次不符。

  图里 8 行信号（从上到下）：
    clk / done（脉冲 = 读出开始）/ read_a / reading（读出窗口）/
    beat（节拍计数，000 → 0FF，共 256）/ dout（RTL 输出）/
    exp_now（该拍应读出的期望值）/ cmp_ok（比较结果，全程高）
  放大窗口 = done 脉冲前一拍起 200 ns（内含 16 个节拍）；两张图共用同一个值。

  **数据链**（每一环都可复跑）：

    refsim/pe1/fntt_wave_tb.v   →仿真→   refsim/fntt_wave.vcd
                                →refsim/gen_wave_figure.py→   上面两张图

  复跑命令：

    cd refsim
    export PATH="/c/iverilog/bin:$PATH"
    iverilog -g2012 -o batch_fntt_wave.vvp <pe1 下的 .v 模块列表> pe1/fntt_wave_tb.v
    vvp batch_fntt_wave.vvp        # 打印：★ 波形覆盖的这一组：256/256 全中
    python gen_wave_figure.py      # 出图前先断言，断言不过一张图都不写

  （`.v` 模块列表照抄 `refsim/run_fntt_check.sh` 的 `SRC` 变量即可。）

  ⚠️ **一句话交代这张图的出身**：它是**专门为出图跑的**单组向量仿真
  （`fntt_wave_tb.v`），**不参与 refsim 的自动判定** —— 判定仍由
  `fntt_batch_tb.v`（16 组）负责。
  图名所声明的事实，**由脚本在出图前断言**（256 拍逐拍 dout == exp_now，
  且 cmp_ok 全程为高），断言不过就一张图都不写、非零退出。不靠目视 ——
  这是 `report/figures/README.md` 的规矩。

  ⚠️ 波形目前**只覆盖 FNTT 一条通路**。INTT / PWM2 / FULL / HALF 的波形我
  **没有出** —— 要的话说一声，同一套脚本加几行就能出。

三、必须一起写进报告的边界（不写，被追问会吃亏）
============================================================

  这些不是「瑕疵」，是**主动写清楚的验证边界** —— 写出来比含糊说「验证充分」有用：

    · 验证**止于一次多项式乘法**。`polyvec_basemul_acc_montgomery`（累加多个点乘
      的向量运算）、base case 乘法（2×2 的 Karatsuba 那步）、以及最终的
      `poly_tomont` / `poly_reduce` 归位**均未验** —— 仓库里没有对应的 RTL，
      没有可验对象。
    · **KAT 只锚到参考实现**。KAT 的字段是 KEM 级的（pk/sk/ct/ss），
      一个只有 NTT 的模块既吃不进也吐不出；KAT 用来锚参考实现，NTT 核由参考
      实现的输出锚。
    · **`refsim/` 下只有 pe1 的仿真验证台**。参数化三档的端到端证据来自**上板**，
      不是仿真。
    · **三档读出顺序不统一**（FNTT 读数路：pe1 = 交织，pe4/pe16 = 自然序）——
      这是**接口的事，不是功能的事**，已作为 H3 协议缺口单独记录。
    · 本章是**功能**验证，**不含**面积 / 频率 / 时序 / 功耗（那些在 `03_*`）。

  权威出处：`refsim/README.md` §八；
  你那边已经写好的是 `report/design/04_functional_correctness.md` §4.9。
