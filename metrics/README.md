# metrics —— 指标汇总表

**主责：C** ｜ 状态：🔄 **资源 / 频率 / 周期数已填（2026-09-29）**；**瓶颈归因已填（2026-10-16）**；**提频实测已填（2026-10-18，综合侧）** —— 80 / 75 / 62.5 MHz，数据落 `report/design/03` §3.10.2 与 `rtl/vivado/board_freq_sweep.md`；**上板五条事务待补**

《选题指导》§8.3 要求有一张指标汇总表，每项写清**测量条件**与**证据文件**。
这个目录就是那张表。

**表里的数由脚本生成**，不手抄：

```bash
node metrics/gen_metrics.mjs      # 资源/频率/周期：从 Vivado 报告解析 → 生成块 + data/metrics.csv
python metrics/bottleneck.py      # 瓶颈归因（PC 侧三段计时）→ 生成块 + data/bottleneck.csv
```

⚠️ **`data/metrics.csv` 的表头按《选题指南》§3.2.5.2 的七列走**（2026-10-17 对齐）：
`指标名称 ｜ 类别 ｜ 数值 ｜ 单位 ｜ 测量条件 ｜ 测试次数 / 时长 ｜ 证据文件`。
原来的「档位」不是独立列，**并入「测量条件」**（例如「档位 pe1；post-route……」），
这样每一行仍然是「一项指标 + 一个可复算的口径」。

---

## ⚠️ 先看三条口径

**1. 这些是 Vivado 实现阶段的数字，不是上板实测的。**
`post-route`（布线后）的资源与 WNS 是工具算出来的，板子跑起来实际能到多少、
串口那条链路的端到端延迟多少，**都不在表里**。上板测出来的才叫实测频率。
（上板「实测最高频率」**2026-10-15 已改判为「做」** —— 例化 MMCM 提频，
数据待 A 的收尾加做第 1 件；端到端延迟目前是**上板墙钟值**，不是核的延迟。）

**2. 数字随报告走，不随手写。**
下面两张主表的每一格都能在 `rtl/vivado/reports/` 里找到出处。
两个 `GEN` 注释标记之间的内容**由脚本生成、不要手改** ——
手改过的数字下次重跑就被覆盖，而且不会有人知道哪个是对的。
要改数字，改的是报告（重跑综合）或本目录的脚本。

**3. 峰值性能不是折叠度越高越好，是取舍。**
三档 Fmax 随折叠度**轻微下降**（168 → 160 → 154 MHz），周期数大幅下降
（904 → 232 → 69）。加速比 1× / 3.9× / 13.1× 是**用频率和资源换来的**。

## 瓶颈归因（PC 侧三段计时）

把一趟 `#NTT` 事务的耗时拆成三段量 —— 计算核、串口搬运、软件参考实现。
归因的结论是 **「瓶颈不在核，在接口」**：核只占万分之几，99.99% 花在 115200 bps 的
串口搬运上。这张表是 `report/design/03` §3.10.3 的数据来源。

**怎么重跑**（要 `python` + `gcc`；**不碰板子**，串口那段走 B 的陪练）：

```bash
python metrics/bottleneck.py    # → 更新本节的 GEN 块 + 写 data/bottleneck.csv
```

⚠️ **计算核那一段是换算值，不是秒表读数** —— 核嵌在协议状态机里，PC 看不见它什么时候起停。
口径是「周期数 ÷ 板上 50 MHz」。串口那一段是**模型值**：字节数是走真实协议栈数出来的线上
真实字节，乘 10 bit ÷ 115200。软件参考实现那一段**随机器变**，机器与编译命令列在最后一节。

⚠️ 表里 **③ 软件参考实现（约 3.9 µs）比 ① 计算核（18.08 µs）快** —— 不是笔误，
口径差异（50 MHz 单蝶形 vs 几 GHz 通用 CPU）与它为什么不影响结论，见
`report/design/03` **§3.10.3**。

| 段 | 耗时 | 在这趟里的占比 | 怎么来的 |

## 单位与陷阱（这三条都踩过）

**① `BRAM tile` 与 `RAMB18` 不是一回事。**
Vivado 把块 RAM 折成 tile：一个 RAMB36 记 1 个 tile，一个 RAMB18 记 **0.5** 个。
所以 5 个 RAMB18 = 2.5 tile。**看 `RAMB18` 那列更直观**，tile 那列容易被误当成个数。

**② `Design State : Fully Placed` 这句话可能是假的。**
上游 `pe16_utop_util.rpt` 里写着 `Fully Placed`，但它对应的日志显示
`place_design` 在 `Phase 1.2 IO Placement` 就报错退出了 —— **布线一步都没走**，
那句是 Vivado 自己标的，与实际不符。
参数化版三档的报告写的是 `Routed`，日志里有 `Router Completed Successfully`。
**别拿那句话当「已布局」的证据截图。**

**③ WNS 为负是设计好的，不是失败。**
约束故意给紧（`create_clock -period 5`，比三档能达到的都快），所以一定不收敛。
Fmax 是**反推**出来的：`T_min ≈ 目标周期 − WNS`，`Fmax = 1000 / T_min`。
如果哪天 WNS 跑出来是**正的**，说明 5 ns 太松、设计没被逼到底，要收紧周期重跑。
（本脚本把这当断言查了：解析出的 WNS 要不是负数就报错退出 —— 写脚本时正是
在「跳过横线行」那句上踩过这个坑，负号被一起过滤掉了。）
