## ★ 主坑：`S_LOAD` 里一个写死的常数

**哪里不对**

`rtl/board/proto_fsm.v` 的 `S_LOAD` 状态里有一句：

```verilog
else if (lc < DATA_LINES + 10'd3)
```

这个 `+10'd3`（也就是「A→B 切 bank 之间等 2 拍」）是**写死的**。

它的真实含义不是「等 2 拍」，而是**核的装载相位有多长**：

```
LOAD_EXT = 256 + PE_NUMBER        // rtl/ntt_core/KyberHPMNTT_top.v:98
```

**pe1 时它是 257，`2+1` 恰好等于 3 —— 所以只有 pe1 是对的。**
折叠度一变，这个数就得跟着变，但它没跟。

**怎么发现不对的**

不是猜的，是把「拍序」真量出来：

| 折叠度 | 相位机可受理的拍数 | B 的 `req_load` 在第几拍 | 余量 |
|---|---|---|---|
| pe1（改前） | 260 | 262 | **+2** ✅ |
| pe4（改前） | 263 | 262 | **−1** ❌ |
| pe16（改前） | 275 | 262 | **−13** ❌ |

余量是负的，意思是**装载请求来得比相位机能受理的更晚**。

**改法**：间隔改成 `DATA_LINES + 2 + PE_NUMBER`，并把 `PE_NUMBER` 从 `ntt_board_top.v`
传进 `proto_fsm`（顶层 parameter，RTL 里不改这个数）。

**为什么可以说「零回归」而不只是「我试过了」**：`2+1` 就是原来的 `3` ——
**pe1 改前改后逐拍字节相同**。这不是抽样，是全逐拍比。

## 两个症状，同一个根因 —— 这一条最值得记

同一个写死的常数，在 pe4 和 pe16 上表现完全不一样，我一开始当成两个 bug 在查。

**症状 (a)：pe4 —— `#PMUL *` 的第二组数据装歪**

`bf_R` 只高 **1 拍**（`load_b_f` 是 1 拍脉冲），而相位机此刻仍然 `slow = 1`，
`else if (!slow)` 判假 ⇒ **这一拍被丢掉，相位永远起不来**。

但**核自己收到了** `bf_R` —— 它从 `OP_IDLE` 进了 `OP_LOAD_DATA`，
于是 `ce` 恒 1、没被按 `1/PE` 门控，**按 PE 倍速把序列化器抽干了**。

所以现象是「每个值都像模像样，不是全 0」—— 这就是开头第一条线索的答案。

**症状 (b)：pe16 —— 连 `#NTT 1`（单 bank）都挂，而且不回话**

`core_start_*` 是**一拍宽**的脉冲，核却在**自由跑的时钟上**把它寄存成 `sf_R`
（`KyberHPMNTT_top.v:134`）。所以 `sf_R` 高那一拍，必须正好撞上 `ce` 被门控打开的那一拍。

相位没结束时 `ce` 按 PE 分频 —— **1 拍宽撞不上** ⇒ start 整个丢掉 ⇒ 核不跑 ⇒
不回 `done` ⇒ 板子 100 ms 后回 `#ERR 06`。

**pe4 为什么侥幸没中**：它的 `ce` 分频比是 4，恰好让那一拍对上了。
**这个「恰好」是最危险的东西** —— 它让一个通用的 bug 在 pe1、pe4 上都藏住了。

## ★ 顺带咬出的护栏缺陷：护栏必须长过被测方自己的看门狗

**哪里不对**

冒烟台的 `GUARD_CC` 原本是 **16 ms**，而**板子自己的核看门狗 `T_CORE_CC` 是 100 ms**。

台子的护栏**比被测方的看门狗还短** ⇒ 台子抢在板子前面放弃，
把一条**马上就要到来的 `#ERR 06`** 误报成「板子没回话」。

**为什么这条比 bug 本身更值得记**：它把**一个能说清原因的失败**（`#ERR 06` = 核超时）
翻译成了**一个说不了原因的失败**（没回话）。诊断信息在这一层被吃掉了一样。

已提到 120 ms。

**规则**：护栏的时间必须**长过被测方自己的看门狗**，否则永远看不到真实错误码。

## ★ 覆盖缺口 —— 这才是它能上板的原因

**哪里不对**

冒烟台只有两条：`#PING` 和 `#NTT 1`。

`#NTT 1` **只装一个 bank**。而 `S_LOAD` 里那个写死的常数，管的是 **A→B 切 bank** 的那一段。

⇒ **「S2 通过了」被拿去背书了一条管两个 bank 的结论。**
那条支路**在仿真里从来没有被行使过**，一次都没有。

**怎么发现的**

修完之后我没有直接上板，先补了一条用例 **`S3`（`#PMUL NTT 1`，A、B 两个 bank 都装）**，
并且**先拿改之前的 `proto_fsm.v` 跑了一遍 S3**：

```
S1  ✅
S2  256/256 ✅
S3  256/256 全挂
```

**复现了真板子那个 2/5。**

**这条阴性对照还带来了一个比「仿真通过」强得多的结论**：

S3 那 256 个实收值 `9f2 161 7fb 961 35b 713 b1f 6f1 …`
与真板子 pe4 的转储 `diag_pe4_pmul_dump.txt` **逐字节相同**。

⇒ **仿真把硬件失效原样复现了** —— 也就是说冒烟台是硬件的**保真**模型。
今天跨三档的所有结论都建立在这个前提上（「仿真过 ⇒ 板子过」），
这条对照是那个前提**唯一**的支撑，比任何一次「通过」都有用。

**探针还直接点了名**：

```
核丢弃的 load 请求：1 次（应当为 0）
→ 有 load 落在相位内被静默丢弃 —— 是 bank 切换的时序，不是顺序
```

**改完对不对**：pe4 真板子 **2/5 → 5/5**，pe16 从**五条全挂**（连 `#NTT 1` 都不回话）
→ **5/5**。三档现在都在真板子上 5/5，各 256/256。

## 一个我自己给自己挖的坑：`nfail` 把 256 个失败瞒成 1 个

冒烟台的结果行是「比对点 520 个，失败 N 个」。

`nchk` 是**逐行**加的（512 个行点），而 `nfail` **每块只加 1**。

⇒ 256 行全挂会印成 **「比对点 520 个，失败 1 个」**。

判据本身没错（结论行仍然正确报「有失败」），但**这个数字是要被报告引用的**。
已改成 `nfail = nfail + nerr`。

⚠️ 今天三档那些「520 / 0」的日志是在这处改动**之前**编译的 ——
通过态看不出差别，只有失败态的计数受影响。这一点我得记着，别在报告里引错。

## 否掉一条「看起来该做」的事：pe2 / pe8 参数扫描

**AI 的判断**

今天板级三档跑通了，很自然地想：「那再扫 pe2、pe8 验证一下参数化做得够不够通用」。

**动手放宽了两处守卫**：`run_board_synth.sh` 的 `case` 改成「任意 2 的幂」，
`smoke_tb.v` 加了 `TB_PE2` / `TB_PE8`。

**然后查到守卫，撤销了，逻辑零改动。**

**为什么**：核与顶层**各有一句 FATAL 守卫**，只认 `PE_NUMBER ∈ {1, 4, 16}`
（`KyberHPMNTT.v:96`、`KyberHPMNTT_top.v:104`）。依据在 `KyberHPMNTT.v:90` 的注释：

> **数据通路是「每档一份」而不是公式。**

表征很直接：`TW_ADDR_W` 写成三路三目

```verilog
(PE_NUMBER==1) ? 9 : (PE_NUMBER==4) ? 8 : 7
```

**不是 `$clog2`。** 要扫 pe2/pe8，得再写两份数据通路副本 + 重推 twiddle 表 + 重验，
是几天的活 —— 不是一个 `case` 语句的事。

**放宽那版如果留着会怎样**：`PE=8` 会**穿过脚本守卫**，跑到综合**深处**才 FATAL。
那正好是那个守卫存在的意义 —— **给错值时宁可一行都不跑。**
两处各留了一段「**别放宽这个 case** / **别加 `TB_PE2`、`TB_PE8`**」的注释。

**教训**：这是 `CLAUDE.md` 约定 5「动手复现某个东西之前先确认它存在」的同类 ——
**扩大适用范围之前，先确认范围。** 这次代价是十几分钟；
若不留神，就是**一小时的综合白跑**（`PE=8` 会一路跑到综合深处才报错）。
