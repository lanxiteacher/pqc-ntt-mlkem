**命令和数据走的是同一条路，但这两类命令根本没有数据。**

**真跑一次，5 秒白等就露出来了。**

**改完对不对**

`board_run.py` 按「有没有标准答案向量」分流：带数据的走 `run()`，探活类走 `probe()`。
`test_host.py` 新增第 9 节（9a–9i，**22 项**），实测 **64 项检查通过**、退 0。

⚠️ **两处口径是我定的、没有经 A 确认**，已原样写进 docstring：**① 探活只发一次**
（不实现 §5.5 规则二的「重新发送」）；**② 探活不发 `#ABORT`**。这两条加了断言钉住，A 若不同意改一行。

## 九、★ `grep` 数行尾会骗人

**问了什么**

这一条没有提问 —— 是 AI 在核 `refsim/batch/` 的行尾状态时，**自己的量法给出了错的数**。

**AI 答了什么**

第一版量法（错的）：

```sh
grep -c $'\r' refsim/batch/ntt_batch_in.txt      # -> 4096
```

报 **4096**（= 全文件都是 CRLF）。**我差点据此下结论「工作区已经脏了」。**

**哪里不对**

**验证方法本身没被验证。** 一个没有对照的量法，给出「4096」这种**太整**的数时，
分不清是「文件真长这样」还是「量法坏了」—— 和 `test_link.py` 第 6 条那个
「整文件字符串搜禁词」是**同一类错**：尺子坏了，量什么都是圆的。

**怎么发现不对的**

用 C 在 `report/ai-log/2026-10-05_C.md` 里写下的那个法子复测了一遍：

```sh
tr -dc '\r' < refsim/batch/ntt_batch_in.txt | wc -c    # -> 0
```

**两个命令给出相反答案。** 于是**拿已知答案的样本去校尺子**：

| 文件 | `grep -c $'\r'` | `tr -dc '\r' \| wc -c` | 实际 |
|---|---|---|---|
| `refsim/batch/ntt_batch_in.txt` | 4096 | **0** | **LF** |
| `research/mlkem_kat/ntt_in.hex` | 4096 | 4096 | CRLF |
| `refsim/batch/fntt_rtl_out.txt` | 4096 | 4096 | CRLF |
| `refsim/run_intt_pwm2_check.sh` | 0 | 0 | LF |

（后两行是**对照**：一个已知带 CR、一个已知不带 —— 表里没有任何一行是孤证。）

**改完对不对**

**以 `tr` 为准。** 结论：`refsim/batch/ntt_batch_{in,exp}.txt` **现在是干净的 LF**
（`git status` 也确认 `refsim/` 无改动）—— 那个 CRLF 缺陷（`KNOWN_ISSUES.md` B3）
**此刻是潜伏的、没被触发**，因为 C 在 10-05 收尾时 `git checkout --` 还原过，
而之后**没人再跑过那条脚本**。

**教训**：**验证方法和被测对象一样要验。**
一个命令给出**太整的数**时，先拿**已知答案的样本**去校它 —— 上面那张表就是那个样本。
**这和 10-04 A 那次「把 WPWS 当 WHS」是同一类**：数字对不上时，**先怀疑自己看的是哪一列**。

## 十二、修掉 B3：CRLF 缺陷（C 报的）

**问了什么**（原话）

> 批准第5步，做完别忘了1和2步

**AI 答了什么**

定的是**四段验法**，不是「改完跑一遍」：
① 改前**先复现** → ② 打补丁 → ③ 再跑 → ④ 看工作区是不是自己干净了。
理由：这个缺陷的症状是**「脏」不是「错」** —— 内容逐字节相同，只是行尾从 LF 变成 CRLF。
**不复现就没法证明补丁真的做了什么**，只能证明「跑完没报错」，而那件事改不改都一样。

**哪里不对**

`refsim/run_intt_pwm2_check.sh` 第 71-72 行用 `cp` 把
`research/mlkem_kat/ntt_{in,out}.hex`（**各带 4096 个 CR**）原样拷进
`refsim/batch/ntt_batch_{in,exp}.txt` —— 那对文件是**已入库**的，内容本来是 LF。
`cp` 把入库的 LF 盖成 CRLF，跑完 `git status` 冒两行黄字。

**怎么发现不对的**

不是我发现的 —— 是 **C 在 10-05 的 H10「非作者从零复跑」时咬出来的**
（`report/ai-log/2026-10-05_C.md:379`）。他只报不改（`refsim/` 是我的主责）。
我今天做的是**复现**：

```
改前：batch/ntt_batch_in.txt 工作区 CR=0
      跑一遍 sh run_intt_pwm2_check.sh  →  CR=4096，git status 冒两行 M
      git diff --ignore-cr-at-eol --stat  →  **空**（内容一个字节没变 → 「脏」不是「错」）
```

**改完对不对**

```
改后：CR=4096（脏状态）→ 跑一遍 → CR=0，git status 只剩我自己改的那个 .sh
      整条链四条脚本依次跑完（fntt → intt_pwm2 → polmul → ntt_layers），退出码全 0
      （脚本清单取自 skill/scripts/check_reproducible.sh:49，不是我随手挑的）
```

**顺带咬出一件事：改完行号就漂了。** 补丁让那两行从 `:71-72` 变成 **`:77-78`**。
全仓库有 6 处在引用这个行号，其中 **2 处是我的**（`KNOWN_ISSUES.md` 的 B3、这篇日志），已跟着改；
另 4 处在 `logs/letter_2026-10-05_C_to_B.txt` 和 C 的日志里 ——
**那是 10-05 的记录，「当时是第 71-72 行」是真陈述，改了反而变成假的**，所以不动。
**教训：行号引用是「会漂的引用」**，改完文件要回头搜一遍谁在指它。

## 十三、第四轮：把两个「写死了」和一个「装不上就验不了」都拆开

这一轮的四面（① 根 `README.md` ② `unpack.py` 的折叠度 ③ `link.py` 的 `loop://` ④ `host/README.md` 状态行），
共同点只有一个：**把「只能靠实物才能验的东西」挪出验的路径之外**。

### 1. 根 `README.md`：补《选题指南》要的「目录对照说明」，但**必须先算清引用点**

《选题指南》§3.3.5.4 要一份「推荐目录 ↔ 本仓库目录」的对照。补之前我先做了一件事：
**`grep -rIn 'README\.md:[0-9]'`** —— 因为根 `README.md` 是**被按行号引用**的。

结果：全仓库引用根 `README.md` 行号的只有 **`:15`**（q=3329 那句）和 **`:110–124`**（目录树）。
而且**其中两处引用落在 `logs/`** —— 那是我**不能改**的目录。
→ 结论：**插入点必须落在 `:124` 之后**，且**插入点之前的行数不能动**（目录树那两行得做成 2 → 2）。

做法与结果：新增 `### 目录对照说明（《选题指南》§3.3.5.4）` 一节（两张表：指南推荐的 8 个目录
逐行映射到本仓库实际目录 + 7 个额外目录），插在 `:128` 之后（新节从 `:130` 起）。
总行数 **204 → 232（+28）** —— **引用点全在 `:124` 及之前，所以一处都没漂**；
事后逐个复核 `:15` / `:110` / `:114` / `:124` **四处仍都指对**。

⚠️ **这里我写错过一次，记下来** —— 我一度把结论写成「**净行数不变**，`wc -l` 204 → 204」。
**插一整节不可能不动总行数**，那句话自相矛盾。真相是：**「行号中性」≠「行数不变」**。
前者说的是**被引用点不漂**；后者只是它的一种实现方式，而这里用的是
「**把新内容插在被引用点之后**」—— 于是总行数照涨，引用照样不漂。
**教训：说「行号中性」的时候，一定要同时说清是哪种实现，否则下一轮的人会照着一个不可能的条件去改。**

⚠️ **中途我自己踩了一次**：目录树那两行一度写成 **4 行**（净 **+2**），正好会顶掉 `:110–124` 这个窗口。
**是自查 `wc -l` 时发现的，没等测试来抓**，立刻合回 2 行。
—— 这跟第二节那次「说错 4 行」是**同一类错**：动被按行号引用的文件，**先数行，再落笔**。

### 2. `unpack.py`：FNTT 的读出序不再写死 pe1（修 B1）

**原状**（`KNOWN_ISSUES.md` B1）：`#NTT` **无条件**取交织表。上板若烧 pe4 / pe16，
FNTT 的**读出**序是**自然序**（§5.3.4:370）→ 解包后 **256 个系数全错**。

**改法**：`permutation(kind, build=DEFAULT_BUILD)`。`build` 就是 `#RDY <ver> <build> <errs>` 的
`<build>`（§5.2:290）。FNTT 查 `_FNTT_PERM[build]`（pe1 交织 / pe4、pe16 自然序）；
**INTT / PWM2 三档同序**，不看它。入口 `board_run.py --build {1,4,16}`。

⚠️ **这一处最要紧的话，我写在代码和 `KNOWN_ISSUES.md` 里都重复了一遍**：
**修的是「能告诉它」，不是「它自己知道」。** `kind_of()` 仍旧 1 参、**故意没动**
（折叠度是编译进位流的，命令里推不出来）；默认档仍是 pe1；而 **`#RDY` 在 A 侧仍是零命中**
（`grep -rIn 'RDY' rtl/` → rc=1）→ **自动识别折叠度仍然做不到**。
谁要是把这条读成「已经能自动认档了」，那就会在 pe4 板上得到 256 个全错的系数还以为是 RTL 的锅。

### 3. `link.py`：SerialLink 的**接线层**终于被跑起来了 —— 顺手咬出一个真 bug

**改动只有一行语义**：开串口由 `serial.Serial(...)` 换成 **`serial.serial_for_url(port, ...)`**。
前者是后者的**子集**：裸口号（`"COM9"`）走**同一条真串口路径**，而 `"loop://"` 会开一个
**进程内的假串口** —— 于是 `SerialLink` 的真身（开 / 关 / 收发 / `LineBuffer` 接线）
在**没有板子**的机器上也能被跑到。

❗ **顺手咬出的真 bug（这条是本轮最值钱的）**：`serial_for_url` 认不出 scheme（如 `"foo://bar"`）时
抛的是 **`ValueError`**，**不是** `SerialException`。原来的 `except serial.SerialException`
**接不住它** → 会冒**裸 traceback**、绕过那句人话。
已改成 `except (serial.SerialException, ValueError)`。真口号打不开那条路**仍旧**走 `SerialException`。

**新验的**：`test_link.py` 第 9 节 9a–9e —— 借 `loop://` 跑真 `SerialLink`：
写→读一行往返 / 超时返回 `None` / 两帧不串 / `discard_pending` 扔对了 / `close` 后 `is_open` 假。

⚠️ **不许含糊的覆盖范围**（我把它写在 `test_link.py` 里，也写进 `KNOWN_ISSUES.md` D6）：
`loop://` **验不到电气层** —— 波特率被**忽略**（实测 4000 字节在 9600 / 115200 / 3M 下都是 ~0.0022 s）、
无 USB 丢字节、无 CH340 流控/DTR、**验不了「真口号能不能打开」**，且内部队列**上限 4096 字节**。
口径只有一句：**接线层验过，电气层一行没验。**

### 5. 一件顺手查清的事：`check_reproducible.sh` 报的「工作区有未跟踪文件」**不是缺陷**
