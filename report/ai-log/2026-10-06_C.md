## 第二件事：让「已验证的效果」真的是**实测**，不是「设计如此」

**AI 答了什么（做法）**：这一列如果写成「这个脚本很好用」，等于没写。
指南评价标准是**可复用性**，而 C 自己刚在 `skill/checklists/verification.md` 第 6 条写下
「**一个永远通过的测试没有价值**」—— 空口的效果不算证据。**于是先去把证据跑出来。**

装了工具链（10-05）之后，三条脚本**本机就能真跑**了：

```
sh skill/scripts/check_data_format.sh refsim/batch
  → 53 文件 / 71168 行；不合规 23 文件 / 1290 行；另有 1 个文件含 CRLF
sh skill/scripts/check_nondegenerate.sh refsim/batch/ntt_batch_in.txt
  → 4096 行 → 2355 个不同值（57.5%）、最常见值 0.17%  ✅
```

**一处交叉核对（顺带验了文档自己的记数）**：`check_data_format` 扫出来的
「**23 个不合规 / 1290 行**」，与 `team/guide_C.md` 与 `todo_C.md` 里记的
「`refsim/batch/` 里 53 个文件有 23 个不合规」**逐项吻合** ——
文档的记数不是抄来的，脚本今天重现了它。

**模板那一类，把两处「未验证」变成了实测**：`batch_testbench.v` 与 `run_checks.sh`
原先写着「本机没有 iverilog、**没有编译验证过**」。工具链 10-05 装好后，今天就真跑一次：

**改完对不对**：骨架**编译 / 语法都过**。但**口径不放大** —— 表里写的是

## 第三件事：四类各补一张「每项四件套」表

**AI 做了什么**：在四个子目录 README 各加一节 `## 每项的四件套（§3.3.5.2）`，
表头固定 `项 | 适用场景 | 使用方法 | 失效条件 | 已验证的效果`：

| 类 | 项 | 「已验证的效果」取的什么 |
|---|---|---|
| `prompts/` | 4 条提示词 | 每条在本项目**实际产生的后果**（① 翻转了实现路线；② 抓出 `Fully Placed` 假标签；③ 抓出 `i16`/`fqmul` 脆弱点；④ 拦下两处「格式对事实错」） |
| `checklists/` | 5 份清单 | 每份**接住过哪类事故**（假失败 / 无区分度 / BRAM 三口径 / 工具预检 / 「格式完美但事实错误」） |
| `scripts/` | 3 个 + `refsim/` 四条入口 | **今天跑出来的数**（23 文件 1290 行；2355/4096；`--from-remote` 退 0） |
| `templates/` | 3 个 | **今天的编译 / 语法检查结果** + 一条如实标注「未端到端跑」 |

**一处刻意的取舍 —— 为什么「一项」按文件算、不按 34 条坑逐条算**：
指南说「每一项」，而踩坑清单有 34 条。逐条给四件套等于**把清单重抄一遍**，
且那 34 条**天生就是「怎么发现的」（= 从哪些观察中总结）**，重复反而稀释。
⇒ 按**清单文件**（5 份）作为「一项」，在 README 里给四件套；
每条坑内部已有的 `现象→原因→怎么修→怎么预防 + 怎么发现的 + 谁扛` 原样保留。
理由写进了 `checklists/README.md` 那一节的开头，**免得下一个读的人以为漏了**。
