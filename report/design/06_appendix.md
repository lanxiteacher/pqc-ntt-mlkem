### A.2 自我纠错轨迹摘编

评分细则点名的「**特别是自我纠错轨迹**」—— 下面六条从已入库的九篇日志里挑出，
共同点是**都不是「AI 一次给对了」，而是「先错了、被查出来、才改对」**，
且**每一条都留下了下一次能自动发现它的手段**。

**① 解析脚本把负号当成了分隔线，三档频率变成同一个数**（09-29）

- **哪里不对**：解析 `Design Timing Summary` 时按「以 `-` 开头就跳过」过滤，
  但 **WNS 是负数、也以 `-` 开头**，真数据行被吃掉，扫进了下面的关键路径表。
  跑出来三档 Fmax **216 / 216 / 216 MHz**，且 **WNS 是正的**。
- **怎么发现的**：两个信号都不用看报告原文就起疑 ——
  ① 同一张表里 LUT 差 12 倍，频率却一个数，不合理；
  ② 时钟约束是**故意给紧**的（200 MHz），WNS 必然为负。`grep` 原文证实真值是 −0.936 / −1.260 / −1.507。
- **改完对不对**：过滤条件改成**只跳整行都是横线的行**；
  并把这个坑**写成断言留在脚本里**（解析出的 WNS 要不是负数就直接报错退出）。
  下次谁改坏这段，脚本自己会喊。

**② 页面印出来的蝶形算式 `t = zeta × b` 本身是错的**（09-29）

- **哪里不对**：`fqmul` 是 Montgomery 乘（自带 R⁻¹ = 169），表里的 `zeta` 又在 Montgomery 域
  （`zetas[0] = 2285 = R`）。两个因子抵消后才成立，所以 `t` **不等于**普通的 `zeta × b`。
  按旧算式算，页面那个例子得 3294，而页面**同时显示**的 a′/b′ 对应的 t 是 743 —— 自己跟自己对不上。
- **怎么发现的**：**没有照抄旧页面往下写**，先写了个探针核 `fqmul` 到底等于什么：
  逆末级 `fqmul(r, 1441) / r` 的比值集合**只有一个值 {512}** → 是纯常数因子 R⁻¹（= R/128），不是算错。
- **改完对不对**：算式改成 `t = fqmul(zeta, b)`；用同一探针把页面显示的
  正变换 28672 个值、逆变换 32768 个值全部复算，**0 处不符**；
  并给页面加了**一行常驻「自检」**——每次打开都把显示的数按页面自己印的算式复算一遍，
  **以后谁改错算式，页面会自己露出来，不靠人看**。

**③ 差点把「多重集相等」写成「逐位对拍」**（10-01）

- **哪里不对**：写参数化三档的功能对拍时，想沿用上游那段的说法写成「4096 个系数**逐位**一致」。
  但探针判的是**多重集相等**（顺序不影响），逐位相等是更强的判据 ——
  **把较弱证据说成较强证据**。
- **怎么发现的**：`../../rtl/probes/README.md` 里明写「**这条判据不含读出顺序**」，
  而三档读出顺序不统一。
- **改完对不对**：章节四里 **§4.4（上游 pe1）= 逐位**、**§4.6（参数化三档）= 多重集**，
  两种用词现在**有区别**；顺序差异归到 §4.8「边界」。
  教训：**术语的精度会被复用**（后面写视频旁白、答辩 PPT 都会照抄），写的时候就要钉住。

**④ 一段 CSS 重构，只有两张图被改写 —— 靠「不一致」揪出一个不报错的 bug**（10-02）

- **哪里不对**：把内联 `style="color:#9ed49e"` 改成类名 `.okfg`（走 CSS 变量），
  颜色值一模一样，**但优先级变了**：`ntt-view.js` 里的 `.stage b { color:var(--fg) }`
  权重 (0,1,1) 盖过单类 `.okfg` (0,1,0)，绿色被前景灰盖掉。
- **怎么发现的**：重跑截图脚本后 `git status` 显示**四张里只有两张对拍页的深色原图被改写**，
  另两张逐字节没变。**「同样一段重构，为什么只有两张变了」这个不一致本身就是警报**。
  于是把已提交那版取出来与新渲染**逐像素比**：差异只有一行文字大小，
  最绿像素从 `#65bc81` 变成 `#d8ded5`。
- **改完对不对**：加更具体的选择器 `.stage b.okfg`，重跑后 `git diff --stat -- assets/` **为空** ——
  4 张深色原图与已提交版本逐字节一致。
  这类 bug **不报错、不崩、只是悄悄变灰**；发现它靠的不是「看」，是「比」。
  **回归基线就在仓库里**（已提交的截图就是正确渲染的基线），此后「重生成图片先 diff 旧版」成了常规动作。

**⑤ 同一篇论文，报告里写了两个频率**（10-03）

- **哪里不对**：章节一 §1.3 主表写 `elec` = **200 MHz**，§1.5 却写「与**主表 1 行**的 **192 MHz** 相差 4%」——
  引用的目标与原文不符。只读 §1.5 不会觉得有问题（它自洽）。
- **怎么发现的**：**照着 §1.5 给的坐标回主表对**才暴露。再往上一层追，
  两个来源文档也打架：汇编 §2.2 写 200、A 的对比表 §四写 192，**而原始 PDF 不在仓库**（版权）。
- **改完对不对**：不改数字不留痕 —— 定 192（按对比表）之后，
  §1.3 表下**加注**「两来源不一致、本表取 192、待核 PDF」，§1.7 溯源表加一行记录取值来源。
  **不留痕的话，下一个人核到汇编 §2.2 会以为我们抄错了。**

**⑥ 照着信里的坐标去核，核出信本身也不准**（10-05）

- **哪里不对**：A 的 H4 第二次投递里写板级三档「总端点数」7783 / 8785 / 12644、
  并列了三份 `board_pe*_txn.txt`。
- **怎么发现的**：回 `board_pe*_timing.rpt` 对 —— 报告里**有两张表都叫 `Total Endpoints`**
  （`sys_clk` 单域 vs 全路径汇总，后者把非时序路径也计了进去，
  是 11242 / 12723 / 18641）；`git ls-files` 只找到 pe4 / pe16 **两份** txn 日志，**pe1 那份不在**。
- **改完对不对**：报告采用 **`sys_clk` 单域**口径（本设计只有一个时钟域）并注明依据；
  pe1 那一档注明「原始日志未入库」、数字另指出处。
  **与第 ⑤ 条同类**：`A 指向 B` 时，就去 B 看 A 说的对不对 —— **引用链就是检查点**。

### A.3 这些纠错背后的一个共同模式

回看上面六条（连同 A.1 里未展开的那些），会发现**绝大多数都不是「逻辑写错了」**，而是两类：

1. **验证手段本身不可靠** —— 校验脚本自己会骗人：`$(...)` 吞掉了行级明细、
   Windows 上 `awk` 看不见 CR 而把 CRLF 判成合规、`command -v` 认得 WindowsApps 占位符、
   解析正则把负号当分隔线。**脚本只要写完就交，这四个全都会留在里面。**
   它们的共同修法不是「改对一行」，而是**把判据本身做成断言留在脚本里**。
2. **引用链没回源头核** —— 报告内部的交叉引用、来源文档之间的数字、
   队友信里的坐标，**每一处都是一个检查点**。
   ⑥ 与 ⑤ 是同一个动作：**顺着指针走一趟，看目标说的和指针说的一不一样**。

这两类都不产生编译错误，也不让程序崩 —— 只会给出一个**看起来对**的答案。
把「怎么发现的」当成长效机制（而不是一次性修修补补），是这份记录里最值得复用的部分，
也是技能包 `checklists/` 那 34 条成文的来源。
