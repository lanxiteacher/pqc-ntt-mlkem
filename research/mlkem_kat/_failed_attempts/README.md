# `_failed_attempts/` —— 抓 KAT 那次失败尝试的原始残留

**这里没有考题，也别拿去做任何事。** 这些是 2026-09-18 抓 `kat_MLKEM_768.rsp`
那次失败尝试留下的中间文件。

**经过和结论不在这里** —— 在两个脚本里，要看就看那两个：

- `../fetch_kat.py` —— 最终跑通的做法（含为什么必须分块、为什么不能一把梭）
- `../complete_kat.py` —— 补尾部的做法，附两条教训（**「不只查大小，还要查内容」**）

## 目录里是什么

| 文件 | 是什么 |
|---|---|
| `fetch_kat.sh` | 第一版抓取脚本（bash）。200 KB 一块，下 GitHub API 的 blob |
| `hdr.txt` | 抓到的 HTTP 响应头。**限额就在这里**：`X-RateLimit-Limit: 60`（未认证 / 小时），当时 `Remaining: 25` |
| `blob.json` | `api.github.com` 的 blob 元数据（668 KB）。⚠️ **它自己也是被截断的** —— JSON 没闭合，`size` 字段写 `12012890` |
| `seg0.bin` | 第一块落盘（1 KB），内容与 `parts_00` 开头相同 |
| `parts_00` / `parts_01` / `parts_02` | 分块下载的块文件（约 1.9 MB）。`parts_00` 从 `count = 0` 开始 |
| `try_raw.rsp` | 改从 raw 主机试抓的残件（852 KB） |
| `kat_repo.tar.gz` | 试抓整个 `post-quantum-cryptography/KAT` 仓库（1.6 MB，gzip 头完整） |

## 为什么失败

目标 blob **12,012,890 字节**，每块 200 KB：

```
12012890 / 200000 = 60.06  ⇒  需要 61 次请求
```

而未认证的 GitHub API 配额是 **60 次 / 小时**。

**差 1 次。** `fetch_kat.sh` 里没有处理 403 限流的分支，第 61 块拿不到，
`cat parts/* > kat_MLKEM_768.rsp` 拼出来的就是缺尾的文件。
（`hdr.txt` 抓到的那个时刻已经用掉 35 次、只剩 25 次。）

后续 `fetch_kat.py` 加上了「403 就睡到配额重置、并支持断点续传」才拿全；
尾部又被混进一个 279 字节的限流错误页，由 `complete_kat.py` 补上。

## 为什么留着不删

反面教材，与 `CLAUDE.md` 约定 5 同类：**动手之前先把约束算清楚**。

61 与 60 这两个数，**在写脚本之前就能算出来** —— 目标大小除以块大小，再和配额比一次。

## 为什么不 `git rm --cached`

`logs/project_state.md` §二 曾记过一条待办，说这 4.8 MB「死文件」要 `git rm --cached` 省体积。
**2026-10-04 核实：省不了，故不做。**

这些 blob 在 `5fdc597`（初始化仓库）提交里**可达**，从 tip 删掉**不影响 pack 的内容** ——
任何一次 clone 照样得把它们传下来。能省下的只有本地检出目录那 4.8 MB，
而改动本身要动 `.gitignore` 加 3 处记录。收益不抵改动。

**真要省 clone 体积，唯一的办法是改写历史 —— 不做**（已经推送给三个人的仓库，
改历史等于让每个队友重 clone）。
