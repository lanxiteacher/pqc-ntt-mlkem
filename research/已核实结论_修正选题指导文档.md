## 修正 1 ｜根本不存在 `zetas_inv` 表  【已验证】

指导文档 §3.2 花大篇幅推导「`zetas_inv` 的层序」，并把它列为「唯一没啃下来的硬骨头」。
**前提就是错的：参考实现里没有这张表。**

`ref/ntt.c` 的 `invntt()` 复用**同一张** `zetas[128]`，只是索引 `k` 从 127 **递减**到 1：

```c
void invntt(int16_t r[256]) {
  const int16_t f = 1441;   // mont^2/128
  k = 127;
  for(len = 2; len <= 128; len <<= 1)
    for(start = 0; start < 256; start = j + len) {
      zeta = zetas[k--];            // <-- 同一个数组，倒着走
      ...
    }
  for(j = 0; j < 256; j++) r[j] = fqmul(r[j], f);
}
```

- `zetas[0]` 正向、逆向**都不使用**。
- 层序（已逐层列出，地址生成逻辑可直接照抄）见 `../rtl/zetas_tables_verified.v` 头部注释。
- 旧 `../rtl/zetas_tables.v` 里的 `ZETAS_INV` 基于错误前提构造，**不可用**（且 64..127 项是占位符）。

## 修正 2 ｜正向 NTT 输出可以直接和教科书 NTT 逐点比对  【已验证】

指导文档「陷阱 2」称硬件 NTT 输出永远无法与干净 Python NTT 逐点比对。**这是错的。**

实测 `ntt(a) mod q` 与标准域教科书 NTT **完全相等**，比值集合 = {1}。
原因：`zetas[i]` 存的是 **Montgomery 形式** `R·17^bitrev7(i)`，而 `fqmul` 内含 `R⁻¹`，两者恰好抵消。

推论：**整条 NTT→basemul→INTT 链路的净缩放恰为 1**，无需任何后处理。
（此结论已用 20 组随机多项式对拍验证，全部通过。）

## 修正 3 ｜常数以参考实现为准  【已验证】

`ref/reduce.h` 用的是**有符号中心化代表**，不是无符号：

| 常数 | 指导文档 | 参考实现（正确） |
|---|---|---|
| `MONT` | 2285 | **−1044** |
| `QINV` | 62209 | **−3327** |

两者 mod q / mod 2¹⁶ 等价，但写进 RTL 时位宽截断行为不同，**直接用文档值会出错**。

指导文档「陷阱 3」正确：`1441` 必须配 `fqmul` 使用（已实测验证）。

## 修正 4 ｜Round-3 官方 KAT **不是** ML-KEM 的 KAT  【已验证】

`research/Kyber-Round3.zip`（2020-10-21 提交版）内的 KAT **不能**用来验收 FIPS 203 ML-KEM。

**证据** —— 两版 `indcpa_keypair` 的种子派生不同：

```c
/* 2020 Round-3 版 (kyber v3.0) —— zip 内 clean/crypto_kem/kyber768/indcpa.c */
randombytes(buf, KYBER_SYMBYTES);
hash_g(buf, buf, KYBER_SYMBYTES);          // G(d)

/* 当前 pq-crystals/kyber ref 版 (ML-KEM / FIPS 203) —— 本机已下载并编译 */
memcpy(buf, coins, KYBER_SYMBYTES);
buf[KYBER_SYMBYTES] = KYBER_K;
hash_g(buf, buf, KYBER_SYMBYTES+1);        // G(d || K)  <-- 多了模块秩域分隔
```

`G(d)` vs `G(d || K)` → **种子不同 → pk/sk/ct/ss 全不同**。

**要对拍 ML-KEM-768，必须换成 ML-KEM 自己的 KAT**（ML-KEM 提交包或 NIST ACVP 向量），
不能用这份 Round-3 的。文档 §10.1 待办项「下载官方 KAT 文件并确认格式」**格式已确认、但取错了版本**。

### KAT 格式本身（已确认，供参考）

`kyber768/PQCkemKAT_2400.{req,rsp}`：

- `.req`：`count` + `seed`（96 hex = **48 字节**）+ 空的 `pk/sk/ct/ss`
- `.rsp`：`# Kyber768` 头 + 每记录 `count/seed/pk/sk/ct/ss`
- 字段字节数：pk **1184** / sk **2400** / ct **1088** / ss **32** —— 与 ML-KEM-768 规格完全一致
- ⚠️ seed 是喂给 **NIST AES256-CTR DRBG** 的，不是直接当随机字节用

## 修正 5 ｜官方 KAT **无法**验证「只有 NTT 核」的硬件  【推论，但确定】

这是对指导文档核心验收方案（§「KAT 对拍通路：PS 喂向量 → PL 计算 → 读回 → PC 比对官方 `.rsp`」）的**根本性质疑**。

KAT 的字段是 `pk/sk/ct/ss` —— **KEM 层的产物**。要复现它们，必须实现完整的
ML-KEM（K-PKE + FO 变换 + SHAKE/Keccak + CBD 噪声采样 + 压缩编解码 + 序列化）。

**一个只做 NTT 的核，喂不进 KAT、也吐不出 KAT。** 这条路走不通。

可行替代：
- **① NTT 核的正确性判据**：用 `ntt_golden.py` 黄金模型逐点对拍（已验证与 C 参考位精确一致），
  外加**数学唯一判据** —— 与 `negacyclic_schoolbook()` 的朴素负循环卷积结果比对（该值数学上唯一，无法糊弄）。
- **② 若要上 KAT**：必须做「PS 跑完整 ML-KEM、PL 只加速 NTT 段」的软硬协同架构，
  且用 ML-KEM 版 KAT（见修正 4）。
