# 921600 演示模式 —— 串口提速与它的天花板

> 2026-10-18 · A ｜ 对应出彩组合第 2 件（A+B）
> 证据：`reports/board_pe1_b921600_txn.txt`（50 MHz）、`reports/board_pe1_f80_b921600_txn.txt`（80 MHz）
> 复跑：见 §五

## 一、结论

| 命令 | 线上字节 | 115200 线上时间 | 921600 线上时间 | 线上倍数 | 事务墙钟 115200 | 事务墙钟 921600 | 墙钟倍数 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `#NTT 1` | 2124 B | 184.4 ms | **23.1 ms** | **8.0×** | 0.250 s | **0.079 s** | **3.2×** |
| `#PMUL NTT 1` | 3168 B | 275.0 ms | **34.4 ms** | **8.0×** | 0.328 s | **0.094 s** | **3.5×** |
| `#PMUL TIME 1` | 3172 B | 275.3 ms | **34.4 ms** | **8.0×** | 0.328 s | **0.094 s** | **3.5×** |

- 三档命令在 921600 下 **0 误码**：`--check` 逐条 `0/256 不同`，六条命令 6/6 PASS。
  50 MHz 与 80 MHz（MMCM 提频版）两版位流都跑过，都是 6/6。
- 线上时间按「字节 × 10 bit ÷ 波特率」算 —— 这就是**串口线本身**的搬运时间，8× 是确定的。
- **事务墙钟只快了 3.2–3.5×**，差的约 55 ms **不是 FPGA、也不是串口线**，是
  板载 **CH340C 的 USB latency timer**：每次「PC 发完 → 板子回一行」的往返固定多约
  **31 ms**（实测 `#PING` 往返：115200 = 0.031 s，921600 = 0.031 s，**与波特率无关**）。
  一条事务有 3 个这样的往返（命令→`#OK`、数据→`#BEGIN`、收完→`#DONE`），
  3 × 31 ms ≈ 93 ms 的上限里，实测只付了约 55 ms（后两个往返与前一段传输重叠）。

> **一句话**：**串口线提速 8× 已经做到了；端到端剩下的时间卡在 USB 转串口的定时器上，
> 不在我们的 RTL、也不在协议。** 这一条对报告 §3.10.3「瓶颈不在核，在接口」是个补强 ——
> 接口内部还能再拆一层：线上 23 ms + USB 往返 ~55 ms。

## 二、怎么做（只动两个参数 + 一处上位机写）

### 2.1 RTL / 综合

`ntt_board_top` 与 `ntt_board_top_mmcm` 本来就有 `UART_BPS` 参数；`uart_rx`/`uart_tx`
按 `CLK_FREQ / UART_BPS` 整数分频。这次只把它接到综合入口：

- `synth_board.tcl` 读环境变量 `UART_BPS`（默认 115200），传给两个顶层；
- `run_board_synth.sh` 透传并打印；
- `run_board_txn_report.sh` 加 `BAUD=`，把 `--baud` 传给 `board_run.py`，
  报告头里写明波特率 —— **给错波特率不会报错，只会收到乱码**，所以必须留痕。

分频取整误差（这是 921600 唯一要算的数）：

| 时钟 | 分频 | 实际波特率 | 误差 |
|---|---:|---:|---:|
| 50 MHz | 54 | 925 926 | **+0.47%** |
| 80 MHz | 86 | 930 233 | **+0.94%** |

8N1 一帧 10 位，累积误差 < 10% 个位宽，远小于半个位（接收端按位中点采样）。
两版位流实测都 0 误码，与这个估算一致。

### 2.2 上位机：整段数据行一次写出

`host.py` 原先把 256 / 512 行数据**逐行** `write`，而 `SerialLink.write()` 每行都
`flush()` 一次 —— Windows 上等于每行一次 USB 往返。115200 时线上 184 ms 把这笔开销盖住了；
921600 时线上只剩 23 ms，它就成了主要开销（实测逐行 0.094 s → 整段一次写 **0.079 s**）。

改法：`Host._attempt` 里对**真串口**走 `_send_bulk()`（一次 `write` 整段字节流），
陪练仍逐行写（`Link.BULK_WRITE` 标志位）。字节流本身不变：每行仍以 LF 结尾、顺序不变，
板子的行组装器只认 LF。`test_host.py` 的「一次 write = 一行」断言仍按陪练的写法成立。

### 2.3 计时口径

`board_run.py` 加了一行 `事务耗时：x.xxx s`，只包 `hst.run()`（发命令 → 收齐最后一行），
**不含 Python 启动、不含开串口**。进程外的 `Measure-Command` 会把 0.4 s 启动时间也算进去，
不能用它比 115200 和 921600。

## 三、为什么没有更快

| 想再快 | 为什么不做 |
|---|---|
| 1 Mbps / 2 Mbps | 线上只从 23 ms 降到 21 / 10.5 ms，而 USB 往返的 ~55 ms 一分不少 —— **不提速也几乎一样**。 |
| 调 CH340 的 latency timer（设备管理器 → 1 ms） | 能把墙钟压到约 30 ms，但那是**每台机器的驱动设置**，写不进仓库、换台电脑就没了；报告里只能当「还能再快多少」的说明，不能当实测。 |
| 去掉「等 `#OK` 再发数据」的握手 | 协议 v1.0 冻结条款，改了要三方同意并重验，收益只有 31 ms。 |
| 改二进制帧 / 压缩向量 | 协议冻结；而且这不是「串口提速」这一件的范围。 |

## 四、边界

1. **921600 是编译期参数**：位流的 `UART_BPS` 与 PC 的 `--baud` 必须一致，否则全是乱码。
   位流之间**文件名不带波特率**，靠目录（`_runs/pe1_b921600`、`_runs/f80_pe1_b921600`）区分；烧之前看清目录。
2. **报告里的 8× 指线上时间，3.2× 指事务墙钟** —— 引用时必须说清是哪一个，别把 8× 写成端到端。
3. 六条命令 6/6 的原始输出在报告里；**没有**做长时间连续跑（比如连跑 1000 次）的压力测试，
   误码率只覆盖了这 6 条 × 2 个位流。
4. CH340C 的 31 ms 往返是**实测值**（`#PING` 往返，两种波特率各 3 次），
   16 ms 的 latency timer 是**推断**（31 / 2 ≈ 15.5）；没有去改驱动参数验证。

## 五、复跑

```sh
# 1) 出 921600 位流（50 MHz 与 80 MHz 各一版，互不覆盖）
VIVADO_RUNS=rtl/vivado/_runs/pe1_b921600 UART_BPS=921600 TAG=_b921600 PE=1 \
  sh rtl/vivado/run_board_synth.sh

VIVADO_RUNS=rtl/vivado/_runs/f80_pe1_b921600 TOP=ntt_board_top_mmcm \
  MMCM_MULT=24 MMCM_DIV=15 UART_BPS=921600 TAG=_f80_b921600 PE=1 \
  sh rtl/vivado/run_board_synth.sh

# 2) 烧 + 跑（口号现查，别写死）
BIT=rtl/vivado/_runs/f80_pe1_b921600/ntt_board.bit sh rtl/vivado/run_board_prog.sh
PE=1 TAG=_f80_b921600 BAUD=921600 PORT=COM10 sh rtl/vivado/run_board_txn_report.sh

# 3) 单条计时（事务耗时只包 hst.run）
python host/src/board_run.py "#NTT 1" --check --build 1 --port COM10 --baud 921600
```
