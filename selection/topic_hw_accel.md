## 〇、本轮锁定的前提（决策依据，先读）

### 硬件与外设（已确认）
| 项目 | 值 | 含义 |
|---|---|---|
| 芯片 | **XC7Z020（7020）** | 53,200 LUT / 220 DSP / 140×36K BRAM = **约 4.9Mb（≈0.6MB）片上存储** |
| 外设 | **摄像头接口/模块 + HDMI 输出** | 实时视觉方向从"不可行"变为"可行"；但驱动与显示时序仍需人上板调 |
| CPU 基准 | **PC 上位机**（跑同算法 C/Python，串口/USB 喂数据） | 保住 PL-only 打法，不碰 PS/SDK/Linux；对比叙事最直白 |
| 演示屏 | 接**真显示器/电视**；录屏用 **USB-HDMI 采集卡** | 笔记本 HDMI 口基本只有输出没有输入，**不能把笔记本当 FPGA 的显示器** |

### 硬性物理约束（枪毙了哪些题）
- BRAM 仅 ≈0.6MB → 装不下任何有规模的权重模型；大图 GNN、端侧 LLM、3DGS 渲染、U200/HBM 级方案**全部出局**。
- 小 ViT / MobileViT 类虽塞得进，但 7020 实测端到端加速仅 **~1.4×**，演示"不震撼"→ 也否。
- 摄像头时序 + HDMI 是 AI 帮不了的段，任何视觉题都要为它**预留板级调试时间**。

### 一个必须先接受的现实（贯穿全部候选）
> **在 7020 + 摄像头上，"最新算法"和"夸张加速比"常常冲突。**
> 加速比能上 43× 的，内核几乎都是**经典但极度并行**的算法；真·新范式（ViT/LLM/3DGS）要么加速比只有 1.4×，要么物理装不下。
> 所以三选一的落点不是"追算法新"，而是 **"经典内核 + 新应用/新系统 + 全程实测数据"**，或在 **HDC 这类"可搬上 7020 的新范式"里当第一个，自己测出数字**。

## 一、候选①：实时视频去雾 / 图像增强（推荐保底）

### 它是什么
摄像头实时画面（雾天/低照度/逆光）→ FPGA 流水线处理 → HDMI 直出增强后的画面。核心算法两条主流路：
- **暗通道先验 DCP**（经典，2009）：估计大气光 + 透射率 → 反推清晰图。
- **CLAHE + 双边滤波**（自适应直方图均衡 + 保边平滑）：对比度增强。

### 为什么加速效果"能上台"
同级别板（PYNQ-Z2 ≈ 7020 逻辑规模）**已有实测**：
- 比 2GHz ARM 软件快 **43×**，12 FPS @ 0.79W；
- 1080p CLAHE 30 FPS，而 PC 软件单帧要约 2 秒；
- 功耗 0.4–2.3W，能效（FPS/W）最高 **153×**。
数据来源见文末。评委最吃的"硬件 vs 软件实测对比表"可以直接照抄这一套路子做自己的。

### 为什么"算法不新"但仍然成立
- 内核老（DCP 是 2009 年论文），但**实时视频去雾在 2025–2026 仍是顶级会议/期刊热题**（HazeClear ASIC、EdgeLUT 等均为 2026 作品）——热在"工程落地"不在"算法发明"。
- 新意可落在：**应用场景**（行车/无人机/安防雾天）、**系统完整度**（实时 30–60FPS 闭环）、**优化手法**（定点化、行缓存流水线、LUT 代替除法）。

### AI 代工边界（哪段 AI 能写、哪段要你扛）
| 环节 | AI 能帮？ | 备注 |
|---|---|---|
| 暗通道求 min、透射率估计、大气光 | ✅ 能写 | 纯逻辑，行缓存 + 比较树，AI 主场 |
| 除法/对数用定点或查表替代 | ✅ 能写 | 数值优化 AI 强项 |
| HDMI / 摄像头 时序驱动与上板 | ❌ 帮不了 | **全项目最大风险点，需预留大量上板时间** |
| 与 CPU 软件逐帧对比测试 | ✅ 写脚本/采集数据 | 你只需会跑 |

### 风险与回退
- 主风险：**摄像头/HDMI 上板翻车**（时序违例 → 黑屏）。
- 回退方案：去雾算法 + 离线图片/录像输入（BRAM/串口喂帧），仍能交"算法加速 + 对比数据"，只是少"实时"两个字。

## 二、候选②：超维计算（HDC）视觉实时分类（要"新算法"就选它）

### 它是什么
不学深度网络的另一个"脑启发"范式：把输入（图像块/特征）编码成**高维二值向量**（hypervector），分类 = 与各类原型向量的**汉明距离/相似度**。核心运算只有 **异或、多数投票、移位、计数**——几乎没有乘法，天然不吃 DSP。

### 为什么新
- 是"新算法优先"三选项里最平衡的一个：算法新、逻辑极简、7020 装得下。
- 竞赛/学术现状：学术圈 2025–2026 刚热起来（多个 2026 FPGA 加速器论文），**但 7020 这个具体平台上还没有公开实现 → 你是第一个**，这就是差异化。GitHub 上有现成 Zynq 的 AXI-HDC 加速器 IP 可参考/二次开发。

### 加速数字要诚实看待（关键提醒）
- 公开的夸张数字（1300× vs CPU、40× vs CPU）来自**更大平台**（U280、ZCU104），**不是 7020 测的**。
- 你如果选它，**"明显加速"这个卖点必须由你自己在 7020 上测出来才算数**——大概率能测出（运算极轻、高度并行），但存在"测出来没那么夸张"的风险。
- 演示叙事可替换为**能效/吞吐**（低功耗实时分类），而不只赌倍率。

### 典型题目形态（供讨论）
摄像头画面 → 按帧做图像编码（如 patch 编码）→ HDC 分类（如手势/物体/简单场景）→ HDMI 叠加结果。或对**持续视觉流做异常/动作识别**。

### AI 代工边界
| 环节 | AI 能帮？ | 备注 |
|---|---|---|
| 编码器（图像→hypervector）与原型训练 | ✅（训练可在 Python 离线做） | 算法理解是你要过的一关 |
| XOR/多数投票/相似度 硬件单元 | ✅ 极擅长 | 逻辑简单 |
| 摄像头/HDMI 上板 | ❌ | 同①，项目共同风险点 |
| 在 7020 上自测加速比并写对比 | ✅ 写脚本 | 数字要你接受并复述 |

### 风险与回退
- 主风险：**自测加速比/精度不如预期**，或答辩时"为什么不用 CNN"被追问。
- 回退：把 HDC 与一个 CPU 端 CNN 做**"同等任务、硬件资源与功耗对比"**，把叙事从"快多少倍"转向"省多少资源做到接近的精度"。

## 三、候选③：实时 ORB 特征提取与匹配（视频稳像/拼接，居中选项）

### 它是什么
对摄像头每帧提取 ORB 角点 + 描述子，做帧间匹配 → 可用于：
- **视频稳像**（估算帧间运动并补偿抖动）；
- **实时图像拼接**（多帧/多路融合）；
- 视觉里程计 / SLAM 前端（更深，2027 再说）。

### 为什么加速效果能上台
- 特征提取是典型"每个像素窗口做相似运算"→ 极度适合流水线/并行。
- PYNQ-Z2 类板上 **ORB 约 48 FPS（CPU 约 15 FPS）**；文献里对 CPU 加速比 3.6×–115×（视平台与分辨率）。
- 效果可直接看到：同一画面 CPU 处理一帧多久 vs FPGA 实时，演示直观。

### 为什么是"居中选项"
- 算法比 DCP 新一点（ORB 2011），比 HDC 成熟得多；工程套路（金字塔/行缓存/滑窗/描述子采样）资料多，AI 好写。
- 但"新意"不如 HDC，加速倍率稳定性不如去雾的 43× 那种夸张——界于两者之间。

### 难度诚实评估
- 比去雾**代码量大**（角点检测 + 方向 + 描述子 + 匹配好几段），比 HDC 更接近"传统 FPGA 图像工程师"的活。
- 要压 30FPS 需要较深的时序/流水功力；对"体验局 + 保底思维"来说，工作量偏大是主要顾虑。

## 四、三选一决策表（拿去和队友/老师讨论）

| 维度 | ① 实时去雾/增强 | ② HDC 视觉分类 | ③ ORB 稳像/拼接 |
|---|---|---|---|
| 加速数字可信度 | ★★★★★（有同板实测 43×） | ★★☆（7020 无数据，要自测） | ★★★★（48FPS vs 15FPS 明确） |
| 算法新鲜度 | ★★（内核老、落地热） | ★★★★★（新范式、7020 首作） | ★★★ |
| 代码工作量 | ★★（中，流水线规整） | ★★（小，逻辑简单） | ★★★★（大） |
| 摄像头/HDMI 依赖 | 高 | 高 | 高 |
| 上板翻车风险 | 中 | 中 | 中高 |
| 答辩"为什么是FPGA"说服力 | 强（低功耗实时） | 强（新范式+首作） | 中 |
| 对 2027 届的延续价值 | 中（视频增强可深化） | 中（HDC 学术新） | 高（SLAM/机器人路） |
| 本队定位契合（体验局保底） | **最稳** | 要接受自测风险 | 工作量偏大 |

**一句话倾向**：
- 只想 2026 稳稳交得出去 → **①**
- 真想要"算法新 + 抢 7020 首作"、且敢自己测数字 → **②**
- 想顺带为 2027 SLAM/机器人铺路、不怕活多 → **③**

## 五、共同的"CPU 对比"做法（三个候选都通用）

1. 同一份输入（同一段录好的视频帧 / 同一批数据）分别喂给：
   - **PC 软件**：C 或 Python（OpenCV）实现同一算法，逐帧计时；
   - **FPGA**：硬件流水线，测单帧延迟 / 吞吐 / 功耗。
2. 输出一张对比表：帧率、单帧耗时、功耗、能效（FPS/W）、精度（去雾的 PSNR/SSIM、HDC 的分类准确率、ORB 的匹配正确率）。
3. 报告/答辩里给**资源占用表**（LUT/BRAM/DSP + 时序报告）+ 上面的实测对比，即评委最吃的那套。
4. 数据流建议：**PC 经串口/USB 喂数据给 FPGA、FPGA 回传结果**；实时视频题则 FPGA 直出 HDMI 到真屏，录屏素材走 USB-HDMI 采集卡。
