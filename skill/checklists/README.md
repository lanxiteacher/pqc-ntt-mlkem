# checklists —— 踩坑清单

**这个目录里的每一条都是本项目真实踩过的**，不是从网上抄的通用建议。
每条按同一个格式写：

```
现象 → 原因 → 怎么修 → 怎么预防
```

外加两行：**怎么发现的**（这一条最重要，它决定下次能不能更快发现）和 **谁扛**
（AI 能代写代码，但概念、常数来源、板级调试只能人扛）。

## 每项的四件套（《选题指南》§3.3.5.2）

指南要求**每一项**写明 **适用场景 / 使用方法 / 失效条件 / 已验证的效果**，
并说明**是从哪些失败或观察中总结得出**。这里「一项」= 一份清单文件；
每条坑内部另按 `现象 → 原因 → 怎么修 → 怎么预防 + 怎么发现的 + 谁扛` 写，
「怎么发现的」就是「从哪些观察中总结」。

| 文件 | 适用场景 | 使用方法 | 失效条件 | 已验证的效果 |
|---|---|---|---|---|
| `data-format.md` | 任何**我们自己写、之后要逐字节比**的数据文件 | 按「现象」当症状检索；新项目起步先设 `.gitattributes` | 只管自写数据文件 —— Vivado 报告、第三方原件、Verilog 源码**不在内** | 定位「数值全对、`diff` 却报 256 行全不同」这类假失败；产物是 `.gitattributes * -text`。10-05 `check_data_format.sh` 扫 `refsim/batch/` 实测 **23 文件 / 1290 行**不合规，与文档记数逐项吻合 |
| `verification.md` | 任何要写「验证通过」的场合 | 每验一块过一遍；时间紧时先读第 1、3、6、8 条 | 拿「**作者自带的期望值**」当判据时会失效（第 5 条） | 立起「全中必须配**非退化**」「阴性对照要**恰好 1 处**」两条硬判据；非退化实测 **2355–2374/4096**、最常见值 < 0.25% |
| `rtl-and-timing.md` | 读 Vivado 资源 / 时序报告，定接口位宽 | 出报告后逐条对照 | 跨器件比 BRAM / WNS 时不适用（见文末附节） | 抓出 BRAM **三种口径差 2 倍**、`Fully Placed` 是**假标签**（日志显示布局已失败）、WNS 负值被「按 `-` 开头过滤」吃掉后表现为「几档频率一模一样」 |
| `toolchain-and-board.md` | 换机器搭环境、上板之前 | 上板前逐条核对那三个**物理前置条件** | 换板卡 / 换工具版本后部分条目需重核 | 定下「工具预检要**真跑**、不能只看 `command -v`（PATH 占位符会骗人）」「Vivado 必须**从仓库外**启动（路径含撇号会让综合引擎崩）」；均在本机实测复现 |
| `ai-collaboration.md` | 与 AI 协作的日常 | 每次让 AI 出汇总 / 常数 / 更正时对照 | 纯写作类任务不适用 | 拦下「**格式完美但事实错误**」这一类（第 5 条）；本项目两次实例见该文件 |

## 怎么用这份清单

**如果只读三分钟**：读 `data-format.md` 第 1 条、`verification.md` 第 1 条和第 3 条、
`toolchain-and-board.md` 第 1 条 —— 这四条是「不知道就会卡半天、而且卡得莫名其妙」的那一类。

**如果是新项目起步**：按 `data-format.md` → `verification.md` → `toolchain-and-board.md`
的顺序把清单过一遍，把能提前设防的设上（`.gitattributes`、有界循环、相对路径）。

**如果是排查具体问题**：清单里的「现象」一栏是按症状写的，用来检索。

## 一句话规律

> **AI 能写大约 90% 的代码；剩下 10% 是概念理解、常数来源、板级调试。**
> 那 10% 决定作品成不成。

本项目里反复出现的一类失败是**看上去失败、其实只是约定不同**：

- 对拍报「256 个系数全错」，实际只差一个常数因子（`verification.md` 第 4 条）
- 灌数据报「256 个系数全错」，实际只是读出顺序不同（`rtl-and-timing.md` 第 5 条）
- `diff` 报「256 行全不同」，实际每个数都一样（`data-format.md` 第 1 条）

**三者的排查方法一模一样：先别怀疑逻辑，先看比值 / 看字节。**
恒定比值 = 约定问题；杂乱比值 = 功能问题。
