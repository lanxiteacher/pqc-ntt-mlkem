# 数据文件的编码与行尾

跨平台协作里最容易出事的一类，而且**症状全都长得像「算法错了」**。

---

## 1. `diff` 报「256 行全不同」，但每个数其实都对

**现象**

拿参考实现算出的期望值跟黄金向量 `diff`，报 `1,256c1,256` —— 256 个系数**全不同**。
肉眼看两边的数字，一个不差。

**原因**

Windows 上 `fopen(..., "w")` 会把 `\n` 翻成 `\r\n`。作者的测试数据是 LF，
参考实现吐出来的是 CRLF，于是每一行的**行尾**都不同，`diff` 按行比就全不同。

**怎么修**

写文件用 `"wb"`（二进制模式）而不是 `"w"`，强制写 LF。

**怎么预防**

1. **不要用 `diff --strip-trailing-cr` 遮掩** —— 那只是把问题藏起来，
   仓库里两种行尾仍然并存，下次换个工具又炸。
2. 仓库层加 `.gitattributes`，内容是 `* -text` —— **不做任何行尾转换，存什么取什么**。
3. ⚠️ **不要**改成 `text=auto` 或 `eol=lf` —— 那两种都会**改写字节**。
4. ⚠️ **不要用「网页上下载 → 编辑 → 上传」改仓库里的文件** ——
   那条路**绕开了 `.gitattributes` 这道防线**，Windows 编辑器写出的 CRLF 会原样进仓库。

**为什么必须堵住**：Git for Windows 默认 `core.autocrlf=true`，
会在 **checkout 时**把 LF 改写成 CRLF —— 等于让**每个队友重踩一遍**这个坑。

**怎么发现的**

按照「diff 结果和肉眼观察矛盾」这条线索查的 —— **只要 diff 说全不同、
肉眼说全一样，先去看行尾，不要去看算法。**

**谁扛**：人（一行 `.gitattributes` 的事，但要知道有这件事）

## 2. 同一种数据，仓库存的是 CRLF

**现象**

同一批 `.hex` 向量，`research/` 下的是 CRLF（每行 5 字节），
`refsim/batch/` 下的副本是 LF（每行 4 字节）。字节数差 20%。

**原因**

两批文件是**不同工具、不同时期**生成的：原件由 C 程序用 `"w"` 写出（CRLF），
副本由 Python 脚本重写（LF）。`.gitattributes` 的 `* -text` 保证**两边都按原样入库** ——
它**不**负责统一行尾，只负责不篡改。

**怎么修 / 怎么预防**

- **读进来先 `trim()` 再用**，不要假设行尾。`split('\n').map(s => s.trim())` 两种都吃得下。
- 需要**逐字节比对**时（比如核对副本没被改花），先把两边都去掉 `\r` 再比，
  并在注释里写明「原件是 CRLF、副本是 LF，差异只在行尾」。
- 新增的跨平台数据文件一律 LF（见第 1 条）。

**怎么发现的**

对拍时发现两个文件「内容相同但 `diff` 不同」，用 `od -c` 看了前 8 个字节才看清。

> ⚠️ 顺带一个教训：**别用 `grep -c $'\r'` 判断行尾**。本项目里对纯 LF 的文件
> 它也报「4096 行命中」，误导过一次。**用字节数或 `od` 判断**，那才作数。

**谁扛**：人

## 3. 十六进制不补零

**现象**

53 个批量向量文件里，23 个有**变长行**（`27` 而不是 `027`，共 1290 行）。
按字符串逐行比的工具碰上它们，会出现「同一个数，一边 `027` 一边 `27`」的假失败。

**原因**

生成脚本用了 `%x` 而不是 `%03x`。

**怎么修**

生成端统一 `%03x`（小写、补齐 3 位）。已有的脏文件**不要顺手改** ——
它们属于**已冻结的黄金向量**，改动要单独议（见「预防」第 3 条）。

**怎么预防**

1. 定格式时就把**行格式**写死：**每行恰好 3 位小写十六进制 + LF**。
2. 加一个格式校验脚本（`../scripts/check_data_format.sh`），
   跑一次就能列出所有不合规的文件与行号。
3. ⚠️ **格式校验发现的问题不要自己修**。先分清「这只是没补零」还是
   「这个值真的不同」—— 前者是格式问题，后者是数据问题，处理方式完全不同。
   而且**已冻结**的向量文件改一个字节都要两边知情。

**怎么发现的**

写批量对拍工具时，按「逐行比字符串」实现，结果对干净文件全过、
对某些文件零星失败。全扫一遍 53 个文件才定位到变长行。

**谁扛**：AI 能写校验脚本；**决定改不改要人**

## 4. 非 ASCII 的源码与文档（GBK）

**现象**

解压出来的 Verilog 源码和 readme 在编辑器里是乱码；本机**没装 `iconv`**。

**原因**

上游资料是 GBK（936 码页）编码，工具默认按 UTF-8 读。

**怎么修**

PowerShell 指定码页读：

```powershell
[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::GetEncoding(936))
```

**怎么预防**

- 自己的产出**一律 UTF-8**。
- 处理第三方资料前，先拿 `od -c` 或 `file` 看一眼编码，别默认 UTF-8。

**谁扛**：人

## 5. 数值口径没写清，两边「都对但不一样」

**现象**

同一个多项式，一边显示 `0..3328`，另一边显示 `-1664..1664`，
值本身能对上（差一个整数倍的 q），但对拍工具判 256/256 全错。

**原因**

一边是**规范代表**（canonical，`0 ≤ x < q`），一边是**中心代表**
（centered，`-(q-1)/2 ≤ x ≤ (q-1)/2`）。两者**同余**但**不相等**。
硬件/软件的口径不同是常态，不是 bug。

**怎么修**

**在文档里显式写出口径**，并在对拍工具里按同一口径归一化后再比。

**怎么预防**

定格式时**连带把口径一起定**，别只定「怎么写十六进制」。
本项目的口径写在各向量的说明文件里（例如「所有系数均为规范形式 `[0, q)`」）。

**怎么发现的**

对拍全错时**先算比值**：如果逐系数的比值只取一个值（不是几百种随机值），
就说明逻辑没错、只差一个全局常数 —— 这是 `verification.md` 第 4 条那套方法。

**谁扛**：人（AI 会「几乎写对」，但口径是你定的）

## 6. 输出位数：`& 0x0FFF` 之后还要补零

**现象**

输出值本身对，但十六进制位数不齐（`a3` vs `0a3`），下游按固定宽度解析就错位。

**原因**

只做了 `& 0x0FFF` 掩码，没做宽度补齐。

**怎么修**

打印端固定 3 位：`%03x`（C）/ `toString(16).padStart(3, '0')`（JS）。

**怎么预防**

把「**掩码 + 补零**」当成一个整体写进格式约定，别只写一半 ——
只有掩码不补零 = 第 3 条那个坑。

**谁扛**：AI 可写，**人验**
