# 验证方法学：怎么才算「验过了」

这个文件里的每一条，都是「本来以为验过了，其实没有」的实例。

---

## 1. 「验证通过」必须配「非退化」才作数

**现象**

灌进 16 组向量，报 `4096/4096 全中`。看上去完美。
但如果向量全是 0、全是常量、或者只有几个不同值，「全中」**可能只是巧合** ——
比如一个把输入原样输出的 RTL，在全零向量上也能 4096/4096。

**原因**

「对上了」只说明两边一致，**不说明这个测试有区分度**。

**怎么修**

灌数据前先统计**输入里有多少个不同的值**，以及**最常见值的占比**。

**怎么预防**

把非退化统计**写进验证脚本**，每次跑都打出来。本项目现有基准：

| 向量集 | 行数 | 不同值 | 最常见值占比 |
|---|---|---|---|
| 16 组 × 256 系数 | 4096 | **2355 ~ 2374** | < 0.25% |

**新造的向量至少要达到这个量级**（4096 个系数里 2300 多个不同值、最常见的一个占 0.2%）。
这种熵下「全中」不可能是巧合。

**怎么发现的**

在验证脚本里加了这一条统计之后，才敢说「通过」——
在此之前，「全中」这个词是没法用的。

**谁扛**：人（这是判断标准，不是代码）

## 2. testbench 里不要写无界 `while (done == 0)`

**现象**

单次跑没事；套进 16 轮循环之后，**任何一轮异常都会让仿真永久挂死**，
而不是报错退出 —— 跑批脚本等到超时被杀，看不出是哪一轮、什么原因。

**原因**

上游作者的原始 testbench 就是无界的 `while(done == 1'b0)`。
单次执行时「挂住」和「等一会」看不出区别，放进循环就变成灾难。

**怎么修**

加计数护栏：

```verilog
parameter TIMEOUT = 5000;          // 正常一轮用不到 1000 拍
integer guard = 0;
while (done == 1'b0 && guard < TIMEOUT) begin
    @(posedge clk); guard = guard + 1;
end
if (guard >= TIMEOUT) $display("❌ 超时");   // 报错并继续，不卡住
```

**怎么预防**

**改别人的 testbench 时，第一件事就是找无界等待。**
把「有没有无界等待」写进 code review 清单。

**谁扛**：AI 可写，**人必须验**

## 3. 对拍前先确认比的是哪一个函数

**现象**

拿参考实现的 `poly_ntt()` 输出当期望值，去比硬件/裸 `ntt()` 的输出，
一直报失败，怎么看都「差一点」。

**原因**

`poly_ntt()` = 裸 `ntt()` **+ `poly_reduce()`**，两者输出**不相等**
（差一次代表归一化）。名字相近、语义不同。

**怎么修 / 怎么预防**

**对拍前先把两边各自调用的是哪一层函数写下来**，
并确认它们处在同一层。宁可多花两分钟确认，也不要用「调一调试试」的方式逼近。

**谁扛**：人

## 4. 对拍全错时，先算比值，别先怀疑逻辑

**现象**

16 组全部 `0/256`。看着像 RTL 坏了。

**原因**

**两侧对「这个函数的输出该不该带 Montgomery 因子」的理解不一样。**
硬件侧和参考实现侧的域约定不同是常态：

| 运算 | 硬件输出与参考实现的关系 |
|---|---|
| 逆变换 INTT | 硬件 = 参考实现 × **R⁻¹**（真逆变换，无 tomont 缩放） |
| 点乘 PWM2 | 硬件 = 参考实现 × **R**（少一级 Montgomery 归约） |

（`R = 2¹⁶ mod q`）

**怎么修**

**不看「通不通过」，改看比值**：逐系数相除，看比值集合有多大。

- **比值集合大小为 1**（不是几百种随机值）→ 逻辑没错，**只差一个全局常数因子**
  → 是约定问题，去找那个因子
- **比值杂乱** → 是功能问题，去查逻辑

这一步同时排除了「点乘被误当成逐系数乘法」这类**真正的功能错误**。

**怎么确认这个因子不是自我安慰**

配一条**不经过参考实现**的往返自检：把硬件的正变换**实际输出**
灌回硬件的逆变换，要求回到时域原值。这条路径不经过「我标的那个定标因子」，
所以骗不了人。

**怎么预防**

把两边的关系式**显式写进文档**，并在生成期望值时明确写下乘了几个常数。
**不要猜。**

**谁扛**：人（理解概念）；写脚本是 AI 的活

## 5. 「跑通了作者的 testbench」什么也证明不了

**现象**

作者的 testbench 打印 `Correct!`，但那只说明**作者的期望输出**和**作者自己的 RTL** 一致。

**原因**

这是**自洽**，不是**正确**。万一作者的期望值本身就错了
（twiddle 表排错、域约定选错），testbench 照样打印 `Correct!`。

**怎么修**

搭一条**独立**的验证链，终点是**外部标准**：

```
国际标准测试向量（官方 KAT）
        │  独立复算，逐比特
        ▼
参考实现（自己编译的官方实现）  ←── 从此它是"地面真值"
        │  复算作者给的输入
        ▼
作者的期望输出  ── 逐比特一致
        │
        ▼
作者的 RTL  ── 逐比特一致（自己的向量，16 组）
```

**中间那一环很关键**：作者的期望输出与参考实现逐比特一致，
**既证明作者的数据没错，也证明我们对参考实现的理解（域约定、输出顺序）
和作者一致** —— 否则后面拿自己的向量去灌 RTL，顺序对不上会**假报失败**。

**怎么预防**

**任何「验证」都要先问：终点是外部标准，还是自己跟自己对？**

**谁扛**：人（设计验证链）；脚本 AI 可写

## 6. 一个永远通过的测试没有价值 —— 要配阴性对照

**现象**

`4096/4096` 全过。但**这个测试到底测不测得出错**，不知道。

**怎么修**

**故意改坏一个期望值，看它抓不抓得到。** 实测：

```
# 把第 7 组第 100 号系数改掉，重跑
向量  7 [100]: 期望 001 得到 3d4
向量  7: ❌ 255/256
✗ 共 1 个系数不符
```

**恰好 1 个不符、位置正确**，而且硬件报出的 `3d4` 正是原值
—— 说明硬件是对的，**测试也确实能把错抓出来**。

**怎么预防**

阴性对照要做两件事：
1. **能抓到**（改了必须报错）
2. **只抓到那一处**（不多不少，说明定位准确）

本项目另外两处阴性对照：
- 装载顺序拨错 → 命中率**塌到 ~22/4096**（= 随机命中），证明「顺序判据」有区分度
- 换成劣化配置 → 多重集不再相等

**谁扛**：人（想到要做）；执行 AI 可写

## 7. 动手「复现」某个东西之前，先确认它存在

**现象**

花了大功夫重建一张逆变换用的 twiddle 表（`zetas_inv`），
建完发现**正逆变换本来就共用同一张表**，只是遍历方向相反。

**原因**

「逆变换应该有自己的常数表」是个**听起来很合理**的假设。

**怎么修 / 怎么预防**

**动手前先搜一遍：这个东西在参考实现里到底有没有。**
`grep -rn "zetas_inv" .` 一条命令的事。
**「合理的假设」不是「事实」** —— 这类问题在 AI 生成的方案里尤其常见，
因为 AI 会顺着你的假设往下写。

**谁扛**：人（花 30 秒搜一下，省半天）

## 8. 写「验证通过」时必须把覆盖边界一起写

**现象**

报告里写「RTL 已验证」，被追问「验到哪一层」时答不上来。

**怎么修**

**边界列成明确清单**，例如本项目：

- 验到「**一次多项式乘法**」为止，**不是**「一次 ML-KEM 运算」为止 ——
  更外层的向量累加点乘、base case 乘法、末级归位**尚未验**
- 单运算那一层的期望值**依赖常数因子换算**（有往返自检背书）
- **只验了一种并行度配置**，多路并行版本没验
- **只做功能验证，没验面积 / 时序 / 功耗**
- 上游自带的测试数据只对了 2 组，样本量小

**把边界写清楚是加分项，不是减分项。** 只写「通过」不写「没覆盖什么」，
被追问时会很被动。

**怎么预防**

验证链画出来之后，**在旁边单独列一栏「这条链没覆盖什么」**，
每加一条验证就补一次。

**谁扛**：人

## 9. 「多重集相等」弱于「逐位置相等」

**现象**

报「4096/4096 全中」，但换一种数据顺序也能全中。

**原因**

判据是**多重集**相等（256 个值的集合对上了），**不含顺序**。
顺序错误在多重集判据下看不出来。

**怎么修 / 怎么预防**

**把「值对不对」和「顺序对不对」拆成两条判据**，互不污染：

- 第 1 条：多重集相等 → 只证明「算出来的 256 个值都对」
- 第 2 条：读出顺序 → 单独量、单独定

这样任何一条失败，都能立刻知道是**算错了**还是**读错了**。
混在一起判，会得到一个「不知道哪里错」的失败。

⚠️ 而且顺序**可能随配置变**（本项目里正变换的读出顺序随折叠度变），
所以「顺序判据」必须**逐配置**验，不能验一档套全档。

**谁扛**：人（设计判据）
