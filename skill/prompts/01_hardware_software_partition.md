# 提示词 ①：从算法描述推导软硬划分

**用途**：拿到一个要加速的算法，用 AI 帮你划分「哪些放硬件、哪些留软件」，
**并且把划分的理由说清楚**（而不是只给一张表）。

---

## 适用范围

**能用**：算法有明确的「固定结构」可被并行/流水化（数字信号处理、密码学、
矩阵运算、卷积……）；**且你知道自己的评分/考察标准是什么**。

**不能用**：
- 算法的开销主要是**数据相关的控制流**（搜索、图遍历、语法分析）——
  这类本来就难放硬件，模板里的二分法给不出有力判断；
- **评分标准未知或不可说**时，第 4 条会问不出东西（但前三条仍然有用）。
- ⚠️ **不要用它来定常数表。** 第 3 条只要求它**指出出处**，
  数值仍然要人从源码里抄（见 `../checklists/ai-collaboration.md` 第 1 条）。

---

## 怎么用

把 `<尖括号>` 里的内容换成你的项目，整段发给 AI。**一次提问，按顺序回答**。

```
我在用 <平台/器件> 做一个 <什么> 的加速项目，要加速的算法是 <算法名>。
先不要给方案，按顺序回答这四条：

1. 这个算法里，哪些步骤是「数据无关的固定结构」（适合硬件：流水 / 并行 / 查表），
   哪些是「数据相关的控制流」（不适合硬件）？逐步骤给理由。

2. 对每个步骤说明：放硬件要做成什么形态（状态机 / 流水线 / 查表），
   放软件的话留在哪一侧，以及这个选择的代价是什么。

3. 列出这个算法里所有**必须查表**的常数。对每一个，
   告诉我它在 <参考实现路径> 里对应哪个文件、哪个函数，
   **不要凭记忆给出具体数值**。

4. 最后一条，也是最重要的一条：以 <评分/考察标准原文> 为准，
   上面这个划分合理吗？如果这个标准看重的是 <A 类能力>，
   而不是 <B 类能力>，划分该往哪边偏？把偏过去的代价也说出来。
```

**第 4 条是关键。** 前三条任何一本教材都能给；第 4 条是**把你的评分标准喂进去，
让划分服从标准**。很多项目在这一条上会翻转结论。

---

## 期望得到什么

- 一张步骤级的划分表 + 每个选择被放弃的那一侧的代价
- 一张「常数表 → 源码位置」的对照（**用来去抄，不是用来抄它给的数**）
- 一段「按标准，该往哪边偏」的判断

---

## 本项目的实例（这是它产生实际影响的唯一一处）

**背景**：团队最初按工程直觉，把方案定成「PL 算核 + 处理器侧轻量协同」，
理由大致是「纯硬件不够灵活、协同更现代」。

**第 4 条问出来的结果**：把评分标准原文（初级组的考察侧重
= **逻辑设计、状态机、时序约束、接口协议**）喂进去之后，结论翻了 ——
**「软硬协同」是高级组的加码项，不在本组的考察面上**；
而且走处理器侧协同**会主动削弱考察面**：
状态机与接口协议从硬件挪进 C 代码，等于**把评委要看的东西藏起来**。

**最后定成纯硬件实现**，理由不只是「风险小」，而是
「纯硬件正好命中四个考察侧重」：
逻辑设计 = 可配置的运算核；状态机 = 串口协议解析；时序约束 = 引脚约束 + 收敛 + 频率数据；
接口协议 = 串口协议本身。

> **从哪个失败里总结的**：一个「听起来更现代、更专业」的划分，
> 在**不看评分标准**的情况下是查不出来的。
> 而看漏这一步的代价是**整条实现路线选错**，返工成本极高。

---

## 失效条件

| 什么时候不管用 | 为什么 |
|---|---|
| 评分标准不公开 | 第 4 条失去输入，退化成「通用工程建议」 |
| 算法本身以数据相关控制流为主 | 「固定结构 vs 控制流」这个二分给不出有力答案 |
| 想用它省掉读源码 | 第 3 条只让它**指路**；常数数值仍须人从源码抄 |
| 已经定了划分、只是想找个理由 | 第 4 条会给你**反过来的**理由，这正说明它没在迎合你 |
