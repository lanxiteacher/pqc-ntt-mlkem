## 每条模板的固定骨架

每条都写清五件事 —— 缺任何一件，别人拿去就会用错：

```
适用范围     —— 什么情况下能用
不能用       —— 明确写出反例（比「适用」更有用）
使用方法     —— 可直接复制的提示词原文 + 怎么填
期望得到什么 —— 输出的形状，方便判断「它答歪了没有」
失效条件     —— 什么时候它会给你看似正确实则有害的答案
```

外加一段 **`本项目的实例`**：这条提示词在我们这儿问出了什么、
**从哪个失败或观察里总结的**。

## 为什么用「模板」而不是「提示词技巧」

一条好提示词的形状，取决于**任务的结构**，不取决于措辞。
这四条的共同结构是：

> **把「判断标准」喂进去，并要求把「依据」写出来。**

- ① 把**评分标准**喂进去 → 划分要服从标准，不服从工程直觉
- ② 把**设计层次 + 日志**喂进去 → 瓶颈要归因到报告里的证据，不能是形容词
- ③ 把**代码本身**喂进去 → 解释要落到「改一个字符会怎样」
- ④ 把**出处要求**喂进去 → 每个数可追溯，拿不出来就写「未报告」

**「请务必准确」这类话没有用**；给一个**具体的、能做到的动作**才有用
（比如 ④ 里「拿不出出处就写『未报告』」—— 它给了模型一个不掉分的出口）。

## 一条通用的反问

不管用哪条模板，AI 答完之后都值得再问一句：

```
上面这段里，哪些是事实、哪些是推断？推断的部分，
要跑什么 / 查什么才能变成事实？
```

本项目两次「格式完美但事实错误」都是被这一问拦下来的
（详见 `../checklists/ai-collaboration.md` 第 5 条）。
