## 每项的四件套（《选题指南》§3.3.5.2）

指南要求**每一项**写明 **适用场景 / 使用方法 / 失效条件 / 已验证的效果**，
并说明**是从哪些失败或观察中总结得出**。逐项对照如下；
「从哪总结」写在每条文件内的 `本项目的实例` 段（表中末句「从哪来」即指它）。

| 项 | 适用场景 | 使用方法 | 失效条件 | 已验证的效果 |
|---|---|---|---|---|
| ① 软硬划分 | 算法有**固定可并行结构**（DSP/密码学/矩阵/卷积…），**且评分或考察标准已知** | 把 `<尖括号>` 换成你的项目、整段发给 AI，**按顺序答**；第 4 条把评分标准喂进去是关键 | 评分标准不公开（第 4 条失去输入）；算法以**数据相关控制流**为主 | **本项目在它上面翻转了整条实现路线**：第 4 条把「初级组考察侧重」喂进去后，结论由「PL 算核 + 处理器侧协同」改为**纯 PL**（协同是高级组的加码项）。从哪来：`01_*.md` §本项目的实例 |
| ② 报告定瓶颈 | 手上有**同一器件、同一约束、同一实现阶段**的一组报告，且能说清设计层次 | 附报告 + **日志** + 设计层次说明，按 5 条顺序问；第 3 条要求每个建议带**验证方法** | 混不同实现阶段 / 不同器件；**只给报告不给日志** | 三档并行度的报告归因出「延迟约 **70% 是布线**、逻辑仅 9–10 级」；第 5 条抓出 `Design State : Fully Placed` 与日志矛盾（布局其实已失败）。数字核对见 `../../rtl/vivado/critical_paths.md` |
| ③ 讲懂自己的代码 | AI 写了、**你要对结果负责**的代码，尤其**要答辩 / 交接 / 长期维护**的 | 贴代码，按 4 条问；**第 4 条只出题不给答案** | 自己没看过代码；想靠它补**架构层**的理解（它只解释这段代码） | 第 2 条抓出成对脆弱点 `i16` / `fqmul` —— 改错则**静默给出错误结果**（第 7 层全错却不报错），就此守住；第 3 条的人话说明直接进了报告。从哪来：`03_*.md` §本项目的实例 |
| ④ 每个数有出处 | 任何让 AI **汇总数据 / 做对比表 / 写指标表**，**尤其格子多又整齐的表** | 贴上含「**未报告**」出口的 5 条规则，**每做一张新表重贴一次** | 出处本身是二手的（PDF 抽取 / 转述）；数据源**单位不一致** | 拦下两处「格式对、事实错」：① 编造了整列 FF（源表根本没这列）→ 全部改「未报告」；② 把 `fqmul(zeta,b)` 写成 `zeta×b`。并派生「**表由脚本生成**」的做法（`../../metrics/gen_metrics.mjs`）。从哪来：`04_*.md` §本项目的实例 |

## 每条模板的固定骨架

每条都写清五件事 —— 缺任何一件，别人拿去就会用错：

```
适用范围     —— 什么情况下能用
不能用       —— 明确写出反例（比「适用」更有用）
使用方法     —— 可直接复制的提示词原文 + 怎么填
期望得到什么 —— 输出的形状，方便判断「它答歪了没有」
失效条件     —— 什么时候它会给你看似正确实则有害的答案
```

外加一段 **`本项目的实例`**：这条提示词在我们这儿问出了什么、
**从哪个失败或观察里总结的**。

## 为什么用「模板」而不是「提示词技巧」

一条好提示词的形状，取决于**任务的结构**，不取决于措辞。
这四条的共同结构是：

> **把「判断标准」喂进去，并要求把「依据」写出来。**

- ① 把**评分标准**喂进去 → 划分要服从标准，不服从工程直觉
- ② 把**设计层次 + 日志**喂进去 → 瓶颈要归因到报告里的证据，不能是形容词
- ③ 把**代码本身**喂进去 → 解释要落到「改一个字符会怎样」
- ④ 把**出处要求**喂进去 → 每个数可追溯，拿不出来就写「未报告」

**「请务必准确」这类话没有用**；给一个**具体的、能做到的动作**才有用
（比如 ④ 里「拿不出出处就写『未报告』」—— 它给了模型一个不掉分的出口）。

## 一条通用的反问

不管用哪条模板，AI 答完之后都值得再问一句：

```
上面这段里，哪些是事实、哪些是推断？推断的部分，
要跑什么 / 查什么才能变成事实？
```

本项目两次「格式完美但事实错误」都是被这一问拦下来的
（详见 `../checklists/ai-collaboration.md` 第 5 条）。
