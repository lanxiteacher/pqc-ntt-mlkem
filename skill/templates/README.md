# templates —— 工程骨架模板

「下一个题目可以直接套用」的东西。同样一件事**第一次做的时候是踩坑，
第二次做的时候应该是抄**。

## 索引

| 模板 | 用途 | 可直接跑吗 |
|---|---|---|
| [`vivado_nonproject.tcl`](vivado_nonproject.tcl) | 非工程模式：综合→优化→布局→布线，出资源与时序报告 | 改参数即可跑 |
| [`batch_testbench.v`](batch_testbench.v) | 批量对拍 testbench 骨架（16 组向量循环） | **有 TODO 占位，需填** |
| [`run_checks.sh`](run_checks.sh) | 一键验证脚本骨架（相对路径定位 + 工具预检 + 汇总） | **有 TODO 占位，需填** |

> ⚠️ 后两个是**骨架**，`TODO` 处要换成你自己设计的端口与命令。
> 本仓库所在的机器上没有 iverilog，**`batch_testbench.v` 没有编译验证过** ——
> 套用时先用一个最小例跑通，再往上加。

## 三个模板各解决什么

### `vivado_nonproject.tcl` —— 「量数字」而不是「上板」

**非工程模式**（不建 `.xpr`、不写 bitstream、不加引脚约束），
一条命令拿到资源与时序报告。选型、对比、优化前后对照都用它。

里面固化了几条容易忘的：

- **综合选项一律默认** —— 加了开关，你的数字就没法跟别人（论文、基线）对比了
- **`place` / `route` 分开 `catch`** —— 器件装不下时仍要拿到综合后的报告，
  不能让脚本整个崩掉、什么都不留
- 打 `RESULT <tag> WNS_NS <值>` 机读摘要行，外层用 `grep` 取数，
  不必为了一个数字整份读日志
- 文件头写了**两个环境雷区**：路径含撇号让综合引擎崩掉（要从仓库外启动）、
  综合子进程间歇性报「文件读不到」（要重试，**且重试前先删旧报告**）

### `batch_testbench.v` —— 三件「不知道就会卡半天」的事

1. **等 `done` 用有界循环**。上游写的是 `while (done == 1'b0)`，无界；
   套进 16 轮循环后，任何一轮异常都会让仿真**永久挂死**而不是报错退出。
2. **报错带下标、期望值、实际值**（`向量 7 [100]: 期望 001 得到 3d4`），
   这样也便于做**阴性对照**：改坏一条期望值，看它能不能恰好抓一处。
3. **灌/读顺序要写进注释** —— 那不是笔误，通常是存储器分 bank 交织的结果；
   而且**不同运算、不同并行度的顺序可能不同**，照抄会得到「256 个系数全错」的假失败。

文件末尾另附三条**验证方法学**要求（非退化统计、阴性对照、
别只拿「作者自带的期望值」当判据）。

### `run_checks.sh` —— 「别人 clone 下来第一条要跑的」

把「找文档 → 复制命令 → 改路径」变成一条命令。要点：

- **`$(dirname "$0")` 定位自己，不写死绝对路径**（每个人仓库路径不同）
- **`( cd ... && ... )` 包住 `cd`**，不让它影响调用者
- **工具预检要真跑一下，不能只看 `command -v`** ——
  PATH 里可能有占位符（命令存在但跑不通、退出码非零）
- **不用 `set -e`**：它在管道和条件里容易失效，而且会在**第一个**失败处退出，
  看不到后面还有哪些也失败了。逐个跑、逐个报，最后统一给结论
- 汇总行写死格式（`SUMMARY ALL_PASS`），既好 grep 又好扫一眼

## 抄这些模板时最容易抄漏的一条

三个模板都建立在一个共同习惯上：**把「踩过的坑」写进注释，而不是写进聊天记录。**

判断标准很简单 —— **删掉这条注释，下一个用的人会不会再踩一次？**
会，就写上；不会，就别写（注释不是日记）。

本项目里这条习惯的产物就是 `../checklists/` 那五份清单，
以及这三个模板文件头里那些「⚠️ 一开始直接传整串 `PE_NUMBER=4`，
Vivado 在 `=` 处切开了参数，报出来的错是『位选 [-1:0] 与声明不匹配』
这种看着像 RTL 写错了的错」的具体记录。
