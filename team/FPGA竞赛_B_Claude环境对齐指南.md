## 〇、一句话讲清"对齐"是什么意思

三个人最后要汇进**同一个 Gitee 仓库**。所以不存在"各写各的、最后合并"这一步 ——
**从第一天起，两台机器上就是同一套目录结构、同一套技术约定、同一套文件格式。**

本文规定的就是那三样东西。

## 一、先做这一步：拿到仓库

仓库发起人先在 Gitee 建一个**私有**仓库，把本目录的骨架推上去，然后把你加成成员。
你这边：

```bash
# 找一台放项目的机器，比如 D:\FPGA
git clone https://gitee.com/<发起人>/<仓库名>.git FPGA
cd FPGA

# 确认三样东西都在
ls CLAUDE.md .gitignore refsim/ team/
```

**关于联网**：仓库约 **26 MB**（最大的是 11.5 MB 的 `mlkem_kat/kat_MLKEM_768.rsp`），
第一次 clone 一两分钟。之后每次 `git pull` 只传增量。编译产物
（`*.exe` / `*.vvp` / `__pycache__/`）已被 `.gitignore` 排除，每台机器自己编。

⚠️ **`research/papers/` 不在仓库里**（47 MB 论文 PDF，版权属于各出版方，
而本仓库最终要按竞赛要求转公开）。clone 下来你不会有这个目录 ——
**这不影响复现**，复现靠 `refsim/` 的脚本 + `mlkem_kat/` + `kyber_ref/`。
要看论文找 B 单独发（群文件/网盘）。

⚠️ **行尾被 `.gitattributes` 锁死了：`* -text`，不做任何转换。**
不要把它改成 `text=auto` 或 `eol=lf` —— 那两种都会在 checkout 时改写字节。
Git for Windows 的安装器默认把 `core.autocrlf` 设成 `true`，一旦生效，
clone 出来的 `refsim/batch/*.txt` 会**全变成 CRLF**，而参考实现外壳是用
`"wb"` 写 LF 的 —— `diff` 就会报"256 行全不同"（数值却一个不差）。
正是第四节第 1 条那个坑，只不过这次是 git 自动造的。

```bash
git pull          # 每次开工前先拉
```

### 两条硬规则

**1. 目录名一律英文。**
竞赛要求提交的开源仓库目录名纯英文。现在就叫英文，是为了避免最后
"把中文目录改名 → 所有脚本路径全断 → 重跑一遍验证"这个返工。
**文件名可以中文**（`logs/FPGA竞赛_项目记录.md` 这种），但**新建目录必须是英文**。

**2. `research/` 是只读的。**
任何对基线 RTL 的修改都在 `refsim/pe1/` 的**副本**上做，原始目录保持原样。
理由：验证的说服力来自"我改了什么"能说清楚；原件被改过就说不清了。

三个人对不上的时候，返工成本比一开始商量高得多。

## 四、技术约定（每条都踩过坑，不是预防性建议）

### 1. 跨平台数据文件统一 LF 行尾，写文件用 `"wb"` 不用 `"w"`

Windows 的文本模式会把 `\n` 翻成 `\r\n`。踩过的坑：256 个系数数值**一个不差**，
`diff` 却报 `1,256c1,256`（256 行全不同），白查半天。

```c
fopen(path, "wb")      // ✅
fopen(path, "w")       // ❌ Windows 上写出 CRLF
```

```python
open(path, "wb").write(...)   # ✅
open(path, "w").write(...)    # ❌
```

**不要用 `diff --strip-trailing-cr` 遮掩** —— 那是把症状藏起来，不是修好。

### 2. testbench 里不要写无界 `while (done == 0)`

作者原始 testbench 就是无界的。单次跑没事，套进 16 轮循环后，
**任何一轮异常都会让仿真永久挂死，而不是报错退出**。
现有批量 testbench 用 `parameter TIMEOUT = 5000` 做计数护栏。

### 3. "验证通过"必须配"非退化"才作数

灌数据前先统计有多少个不同值。向量全是 0 / 全是常量 / 只有几个不同值时，
"256/256 全中"很可能只是巧合。

现有基准：**每 4096 个系数里有 2355～2374 个不同值**，最常见值占比 < 1%。
你新造的向量至少要达到这个量级。`gen_batch_vectors.py` 里有现成的
`check_nondegenerate()`，照抄它的判据。

### 4. 对拍前先确认比的是哪一个函数

`poly_ntt()` = 裸 `ntt()` **+ `poly_reduce()`**，两者输出**不相等**。
比错了会一直假报失败。

同理，**RTL 的域约定和 C 参考实现不同**，直接拿参考实现的输出当期望值会得到
"256 个系数全错"的假失败。差异因子必须显式写出来并交叉验证，不能猜。
（现有做法见 `refsim/gen_batch_vectors.py` 头部的约定表。）

### 5. 动手"复现"某个东西之前，先确认它存在

踩过的坑：曾花大力气重建一张根本不存在的 `zetas_inv` 表 ——
正逆变换共用同一张 `zetas[]`，只是方向相反。

### 6. 读出顺序不是笔误

RTL 的读出顺序 `0,2,1,3,4,6,5,7,...` 是 BRAM 分两 bank 交织的结果。
**而且 FNTT / INTT / PWM2 三个运算的顺序规则不一样** ——
照抄 FNTT 的读出循环去做 INTT，会得到 256 个系数"全错"的假失败。
具体规则写在 `refsim/pe1/intt_batch_tb.v` 头部注释里。

### 7. 路径一律相对仓库根写

脚本里用 `$(dirname "$0")` 定位自己，不要硬编码绝对路径 ——
两台机器的盘符和用户名不一样（本机路径里还有个单引号 `l'x`，很容易出问题）。

```sh
HERE="$(cd "$(dirname "$0")" && pwd)"
cd "$HERE"
REF="../research/kyber_ref"
```

## 五、验证链（这是 B 这块的全部价值所在）

```
   FIPS 203 KAT 向量集（1000 条）
              │  kat_verify.c 四项独立复算 → 1000/1000 通过
              ▼
   C 参考实现（research/kyber_ref/）  ←── 从此它是"地面真值"
              │
              ▼
   黄金向量  ── 灌进 RTL ── 逐比特对拍
              ▼
   ∴ 这份 RTL 符合 FIPS 203
```

**为什么不能只跑作者的 testbench**：作者的 testbench 是拿**作者自己给的期望输出**
去比**作者自己的 RTL**，只能证明自洽。万一作者的期望值本身就错了
（twiddle 表排错、域约定选错），照样打印 `Correct!`。

**怎么跑**（在 `refsim/` 下）：

```sh
sh run_fntt_check.sh          # NTT 全流程：编译参考实现 → 对拍作者数据 → 16 组向量灌 RTL
sh run_intt_pwm2_check.sh     # INTT + PWM2 + RTL 往返自检
sh run_ntt_layers.sh          # 打印并机器验证 twiddle 层序表
```

**覆盖边界的权威说明在 `refsim/README.md` §八** —— 它列出了"这条链没覆盖什么"。
报告里写"验证通过"时，边界要一起写。

## 六、文件互通格式（这一节是"互通"的核心）

下面这张表是 A 和 B 之间的接口。**格式变了要通知对方**，否则对方拿到的东西读不了。

| 契约 | 格式 | 谁定义 | 谁消费 |
|---|---|---|---|
| **黄金向量** | 每行一个十六进制系数，3 位小写、无前导零歧义、LF 行尾；每组 256 行，共 16 组 | **B** | A 灌 RTL 自测；C 做演示页 |
| **批量对拍数据** | `refsim/batch/<运算>_batch_in.txt` 与 `_exp.txt` | **B** | testbench `$readmemh` |
| **testbench 命名** | `refsim/pe1/<运算>_batch_tb.v`（如 `intt_batch_tb.v`） | **B** | A 复用 |
| **一键脚本命名** | `refsim/run_<运算>_check.sh` | **B** | 全员；也是开源仓库的复现入口 |
| **RTL 端口说明** | 端口名/方向/位宽 + 时序（什么时候 `start`、几拍出 `done`、两次运算要不要间隔） | **A** | B 照着写 testbench |
| **串口协议** | 波特率、命令字、数据帧格式、超时规则 | **A + B 共同冻结** | 两侧各实现一端 |

**三条注意**：

1. **上位机先对仿真跑通协议，再上板。** 仿真里都跑不通，上板只会更难查。
2. **串口协议 W2 必须冻结**（H3）。板子侧 A 写、PC 侧你写，不冻结一定对不上。
3. **端口说明到点没收到就主动要**（H1）。**不要自己猜时序** ——
   猜错了会误报"RTL 有 bug"，这个误报比多问一句贵得多。

## 七、纪律：两个人、两个 Claude、同一个仓库

这一节是新的。两个 Claude 同时改一个仓库，最贵的错误是**互相覆盖**。

1. **开工前先 `git pull`**，收工前 `git commit && git push`。别攒。
2. **只改自己主责的目录**（见第二节的表）。
3. **`CLAUDE.md`、`../logs/FPGA竞赛_项目记录.md`、`team/` 是共享的** ——
   要改先跟对方说一声，别两个 Claude 同时改同一份。
4. **一个能跑通的小步 = 一个提交。** 不做完不合并 ——
   保持仓库随时是可运行的，别让队友拿到跑不起来的东西。
5. **冲突了不要硬合、不要 force push。** 先停下来问。
6. **让 Claude 改共享文档前，先确认它读的是最新版**（`git pull` 之后）。
   两个 Claude 各自拿着一份过期的文档同时改，是最容易出事的情形。

## 九、卡住了怎么办

| 卡在哪 | 怎么办 |
|---|---|
| 对拍不通过 | 先确认**比的是哪一个函数**（第四节第 4 条）。域约定和读出顺序是两个高发区 |
| `diff` 报"全部不同" | 先怀疑行尾，别急着怀疑数值（第四节第 1 条） |
| 仿真挂死 | 检查有没有无界 `while (done == 0)`，加计数护栏 |
| 拿不到 A 的端口说明 | 主动要。同时可以先按 `refsim/pe1/` 里已有模块的时序风格写草稿 |
| 板子连不上 | 那是 A 的工位问题，别自己死磕 |
| 上位机对仿真跑不通 | 别急着上板 |
| 两个 Claude 改冲突了 | 停下来问，别硬合 |

**降级顺序**：上位机做不完就用仿真波形截图代替串口实测；
但**验证数据本身不能省** —— 它是"功能正确性 20 分"的载体。
