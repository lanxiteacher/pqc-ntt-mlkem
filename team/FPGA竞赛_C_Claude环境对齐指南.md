## 一、项目架构

### 1.1 一句话

**我们要做一块 FPGA 硬件，让它算 NTT 算得又快又省，并且证明它算得对。**

NTT 是后量子密码标准 ML-KEM 里最耗时的一步：拿 **256 个数字**，按固定规则
重排组合 **7 遍**，每遍把所有数字两两配对，每对做一次「一加一减、再乘个常数」
的动作（叫**蝶形**）。

### 1.2 三层结构（从上往下看）

```
┌─────────────────────────────────────────────────────────────┐
│  ① PC 上位机            host/                    【B 主责】  │
│     把 256 个数字喂给板子 → 收回结果 → 和标准答案自动比对      │
└───────────────────────────┬─────────────────────────────────┘
                            │ 串口（USB 线，CH340C，115200-8N1；COM 号会变）
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  ② 板子：正点原子领航者 ZYNQ  xc7z020clg400-2                │
│  ┌───────────────────────┐  ┌────────────────────────────┐  │
│  │ PS（ARM 核）           │  │ PL（FPGA 可编程逻辑）       │  │
│  │ 「轻量协同」：         │◄►│ ★ NTT / INTT / 点乘 加速核  │  │
│  │ 把 PL 的结果转发给 PC  │  │   这才是我们的作品本体       │  │
│  └───────────────────────┘  └────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
                            ▲
                            │ ③ 数字从哪来、怎么证明对 → 见 1.5 验证链
                            │    产物在 refsim/                 【B 主责】
```

**我们不碰 PS。** PS 是板子上那颗 ARM 处理器，PL 是我们写的硬件电路。
2026-09-29 定案：**纯 PL 实现** —— 串口收发、协议状态机、NTT 核全部用 Verilog 写。

依据 `选题指南.pdf` §3.3.1.1（PDF 第 19 页）：**初级组的考察侧重是「逻辑设计、状态机、
时序约束、接口协议等基本 FPGA 设计能力」**；「软硬件协同」写的是**高级组**的考察侧重
（原文：「在上述基础上**进一步**考察软硬件协同与器件整体性能的发挥」）。
（此前记的「3.3 明写考察软硬协同」是错的，09/29 已更正。）

> ⚠️ **现状：这一层还没通。** 上板是全项目**唯一没验过**的环节，
> 而初赛要交**实物演示视频**。这是 A 目前最紧的一件事。

### 1.3 PL 里面是什么（我们的作品本体）

以 `pe1`（最小配置）为例，`rtl/pe1/` 下的模块分成四类：

```
KyberHPM1PE_top.v          ← 顶层：把下面这个核包一层寄存器
└── KyberHPM1PE.v          ← 核本体
    ├─ 存储  BRAM.v        存 a、b 两个多项式（分两个 bank，读出顺序因此是交织的）
    │        BROM.v        存 twiddle 常数表（正逆变换共用同一张，只是方向相反）
    ├─ 运算  butterfly.v   蝶形单元：一加一减再乘常数
    │        modmul/modadd/modsub/modred/intmul  ← 模 q=3329 的各类算术
    │        FA.v / HA.v   全加器 / 半加器
    └─ 控制  addressgenerator.v   地址生成（决定每层怎么配对）
             shiftreg.v / dt0..3.v / div2.v   ← 各种延时与打拍
```

**顶层接口长这样**（`KyberHPM1PE_top.v`）：

| 信号 | 作用 |
|---|---|
| `clk` / `reset` | ⚠️ reset 是**异步高有效**；而板子的 `sys_rst_n` 是**低有效** —— 两者极性相反，上板时要处理 |
| `load_a_f` `load_a_i` `load_b_f` `load_b_i` | 把数据装进 BRAM（时域 / NTT 域两套入口） |
| `read_a` `read_b` | 读回结果 |
| `start_fntt` `start_intt` `start_pwm2` `start_ab` | 启动哪种运算（正向 NTT / 逆向 NTT / 点乘） |
| `din` / `dout` | 数据，位宽 = **12 × 蝶形数** |
| `done` | 算完了 |

### 1.4 折叠度：我们的主要卖点

**折叠度 = 一次并行算几个蝶形。** 写成参数 `PE_NUMBER`：

| 配置 | 一次算几个蝶形 | LUT | DSP | IOB（引脚） | 最高频率 | NTT 要几拍 |
|---|---:|---:|---:|---:|---:|---:|
| `pe1` | 1 | 808 | 1 | 37 | 168 MHz | 904 |
| `pe4` | 4 | 2190 | 4 | 109 | 163 MHz | 232 |
| `pe16` | 16 | 8450 | 16 | **397** | 158 MHz | 69 |

> 数据出处：`rtl/vivado/折叠度对比表.md`（Vivado 实测，2026-09-22）

**看出来了吗**：一次算得越多越快，但**引脚数线性增长**。
板子的芯片只有 **125 个引脚**，而 pe16 要 **397 个** —— **根本放不下**。

> ⚠️ 这是已实测出来的硬约束：想做可配置折叠度，**必须写成固定宽度接口 + 数据分拍送**，
> 不能随折叠度加宽接口。

**「折叠度可配置」就是我们「创新性 30 分」的主要卖点** —— 别人做死一个配置，
我们做成一个能调的旋钮。

**你要拿它做的东西**：演示页上的那张对比图，和报告里的「性能与资源」章节。

### 1.5 验证链（这是本仓库最值钱的部分）

凭什么说我们的硬件是对的？靠这条链：

```
   FIPS 203 官方考题（1000 条）      ← 美国国家标准局出的题
              │
              │  kat_verify.c 四项独立复算 → 1000/1000 全过
              ▼
   C 参考实现 research/kyber_ref/    ←── 从此它叫"地面真值"
              │                          （它对了，它说的就算数）
              │  用复算出的黄金向量灌进 RTL，逐比特对拍
              ▼
   ∴ 这份 RTL 的 NTT / INTT / 点乘 / 完整乘法 符合 FIPS 203
```

**当前结果**：NTT、INTT、点乘、完整多项式乘法，**各 4096/4096 个系数逐位一致**。

**为什么这条链值钱**：别的队伍只能写「仿真通过」。我们能写
「用 FIPS 203 标准的 1000 道考题验过，4096 个系数逐比特一致」——
这是**别人拿着能自己复算一遍**的硬证据。

**为什么不能只跑作者自带的 testbench**：那是拿作者自己给的期望输出去比作者自己的 RTL，
只能证明自洽。万一作者的表就排错了，照样打印 `Correct!`。

**你要拿它做的东西**：演示页里「对拍结果」那一页，和报告里的「功能正确性」章节。

### 2.3 两条关于仓库的硬事实

**① 行尾被 `.gitattributes` 锁死了：`* -text`，不做任何转换。**

不要把它改成 `text=auto` 或 `eol=lf` —— 那两种都会在 checkout 时**改写字节**。
Git for Windows 的安装器默认把 `core.autocrlf` 设成 `true`，一旦生效，
clone 出来的 `refsim/batch/*.txt` 会全变成 CRLF，而对拍就是靠**逐字节**
比出来的 —— `diff` 会报「256 行全不同」而数值一个不差。

**② `research/papers/` 不在仓库里。**

那是 47 MB 论文 PDF，版权属于各出版方，而本仓库最终要按竞赛要求**转公开**。
clone 下来你不会有这个目录 —— **这不影响复现**。
你要用（做相关工作对比表）就找 B 单独发（群文件/网盘）。

好消息：`research/kyber_ref/papers/*.txt` 里已经**抽出了对比数据**
（`out_table.txt` / `pq_table.txt` / `pqshield.txt` / `mdpi_v*.txt`），
这几个 `.txt` **在仓库里**，是你做相关工作表的第一手原料。

## 三、VSCode + Claude Code 怎么开工

### 3.1 装什么

| 装什么 | 怎么装 |
|---|---|
| **VSCode** | [官网](https://code.visualstudio.com/) 下载安装 |
| **Claude Code** | VSCode 里搜扩展 **Claude Code** 装上；或者不装扩展，用 VSCode 的**集成终端**（`Ctrl+~`）直接敲 `claude`。**两条路都行**，看你顺手哪个 |
| **Git** | [git-scm.com](https://git-scm.com/)，装完 `git --version` 能出版本号就行 |

### 3.2 打开方式（这一步做对了，后面都省事）

**把整个仓库目录当工作区打开**：VSCode → `文件` → `打开文件夹` → 选 `FPGA` 那个目录。

⚠️ **不要只打开 `demo/` 或 `docs/` 子目录。** 原因：

- 仓库根目录下的 **`CLAUDE.md` 会自动进入 Claude 的上下文** ——
  那里面写着全项目的规矩（行尾约定、别改 `research/`、多人协作纪律）。
  **你只打开子目录，Claude 就读不到它，你就会重复踩别人踩过的坑。**
- Claude 需要能读到 `refsim/` 和 `logs/` 才能帮你查东西。

### 3.3 每次开工的固定动作

```bash
git pull                                    # ① 先拉，别人可能刚推过
```

然后对 Claude 说（**第一句就这么说**）：

> 先读 `logs/FPGA竞赛_项目记录.md`，告诉我现在项目什么状态、我这周该干什么。

那份文件只有约 80 行，是专门为「读完就能开工」写的。
**让 Claude 先读它，比你自己翻一遍快。**

### 3.4 让 Claude 干活的四条习惯

**① 说清楚「做完看到什么算完成」。**
不要问「帮我把演示页做好」——太大，Claude 会给你一个你不想要的东西。
要问「做一个网页，输入 256 个数字，点一下走一层蝶形，数字用颜色标出变化的」。
**判据越具体，返工越少。**

**② 让它改文件前，先让它说一遍打算怎么改。**
它说对了你再让它动手。**它说错了，你省下的是一次白改。**

**③ 收工前让它提交。**

> 我这轮改了 `demo/index.html` 和 `docs/related-work.md`，帮我 commit 并 push，
> commit message 写清楚改了什么。

⚠️ 一个能跑通的小步 = 一个提交，别攒。**谁 push，钉钉群会自动弹通知**，
A、B 看到就知道该 pull 了。

**④ 卡住了就把原话贴给它，别自己转述。**
报错信息、你看不懂的那句话、页面上奇怪的显示 —— 原样贴。
**转述会丢掉关键线索。**

### 3.5 ⚠️ 一条最容易犯的错

**不要在 Gitee 网页上直接编辑文件再提交。**

网页编辑器**绕开了 `.gitattributes`** —— Windows 上写出的 CRLF 会原样进仓库，
然后 B 那边对拍就会报「256 行全不同」。
**要改文件，就在你本地的 VSCode 里改，然后 commit + push。**

## 六、技术约定（每条都有人踩过）

### 1. 跨平台数据文件统一 LF 行尾

Windows 的文本模式会把 `\n` 翻成 `\r\n`。踩过的坑：256 个系数数值**一个不差**，
`diff` 却报「256 行全不同」，白查半天。

**你写 Python 导出演示页数据时也一样**：

```python
open(path, "wb").write(...)   # ✅
open(path, "w").write(...)    # ❌ Windows 上写出 CRLF
```

**不要用 `diff --strip-trailing-cr` 遮掩** —— 那是把症状藏起来，不是修好。

### 2. 别用「网页下载 → 编辑 → 上传」改仓库里的文件

重复一次，因为这是你这块最容易犯的：**网页那条路绕开 `.gitattributes`**。
本地改，本地提交。

### 3. 目录名英文，文件名可以中文

只有这一条区别，别记反。

### 4. `research/` 只读

包括里面的论文汇编、基线 RTL、官方考题。
**你要引用它、读它、拿它的数据 —— 但不要改它。**

## 七、素材命名规范（你是这个目录的维护者）

**A、B 每完成一小步，应该把「截图/录屏 + 一句话说明」丢进 `assets/`。
他们会忘 —— 忘了你就去要。这不是打扰，是你工作的一部分。**

### 7.1 文件名格式

```
assets/YYYY-MM-DD_<谁>_<一句话>.<后缀>
```

例：

```
2026-09-22_A_折叠度三档Vivado实测对比表.png
2026-09-23_B_16组向量逐比特对拍全绿.png
2026-09-25_A_上板串口第一次收到数据.mp4
2026-09-28_C_NTT第一层蝶形动画.gif
```

### 7.2 五条细则

| 字段 | 规则 |
|---|---|
| `YYYY-MM-DD` | **素材产生那天**，不是补录那天。补录会毁掉时间线 |
| `<谁>` | `A` / `B` / `C`，**单个大写字母** |
| `<一句话>` | 中文，说清**「这张图证明了什么」**。不许写 `截图1` `未命名` `新建文件` |
| 后缀 | `.png` 静态图（截图／波形图／Vivado 报告截图）<br>`.mp4` 录屏<br>`.gif` 30 秒以内的短动效（能直接插进报告的那种） |
| 合法字符 | ⚠️ Windows 不允许 `/ \ : * ? " < > \|`，一句话里**一个都不能有** |

### 7.3 三条规矩

1. **别攒。** 攒到最后补不回来 —— 「对拍通过」那张截图是报告和视频里最有说服力的素材，
   而它只在那 10 分钟里存在过。
2. **存原始文件，不要只存进 PPT/Word。** 剪视频时要从原始文件取，从 PPT 里抠出来的图是糊的。
3. **素材不是只给视频用。** 报告配图、答辩 PPT、演示页的截图 —— 都从这里出。
   **一个素材至少被用三次**，所以命名要让人六个月后还找得到。
