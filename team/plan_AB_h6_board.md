## 一、这一趟为什么必须用新位流

`rtl/board/proto_fsm.v` **2026-10-07 18:36** 加了 `#RDY`：板子上电/复位后**不等命令**
自发一行

```
#RDY <ver> <build> <errs>
```

`<build>` 就是**折叠度**（`1` / `4` / `16`），三档校验和分别是 `*7c` / `*79` / `*4a`。

**它解的是什么问题**：折叠度是**编译进位流**的，命令里没有这个字段 ——
所以电脑端拿到 `#NTT` 时，**判断不了该用哪张读出序表**。三档里 pe1 是交织序、
pe4/pe16 是自然序，选错就是 256 个全错。

⇒ **烧 10-07 之前出的位流，一行 `#RDY` 都不会有**，B 的「自动认折叠度」这条路当场断掉。

⚠️ **「先开串口、后烧位流 / 按复位」这个顺序要保留。** 原因不是解析会挂
（B 的 `1df5625` 已经把它接住了），而是**只有这个顺序才收得到 `#RDY`**：
先烧位流、后开串口的话，它在串口打开的**之前**就发完了。

再确认一件事：**B 的代码能在真板子以外的环境里吃掉 `#RDY` 那一行**。
没有真板子时，让陪练多发一行 `#RDY` 来测（`host/src/fake_board.py`）。

> B 的 `1df5625` 已经把 `#RDY` 接住了：`host/src/host.py` 另立 `RDY_PREFIX` + `parse_rdy()`，

> 真板子以外的环境里也走得通。

## 四、见面当天（照顺序做，每步有判据）

### 第 1 步 三处硬件 —— 缺一条都表现为「看不到设备」

| 哪一处 | 怎么接 |
|---|---|
| **下载器** | 插**底板右侧的 14-Pin JTAG 座** —— ⚠️ `USB_UART` 和 `USB_SLAVE` 那两个口**都不能**下载 |
| **底板 P5** | 跳 **PL 档**：**3–5、4–6 短接** |
| **启动拨码** | **JTAG 档**：两位都 ON |

判据：无命令，插好拨好即可。**这一步不对，第 2 步一定报「看不到设备」，且现象只有这一句。**

### 第 2 步 扫链，确认下载器看得见

```bash
sh rtl/vivado/run_board_prog.sh scan
```

只扫 JTAG 链、**不烧任何东西**。判据：能扫到器件。过了再往下。

### 第 3 步 烧 pe1（**必须带 `BIT=`**）

```bash
ROOT="$(pwd)"
BIT="$ROOT/rtl/vivado/_runs/pe1/ntt_board.bit" sh rtl/vivado/run_board_prog.sh
```

- 烧之前脚本会把**档位戳**打出来（「这版是 peN」）—— **核一眼是不是 `1`**。
- ⚠️ **一定带上 `BIT=`。** `_runs/`（根）、`_runs/pe1/`、`_runs/pe4/`、`_runs/pe16/` 里
  **各有一份同名 `ntt_board.bit`**，裸敲读的是**根下那份** —— 那份是 **10-04 的旧 pe4**，
  **没有 `#RDY`**。更麻烦的是**它的档位戳也写着 `4`**，跟 `_runs/pe4/` 那份撞号 ——
  所以「核档位戳」这招**核 pe1（是不是 1）挡得住，核 pe4 会假绿**。
- 判据：日志里 `End of startup status: HIGH`。
- ⚠️ **位流掉电即失**，中途断过电就得重烧。

### 第 4 步 查串口号（核对用，不是输入）

```bash
powershell -NoProfile -Command "[System.IO.Ports.SerialPort]::GetPortNames()"
```

设备名 `USB-SERIAL CH340`，**115200-8N1**。⚠️ **COM 号会变**（见过 COM9、COM10）——
Windows 按「插在哪个 USB 口」现分配，**不要写死**。B 的 `board_run.py` 自己扫串口，
这一步是**核对**：`--list` 扫不到时，先看这里有没有设备。

### 第 5 步 先陪练，再真板子（B 跑）

```bash
python host/src/board_run.py --list
python host/src/board_run.py --loopback "#NTT 1"      # ① 陪练，一个硬件都不用
python host/src/board_run.py --build 1 "#NTT 1"       # ② 真板子
```

判据：**① 必须先绿**（理由见 §二）。

### 第 6 步 ★ H6 正题 —— 上位机接真板子

```bash
python host/src/board_run.py --build 1 --check "#NTT 1"
python host/src/board_run.py --build 1 --check "#PMUL NTT 1"
```

| 命令 | 期望 |
|---|---|
| `#NTT 1` | **256/256**；核跑 905 拍 = **18.1 µs** |
| `#PMUL NTT 1` | **256/256**（A、B 两个 bank 都装） |
| `--build 4` / `--build 16` | 先重烧对应档位再跑（**加分项**，见下） |

- ⚠️ **`--build` 必须与板子里烧的那一档一致。** 烧 pe4 却按 pe1 解包 → **256 个全错**，
  看着像 RTL 挂了。这是**响亮失败**，不会静默给出「看起来对」的答案。
- ⚠️ **`--loopback` 配 `--check` 必然全错** —— 陪练回的是文件序，不是 bug。
- 端到端耗时约 **0.18 s / 0.27 s**，**三档几乎一样** —— 那是**串口搬运**的时间，
  核本身只占 **0.010%**。**别读成「折叠度没生效」。**

> **加分（可选）**：`--build 4` / `--build 16` 各跑一遍 ——
> 那是「三档都验过」的**当面证据**，也是报告 §3.13 那几张表唯一的一次现场复核。
> 每次换档都要**重烧对应位流**。

## 五、出问题怎么办

| 症状 | 最可能的原因 | 怎么办 |
|---|---|---|
| 扫链扫不到设备 | 第 1 步三处硬件有一处不对 | 核下载器是不是插在 14-Pin 座；P5 跳线；拨码 |
| 烧进去了，但一条 `#RDY` 都没有 | 烧的是 10-04 的旧位流 | 回第 3 步，**带 `BIT=`** 重烧 |
| `--build` 给了，FNTT 还是 256 个全错 | 板子里烧的档位与 `--build` 不一致 | 核 `_runs/peN/ntt_board.pe`；重烧，或改 `--build` |
| 全部命令超时 | 串口开错口 / 波特率 / 板子没配置 | `--list` 看设备名；回第 2、3 步 |
| 综合报 `couldn't read file` | Vivado 2020.2 helper 抖动（已知） | 等脚本自己重试；连报 5 次才要人看 |
