## 二、**B** · 在自己机器上（一个硬件都不用）

```bash
python host/src/board_run.py --loopback "#NTT 1"        # ① 进 = 出（256 进 / 256 出）
python host/src/board_run.py --loopback "#PMUL NTT 1"   # ② 进 ≠ 出（512 进 / 256 出）
```

判据：**两条都必须绿**。

> ⚠️ **② 不能省 —— 2026-10-07 实测它就挂。** `#NTT 1` 走陪练是绿的，`#PMUL NTT 1` 走陪练
> **STOP**：它**恰好是唯一不暴露这个 bug 的一档**（256 进 256 出 ⇒ 三个 count 同值）。
> **只跑 ① 等于专挑不会失败的那一档。**

**为什么要先做这一步**：真板子上失败时，要能分清是**上位机的问题**还是**电气层的问题**。
陪练跑不通就是代码问题，跟板子无关。

再确认一件事：**B 的代码能在真板子以外的环境里吃掉 `#RDY` 那一行。**
没有真板子时，让陪练多发一行 `#RDY` 来测（`host/src/fake_board.py`）。

> B 的 `1df5625` 已经把 `#RDY` 接住了：`host/src/host.py` 另立 `RDY_PREFIX` + `parse_rdy()`，
> `host/src/board_run.py` 会打出 `build_src` —— **告诉你折叠度是「`--build` 显式给的」
> 还是「从 `#RDY` 认出的」还是「没收到、退回默认的」**。上面这条是确认这个机制在
> 真板子以外的环境里也走得通。

改完 → `git commit -F <UTF-8 文件>`（⚠️ **不要用 `-m`**，git 会把中文参数静默转码）→ `git push`。

### 第 2 步 · 烧位流 + 跑 `#PMUL NTT 1` —— **H6 的最终判据**

```bash
# ① 扫链（只扫，不烧）
sh rtl/vivado/run_board_prog.sh scan

# ② 烧 pe1 —— ⚠️ 必须带 BIT=，理由见下
ROOT="$(pwd)"
BIT="$ROOT/rtl/vivado/_runs/pe1/ntt_board.bit" sh rtl/vivado/run_board_prog.sh

# ③ 查串口号（核对用，不是输入）
powershell -NoProfile -Command "[System.IO.Ports.SerialPort]::GetPortNames()"

# ④ 验收
python host/src/board_run.py --build 1 --check "#PMUL NTT 1"
```

- 判据：`End of startup status: HIGH`，然后 **`#PMUL NTT 1` 256/256**。
- ⚠️ **先开串口、后烧位流 / 按复位。** 顺序不能反 —— **只有这个顺序才收得到 `#RDY`**
  （先烧后开的话，它在串口打开**之前**就发完了）。B 的 `1df5625` 已经把它接住了，
  这里要的不是「解析不挂」，是**那一行本身要能到**。
- ⚠️ **一定带上 `BIT=`。** `_runs/`（根）、`_runs/pe1/`、`_runs/pe4/`、`_runs/pe16/` 里
  **各有一份同名 `ntt_board.bit`**，裸敲读的是**根下那份** —— 那份是 **10-04 的旧 pe4**，
  **没有 `#RDY`**。更麻烦的是**它的档位戳也写着 `4`**，跟 `_runs/pe4/` 那份撞号 ——
  所以「核档位戳」这招**核 pe1（是不是 `1`）挡得住，核 pe4 会假绿**。
- ⚠️ **位流掉电即失**，中途断过电就得**重烧**（约 1 分钟/档）。
  磁盘上的 `.bit` **不会消失**，**不需要重出**（重出 = 10–20 分钟/档，只在 RTL 变了才要）。
- ⚠️ **`--build` 必须与板子里烧的那一档一致。** 烧 pe4 却按 pe1 解包 → **256 个全错**，
  看着像 RTL 挂了。这是**响亮失败**，不会静默给出「看起来对」的答案。
- 端到端耗时约 **0.18 s / 0.27 s**，**三档几乎一样** —— 那是**串口搬运**的时间，
  核本身只占 **0.010%**。**别读成「折叠度没生效」。**

**加分（可选）**：`--build 4` / `--build 16` 各跑一遍 ——
「三档都验过」的**当面证据**，也是报告 §3.13 那几张表唯一的一次现场复核。每次换档要**重烧对应位流**。

## 四、为什么不见面（留档）

**原来的方案**：B 到 A 的工位当面联调。理由是「板子的两个 USB 与 Vivado 都只接在 A 这台机器上」。

**这条硬件事实仍然成立，但它不再构成见面的理由：**

1. **H6 的判据「B 的上位机第一次接真板子」已经不依赖 B 在场。**
   2026-10-07 夜，A 在本机用 **B 的** `host/src/board_run.py` 跑通了 `#NTT 1` ——
   上位机已经在真板子上跑过一次了。**这是一次实测，不是推断。**
2. **剩下的卡点是纯软件**：`host/src/host.py` 一处 `txn.count` 的语义，**不吃板子**。
   它能在**零硬件**下复现（`--loopback`），也能在 B 自己机器上验证完再推。
3. **原方案里「位流掉电即失 ⇒ 分两趟就要重出三档」的担心是多余的** ——
   掉电丢的是 **FPGA 里那份配置**，**磁盘上的 `.bit` 不会消失**；重烧约 **1 分钟/档**，
   与「重出」（10–20 分钟/档）是两回事。

⇒ **改成：B 远程改 + 自测 + push，A 在本机验收。** 省掉一趟往返，且两边可以并行推进。
