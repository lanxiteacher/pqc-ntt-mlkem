## 1. 总体判断

作品已经形成可运行的工程闭环，初级组的逻辑设计、状态机、接口协议与时序实现内容充足。最强项是分层验证和失败留证；最弱项是创新性与实际应用收益之间的连接。三档参数化、窄接口和验证平台有工程价值，但不能直接升级成新 NTT 算法、完整 ML-KEM 加速或系统级性能优势。

## 2. 必须先处理的事实与口径问题

### J01 / P0：CPU–FPGA 能耗倍数缺少可比基础

证据：`report/design/03_performance_and_resources.md` §3.10.5，尤其“45 W × 4.05 µs≈182 µJ”与“pe16 动态能量低约两个数量级”。

CPU 一侧是封装 TDP 假设，FPGA 一侧是 vectorless 动态功耗；边界、活动率、静态功耗处理均不一致。即使标“量级”，仍不能据此证实低两个数量级。PL 功耗乘纯计算时间也不是包含装载、读出、串口等待的实际每次事务能量。

优化：保留六版 FPGA 工具估算作为趋势分析，将 CPU 数字仅列为敏感性假设，撤下已证明能效倍数的结论。统一写明 E=P×T 中的功耗边界、活动率和时间窗口。若要提出实测能效优势，须补同任务、同边界、扣空闲策略一致的测量，不能用 TDP 代测量。

负责：A/C；B 可独立做公式与措辞审阅。完成标准：摘要、正文、图、视频均不把该估算写成已验证的 CPU 能效优势。

### J02 / P0：f/CC 只是纯计算上限，当前不等于可交付吞吐

证据：同章 §3.10.3、§3.10.6；`metrics/gen_pareto.mjs` 以 f/CC 生成吞吐；`rtl/board/proto_fsm.v` 明确顺序执行 S_LOAD→S_START→S_READ→S_OUT。

当前核必须串行装入和读出系数。没有证明计算、装载、读出可完全重叠，不能把 62.5 MHz/69≈905,797 NTT/s 叫成整机实测持续吞吐。即使去掉 UART，一次 256 系数装载、256 系数读出也不能免费消失。

示例下界：不重叠时至少考虑 256+69+256=581 拍，尚未加控制/流水开销。62.5 MHz/581≈107,573 次/s 只是这一简化边界下的上限，不是本轮测量值。当前每分钟 230.8 次的浸泡事务率则含串口、软件及间隔，边界不同。

优化：分别给出纯计算延迟、片内装载到读出延迟、真实串口事务延迟/持续事务率。利用现有仿真信号量相邻事务的启动间隔；没有量到启动间隔时，把 f/CC 标成计算阶段理想上限。带宽 roofline 同时标明采用文本协议 2124 B，而非通用二进制数据量。

负责：B 可量本机 RTL、C 同步指标/图、A 补实板统计。完成标准：不把时钟参数换算结果写成整机实测吞吐；图表不能混用边界。

### J03 / P1：ATP 定义需更精确

证据：同章 §3.10.6、`metrics/gen_pareto.mjs` 把 LUT×cycle 称为“面积×时间、与时钟无关”。

LUT×cycle 是面积与周期的乘积。真正时间为 cycle/f；频率不同时 A×T 排名不能不经复算直接沿用。只计 LUT 也没有计 DSP、BRAM、FF，不能概括成总资源效率最优。

优化：保留 LUT·cycle 名称；另列同频率或实际工作频率下的 LUT·µs，并独立展示 DSP/BRAM 限制。“pe4 最优”限定为三个已测配置与指定指标。

负责：C；B 复算。完成标准：指标单位、公式、条件一致。

### J04 / P1：CPU 基线尚不足以支撑普遍的速度优势

证据：`metrics/bottleneck_ref_timing.c:55` 和 `:63` 反复对同一数组调用裸 `ntt()`；未在每次调用间重新准备合法输入或约减，也没有导出最终结果用于语义核查。`metrics/bottleneck.py` 编译裸 ntt.c/reduce.c，正文比较边界使用 poly_ntt 及核结果。

反复 NTT 可能让输入离开该实现预期的有界表示，应先确认输入前提；裸 ntt 与 poly_ntt 的 reduce 步骤也不同。当前基线没有给出足够的 CPU 型号、运行电源模式、优化实现对照和完整原始轮次记录。现有数据仍可作为某次便携 C 参考实现计时，不能推广为 FPGA 战胜 CPU。

优化：明确比较同一语义任务；每次准备合法输入，区别记录输入准备开销；保存校验摘要与每轮时间，记录 CPU/系统/编译参数。至少区分“便携参考 C”和“经过优化的软件”，不强求这次加入 AVX2，但不能暗示已击败优化软件。

负责：C 的 metrics 实现，B 可在自己机器提供独立测试/审阅；不在未经协调时直接改 C 的生成器。

### J05 / P1：397→37 引脚的工程贡献不宜被写成技术上不可替代

证据：`report/design/02_design_and_innovation.md` §2.1、§2.3.3，特别是“第一次能真正落地”；`rtl/board/ntt_board_top.v` 的板级顶层只有时钟、复位、UART RX/TX 四个端口。

397 IOB 是把上游宽口核直接作为器件顶层的实现条件。宽口若连在 FPGA 内部 RAM、控制器或其他模块之间，不要求对应外部封装引脚。串行化是合理适配，但不存在“原核在此器件上任何集成方式都无法使用”的证明。37 是核顶层边界，不能与完整 UART 板级四引脚混称。

优化：增加“上游独立核顶层/本队窄口核顶层/完整板级顶层”边界表；把贡献落到地址参数化、接口时序适配、在面积/延迟/维护成本之间的取舍和已验效果。补一个序列化开销表或消融比较，比反复强调 397 更能回答原创深度。

负责：A/C。完成标准：能清楚说明采用此方案的理由和代价，并承认合理替代集成方式。

### J06 / P1：时序报告不支持无条件“零告警、全部约束完善”

证据：`rtl/vivado/reports/board_pe1_timing.rpt:46` 列 no_input_delay(2)、no_output_delay(1)，正文具体标 HIGH；`rtl/board/ntt_board.xdc` 只有时钟与管脚约束。基线顶层已有异步置位、同步释放复位，这是优点，不能误报成缺少复位同步。

UART 和按键属于异步接口，不能简单套同步输入延迟约束；但需要说明同步器、CDC、异步复位路径处理，以及为什么这些缺项可接受。时序 MET 只代表已约束/已分析路径，不能等同不存在任何设计风险。

优化：A 出一份约束覆盖说明，区分内部同步路径与异步外设接口；检查 CDC/同步器属性及必要例外。禁止为消除提示而盲目添加 false path。C 删除无边界“零告警”表述。

负责：A；B 只审阅原始报告和说明。完成标准：每个例外有对象、理由、验证依据。

### J07 / P1：最新提交的硬件证据还没有闭环

证据：`logs/verification_2026-10-21_B_phase2.md`、`host/serial_write_safety.md`。新增 count=1/2 只有 RTL；正式 SerialLink 修复只有本机验证。原 40 分钟 9233 次对应 A 旧 no-flush 浸泡路径。`logs/project_state.md` 同时还保留“A 板子已无后续任务”的旧收工判断。

优化：A 接板完成新增两份三档回放（90 次）及新正式驱动回归；保留当前提交、位流 SHA、档位/频率/波特率和原始结果。若暂不补，提交物仍保留“45 真板、135 RTL”的区分。

负责：A，B 复核结果，C 回填。完成标准：记录能对应最新驱动与实际输入哈希，不能借旧日志销新任务。

### J08 / P1：异常能被发现，但正式 CLI 还缺少完整的失败留证

证据：`host/src/board_run.py` 正常事务分支直接 `hst.run()`，最终才 `lk.close()`；缺少包围该分支的 try/finally。新发送逻辑会传播超时/短写/断连异常，因此 CLI 可能直接 traceback 并跳过显式关闭和结构化失败摘要。进程退出通常会释放句柄，不声称串口会永久占用；外层 run_kem_board.py 已有部分失败留证，二者须区分。

优化：B 增加结构化失败状态与 finally 关闭，保留异常类型和已发/已收阶段，不自动重试半帧。用受控短写、断连、写超时验证退出码、日志及资源关闭；不要通过吞异常伪造成功。

完成标准：三类失败均非零退出、留证、调用 close，成功路径不变。

### J09 / P1：通信协议没有数据级完整性保证

证据：`host/proto.md` §5.4 明确数据行无校验，控制行仅 XOR；build 只在上电 RDY 尽力发送，可能缺失。已知答案检查能发现最终错值，但任意应用输入在传输中变成另一个合法十六进制值时，不能靠格式检查检出。

优化：本届明确是受控验证链路，不宣称安全通信接口；立即可补合法数值篡改/错档/复位恢复的故障实验和失效边界。CRC、事务序号、主动身份查询可作后续协议 v2 候选，冻结前不建议为此全面改协议。

负责：A/B 协议共同决策。完成标准：展示与报告说明当前检测到什么、检测不到什么，不将“6/6 零差异”写成误码率证明。

## 3. 验证体系还能增加的高价值检查

### J10 / P2：增加少量独立数学性质，比继续堆同源样本更有价值

现有 C 参考+兼容 KAT+实际 RTL+变异控制已形成很强的证据，不存在“全部都是自己对自己”的问题；但许多检查复用同一 C 算法。可独立写朴素的模 (x^256+1) 卷积，检查 FULL 乘法的数学结果，再加单项式、单位元、零多项式、线性性质。先澄清 Montgomery 因子和排列，不能拿错域的结果误判硬件。

B 可在 refsim/ 做；无板。验收：独立于 NTT/basemul 实现的 oracle 与三档完整乘法一致，故意改变符号/排列时检查失败。它是可选强化项，不是原正确性结论被推翻。

### J11 / P1：文档、复现与最终提交版本存在漂移

证据：报告第五章仍有“驱动脚本未入库”等当前已失效表述；冻结清单写 Host 9 脚本且未纳入 B Phase 2 总入口；主状态旧收工判断与新交接冲突。提交清单 AI 日志数量也已过期。已更正的历史记录无需重写，当前入口必须一致。

优化：确定一个提交版本和一份带哈希的交付清单，核对源码、bitstream、报告、指标、视频；为评委提供最短入口和慢速完整验证入口。提交前从实际最终压缩包解压验证，不能只检工作目录。H10 是团队设定的换机验收，不应冒充指南明文要求独立第二台电脑；目前如实说明同机干净克隆已验。

负责：A/B/C；B 可查链接、命令和状态，C 出最终 PDF/视频，A 管位流。完成标准：陌生人拿到包可找到全部证据，运行失败能定位，版本不混杂。

### J12 / P2：协作与技能包展示应重决策、重迁移

现有归因、失败轨迹、许可证清单和逐日日志是优点。不能按日志数量或代码行数论证贡献，也不能把“零基础”当加分依据。

优化：选 3 个明确案例，展示人的需求/判断、模型的错误、如何用证据否定、最终改法与验证结果；再选已具备通用性的检查器，在第二种算法/干净环境中展示复用。不要倒补历史聊天，引用现有记录即可。PYNQ 额外加分需要真实 PYNQ 框架与通用性证据，纯 PL 或 JSON 检查器不能自动获得该加分。

负责：全员+C 汇总；B 的通用整数比较组件已有两算法离线证据，应引用已有成果而非重复实现。

## 4. 评委最可能问的十个问题

1. 上游提供了哪些模块？哪些是你们自己设计、哪些只是参数替换？请打开一个具体改动说明其必要性。
2. 397 引脚是完整系统的必要需求，还是核被直接设成顶层的结果？为什么不放到片内总线上？
3. 串口端到端远慢于 CPU，为什么这个作品仍有实际用途？哪类部署条件会获益？
4. pe16 的 69 拍从哪个 start 到哪个 done？输入准备、装载、读出、下一次启动各花多少？
5. pe4“最优”按什么指标？把 DSP、BRAM、实际频率和串行化开销加入后还成立吗？
6. 能量优势怎么测得？为什么 CPU 用 TDP、FPGA 用动态估算？
7. KAT 验证的是完整 C KEM 还是完整硬件 KEM？135 次里多少是真板？是否覆盖拒绝路径？
8. 为什么 51 个变异只捕获 50 个？等价项的源代码证明在哪里？
9. 发送一半拔线或板卡复位，程序会怎样退出？随意篡改一个合法数据值能否被检测？
10. 给另一队一份最终包，哪条命令能运行？实际测过哪些环境？三个成员分别作出了什么技术判断？
